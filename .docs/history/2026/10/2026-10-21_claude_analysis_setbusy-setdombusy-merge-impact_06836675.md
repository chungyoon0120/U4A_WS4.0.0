## 1. 판정 — 나눌 이유가 없다 (장군님 말씀이 맞다)

`setDomBusy` 는 `setBusy` 의 **부분집합**이다.

| 하는 일 | `setDomBusy` | `setBusy` |
|---|:---:|:---:|
| busy 창 여닫기 | O | O (같은 함수를 부름) |
| 0.6초 기다린 뒤 닫기 | O | O |
| 최상위 문서 pointerEvents 막기 | X | O |
| 포커스 저장·복원 | X | O |
| 작업표시줄 진행바 | X | O |
| 메인 창 닫기 버튼 | X | O(실제 영향 0 — 아래 2절) |

**왜 둘로 나뉘어 있나** = 설계가 아니라 잔재. `setDomBusy` 는 2026-09-15 전까지 busy 본체였고,
공통 파일(`theme/u4a-busy.js`)로 옮기면서 이름만 남았다. 호출처가 옛 이름을 그대로 쓰고 있다.

| # | 무엇 | 영향 |
|---|---|---|
| 1 | 메인 창 닫기 버튼 비활성/활성 | **0** — `setMainCloseBtnDisabled`(index.js 903) 가 `if (!oWS.utill.attr.sap) return;` 로 시작한다. UI5 를 뺐으므로 **실행되는 파일 중 `attr.sap` 을 세팅하는 곳이 한 곳도 없다**(`ws_main.js:1104` 에 「UI5 제거」 주석, `ws_main copy.js:854` 는 미로드 사본). 즉 늘 즉시 return |

| 3 | 작업표시줄 진행바 | 보이는 변화 — 로그인 중 Windows 작업표시줄 아이콘에 진행 표시가 켜진다 |

## 3. ★막는 것 하나 — 로그인 화면의 포커스

화면 겹침(로그인 때) = 최상위 문서(`ws10_20/index.html`) → iframe 1개(로그인 화면, `control.js:130`
에서 `createElement("iframe")`). `ws10_20/index.html:111~113` 의 `ws_frame` iframe 은 **주석 처리**돼 있다.

그래서 `index.js:964` 의 `ws_frame` 체크는 **안 타는 코드**이고, 늘 최상위 문서를 본다.
최상위에서 `document.activeElement` 를 물으면 돌려주는 것은 **iframe 요소**다 — 비밀번호 칸이 아니다.
저장되는 것이 iframe 덩어리이므로, 되돌릴 때 `iframe.focus()` 를 해도 **안의 어느 칸인지 정해지지 않는다.**

→ 합치면 로그인 실패 후 커서가 비밀번호 칸으로 안 돌아갈 수 있다.

**메인 화면(로그인 후)은 iframe 이 없어** 이 문제가 없다. 그래서 `parent.setBusy` 를 쓰는 WS20 62곳은 멀쩡하다.

고치는 방법 = 돌려받은 것이 iframe 이면 `iframe.contentDocument.activeElement` 로 다시 물어
iframe 이 안 나올 때까지 되풀이. 고칠 자리 **2곳**: `index.js` 966~983(`utill.fn.setBusy`) ·
1044~1070(`setBusyDialog`). 둘은 **같은 변수**(`oWS.utill.attr.beforeActiveElement`)를 쓴다.

**고쳐도 남는 것** — 화면이 다시 그려지면 저장해 둔 입력칸이 DOM 에서 떨어져 복원이 안 된다.
지금 `setDomBusy` 는 포커스를 아예 안 건드려서 **그 경우엔 지금이 낫다.**

**미확인** — 모달 `<dialog>` 는 닫힐 때 브라우저가 직전 포커스로 되돌려 준다(HTML 표준).
그렇다면 이 저장·복원 자체가 필요 없다. Chromium 93 에서 실제로 도는지는 **앱을 돌려 봐야** 안다.

## 5. 같이 찾은 것 (고치지 않음 · 결정 대기)

- **순수 중복 3곳** — `ws_main.js` 1185·1265·1283 은 `parent.setBusy("")` **바로 다음 줄**에
  `parent.setDomBusy("")` 가 또 있다. 전에 길이 두 갈래였던 흔적. 이제 앞 줄이 뒤 줄을 포함하므로
  뒤 줄이 남아 있으면 기다림이 **2개 동시에** 돈다(1.2초는 아니지만 쓸데없이 두 번). 위험 0, 지우면 된다.
- 이름만 같은 다른 변수 `oAPP.attr.beforeActiveElement` 8곳(`ws_common.js` 저장 5 · `ws_events.js` 복원 2 ·
  `ws_usp.js` 복원 1)은 **단축키(「Active」·「Save」·코드 정리)** 가 쓰는 것이다. busy 와 안 섞인다.

## 6. 내가 틀렸던 것 (판정 2회 정정)

1. 「`setDomBusy("")` 는 그 자리에서 바로 끈다」 — **틀렸다.** 기다림이 `U4ABusy.hide()` 안에 있어
   양쪽 다 0.6초 기다린다. `hide()` 안을 안 보고 썼다.
2. 「`setDomBusy` 는 필요하다 — 바로 꺼야 하는 자리 전용」 — 1번이 틀렸으므로 이 근거도 무너졌다.
   남는 차이는 부수 작업뿐이고, 그중 실제로 걸리는 것은 포커스 하나다.

**또 밟을 함정**: 두 함수를 비교할 때 **각자가 부르는 아래쪽 함수까지 읽어야 한다.**
겉면(`setDomBusy`)만 보고 「기다림이 없다」고 판단했다가 두 번 정정했다.

## 7. 용어

「iframe 대응」은 내가 만든 말이다 — 쓰지 않는다. **「포커스를 찾을 때 iframe 안에서 다시 묻는다」** 로 적는다.
