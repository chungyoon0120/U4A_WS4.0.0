# UI 개인화 팝업이 처리중 표시가 꺼진 뒤에야 뜨던 것 — 수정

- 시각: 2026-10-22
- 장군님 지적: 「지금은 busy 만 켜지고, 한참 있다가 busy 가 꺼진 이후에 팝업이 바로 뜨게 동작한다」
- 장군님이 정하신 올바른 순서: **busy 켜기 → 팝업 껍데기 나오기 → 내용 그리기 → busy 끄기**

## 원인

`fnP13nDesignPopupOpen`(`js/fnP13nDesignPopupOpen.js`)이 `oUI.dlg.show()` 바로 뒤에
**양보 없이** `lf_afterOpen()` 을 불렀다. 그 안에서 미리보기 HTML 만들기·목록 그리기가
동기로 이어져 **브라우저가 화면을 다시 그릴 틈이 없다** → 팝업 껍데기가 안 보이고,
다 끝난 뒤에야 한꺼번에 나타난다.

같은 파일 85~87행 주석에 이미 그 함정이 적혀 있었다(「양보가 없으면 busy 가 그려질 틈이 없어
화면이 그냥 멈춰 보인다 — 실측 10.6초」). **다른 조작(`_busyThen`)에는 넣었고 여는 길에만 빠져 있었다.**

## 고친 것

`show()` 직후 `APPCOMMON.fnYieldToPaint()` 로 **한 번 양보**한 뒤 `lf_afterOpen()` 을 부른다.

★**이 함수는 동기 그대로 뒀다**(async 로 바꾸지 않음) — 호출처 2곳
(`ws_html5_ws20_edit.js:2714` · `ws_html5_ws20_tree.js:363`)이 `try/catch` 로 감싸는데,
async 로 바꾸면 그 catch 가 예외를 못 잡는다(`.claude/rules/code.md`).
대신 `lf_afterOpen()` 을 작은 함수로 묶어 `.then(fnAfter, fnAfter)` 로 넘기고,
그 안에서 자체 `try/catch` + 실패 시 `_unlock()` · `_busy(false)`.
양보 함수가 없으면 `GUARD_EXIT` 로그를 남기고 전처럼 바로 부른다.

## 내가 판정을 두 번 틀렸다 (되풀이하지 말 것)

1. 「창은 끄기 전에 이미 떠 있다」 — **코드만 보고** 말했다. 화면에 언제 그려지는지를 안 봤다.
2. 「busy 가 팝업을 가린다」 — **틀렸다.** 공통 busy 의 backdrop 은 `transparent`
   (`theme/u4a-busy.css` 63행)라 가리지 않는다. 확인 없이 top-layer 만 보고 단정했다.

→ **함정: `show()`/`appendChild` 를 불렀다고 화면에 보이는 것이 아니다.**
  그 뒤에 동기 작업이 이어지면 **그 덩어리가 끝나야** 그려진다. 「떴나」를 코드로 판정하지 말 것.

## 덧 — 「기다림 상한에 닿음」을 오류에서 참고로 낮춤 (장군님 지적 2026-10-22)

> 「busy 는 말 그대로 오랫동안 돌아갈 수 있는 거야 … 근데 마치 오류처럼 이렇게 하는 건 아니지」
> 「느린 PC 에서 실행할 경우 … 화면 그리는 시간이 오래 걸릴 경우는 이걸 오류 콘솔에 남기는 게 맞는 건지?」

**맞지 않다.** 끄기 신호 뒤 화면이 잠잠해지기를 기다리다 5초 상한에 닿으면 그냥 끄는데,
그것은 **정상 경로**다 — 화면도 멀쩡하다. 느린 PC 에서는 더 자주 난다.

`theme/u4a-busy.js`:
- 빨간 오류(`console.error`, 코드 `UBSY-005`) → **참고**(`console.info`)로 낮췄다.
  코드는 뺐다(다른 곳에서 안 쓴다 — 실측 0건).
- 상한 상수 주석의 「고장 알림용」을 지우고, **왜 상한을 두는지**(없으면 영영 안 꺼짐)와
  **오류가 아님**을 적었다.
- 값(얼마나 기다렸는지 · 몇 번 바뀌었는지)은 그대로 `[BUSY]` 줄에 남는다.

### 함정

**「시간이 오래 걸린다」를 오류로 찍지 말 것.** 느린 PC 는 정상 범위다
(`.claude/rules/always.md` 「항상 느린 PC 도 고려한다」). 상한은 **멈추지 않게 하는 안전장치**이지
고장 신호가 아니다.
