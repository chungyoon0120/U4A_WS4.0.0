# 테마 디자이너 창 최대화 시 ResizeObserver loop limit exceeded

- 날짜 **2026-10-12** · 세션 `abc286a4` · type `fix`
- 장군님 제보 + 캡처: 테마 디자이너 창을 최대화하니 크리티컬 오류창.
  「ws3.0 → ws4.0 초반에 많이 나왔던 오류」 → **맞다. 같은 종류다.**
- 테스트 TD1~TD4 · UW1~UW5 **전부 통과(2026-10-13)** — 테스트 문서는 끝나서 지웠다(장군님 지시).
  이 파일이 이 건의 유일한 기록이다.

## 원인

`Popups/monacoThemeDesign/Popup/js/wizardNav.js` 의 ResizeObserver 콜백 2곳이
**콜백 안에서 동기로 레이아웃을 바꾼다** → 같은 delivery 사이클에 재발화 → loop limit 초과.

| 자리 | 콜백이 하는 일 |
|---|---|
| `_wzNavResize(nav)` (관측 대상 = `oNav`) | `classList.remove("is-collapsed")` → `scrollWidth/clientWidth` 읽기 → `classList.toggle` → `_renderMiniCollapsed` 로 DOM 재생성 |
| `_updateScrollPad(oPage)` (관측 대상 = `oPage`·`oContent`) | `oPage.__pad.style.height` 를 바로 바꾼다 |

창 최대화는 폭 변화가 커서 재발화가 한계를 넘기 쉽다.

## 해결 — 원인 제거 (오류 삼키기 아님)

콜백 본문을 `requestAnimationFrame` 으로 **다음 프레임에 1회 코얼레싱**. 재진입 가드(`__roRaf`/`__padRaf`) 동반.
delivery 사이클 밖에서 레이아웃이 바뀌므로 루프가 성립하지 않는다.

**근거**: `.analy/16 §3.4.2`(ResizeObserver 를 계속 붙여둬야 하면 rAF 로 미룬다) ·
공통 `attachOverflow` 의 `_scheduleReflow` 와 같은 방식 ·
메모리 `resizeobserver-loop-defer-with-raf` / `resizeobserver-loop-benign-guard`.

★**onError 에서 이 오류를 삼키는 가드는 절대 금지**(장군님 지적 2026-07-10) — 넣지 않았다.

## 검증

- `node --check` 통과.
- 실제 동작은 **장군님 테스트 대기**(TD1~TD4).

## 같은 결함이 남아 있는 곳 — 손대지 않았다 (지시 대기)

| 파일 | 자리 |
|---|---|

## 이 오류가 되풀이되는 까닭 (기록)

같은 패턴이 변환물 여러 곳에 **복사돼 퍼져 있다.** 한 곳을 고쳐도 복사본이 남아 다시 터진다.
공통 위저드 자산을 쓰는 창을 만들 때 **RO 콜백은 무조건 rAF 로 감싼다**를 지키는 수밖에 없다.

## 원본(as-is) 확인 — 원본에 없던 결함

본 곳 : `U4A_WS_DESIGN\Popups\monacoThemeDesign\` (디자인 영역 담당 원본)

| 확인한 것 | 결과 |
|---|---|
| 원본에 ResizeObserver | **0곳** |
| 원본의 위저드 | `sap.m.Wizard` + `WizardStep` 3개 (`Popup/views/vw_main/view.js` 134·153·238·417줄) |
| 진행 가로줄 접힘을 원본이 직접 처리하나 | **안 한다** — UI5 컴포넌트 안에서 처리 |
| 그 UI5 컴포넌트 소스가 이 PC 에 있나 | **없다** — 개발 때 CDN 에서 받아온다 |

즉 **HTML5 로 옮길 때 진행 가로줄 접힘을 손으로 다시 만들면서 생긴 결함**이다.
그래서 고침 기준은 「원본 1:1」이 아니라 **브라우저 규칙** 하나다 —
ResizeObserver 콜백 안에서 레이아웃을 바꾸지 않는다.
같은 자산을 복사해 쓴 UI 템플릿 마법사도 원본에 없던 손제작 코드다.

## rAF 로 미뤄도 되는지 — 함수 5개 전수 확인 (2026-10-13)

장군님 「100% 보장되면 고쳐라」 → 함수 본문을 끝까지 읽고 판정했다.
(앞서 「보장 못 한다」고 한 것은 **읽지 않고 한 말**이었다.)

| 확인한 것 | 결과 |
|---|---|
| 매번 불리는 걸 전제로 뭔가 누적하는가 | **전부 아니다** — 지금 폭·높이를 읽어 **처음부터 다시 계산**한다. 몇 번 불리든 마지막 결과만 남는다 |
| 다른 코드가 중간 결과를 읽는가 | **전부 아니다** — 돌려주는 값이 없고 화면 모양만 바꾼다 |
| 창이 닫힌 뒤 한 번 더 돌면 터지는가 | **아니다** — 다섯 다 맨 앞에 대상이 DOM 에 없으면 빠져나가는 가드가 있다(`document.body.contains` / `isConnected`). `cancelAnimationFrame` 없이도 안전 |

확인한 다섯 자리 : UI 템플릿 마법사의 아래 여백 · 진행 가로줄 접기 · 좌우 칸 폭 보정 /
WS20 속성 개인화 팝업의 좌우 칸 폭 보정 / WS10 앱 목록 창의 작은 머리줄 접힘.
가로줄 접기와 작은 머리줄 접힘은 **매번 전부 펼친 상태에서 다시 측정**하므로 누적이 없다.

당시 적어 둔 남는 위험 = 「좌우 칸 폭 보정이 한 프레임(약 16ms) 늦어 최소폭을 살짝 넘은 상태가
한 프레임 보일 수 있다 — 띄워 봐야 안다」. **TD4 · UW3 통과로 해소**(눈에 띄지 않는다).
`window` 의 resize 는 지금도 따로 즉시 호출되고 그 경로는 건드리지 않았다.
