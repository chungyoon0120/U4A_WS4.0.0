# 미리보기에서 UI 를 고르면 처리중 표시가 1.5초씩 걸리던 것 — 수정

- 작성 2026-10-20 · 세션 06836675 · type=fix
- 지시: 장군님 「미리보기 영역 내의 UI 요소를 클릭 … 숨겨져 있던 UI를 선택할때 busy 종료 시간이 길어 왜그런거지?」 → 분석 → 「고쳐라」

## 1. 증상

WS20 편집 화면에서 **미리보기를 스크롤해 안 보이던 UI 를 클릭**하면 처리중 표시가 **1.5~1.7초** 떠 있다. 좌측 UI 트리에서 고르면 0.1초면 끝난다.

## 2. 숫자 (콘솔 + Performance 실측)

```
[BUSY] on→off=1662ms mut=159 (offSignal→off=1527ms quiet=72ms idle=1527ms)
```
- **화면 그리기는 72ms 에 끝났다**(quiet). 느린 것은 그 뒤 **브라우저가 한가해지기를 기다린 1527ms**.
- Performance Bottom-Up(27초 기록, 여러 번 클릭 합계):
  - 동기 IPC(`i.sendSync`) **902ms** — 펼쳐 보니 전부 `@electron/remote` (객체 얻기 306 + 함수 부르기 344 + 값 읽기 236 + 창 얻기 16)
  - Recalculate Style 840ms (`ResizeHandler-dbg.js`) · Layout 530ms
  - 트리 줄 만들기 1147ms · 트리 다시 그리기 1227ms · 줄 오른쪽 버튼 만들기 982ms
  - Total blocking time 1506ms

## 3. 원인

선택 처리(`ws_html5_ws20_attr.js` `fnWs20SelectUI`) 6단계가 **선택 표시 하나 바꾸려고 `fnRenderDesignTree()` 로 트리를 통째로 다시 그렸다.**

다시 그리면 보이는 줄을 전부 새로 만들고, 줄마다 ＋·삭제 버튼을 만들며 **버튼 제목 두 개를 메시지 DB 에서 꺼낸다.** 그 경로가 `@electron/remote` 라 **글자 하나당 메인 프로세스를 세 번 왕복**(`REMOTE.getGlobal('WsMsgCls')` → `.getRow(...)` → `.TEXT`). 줄 100개면 600번. 동기 IPC 라 그동안 화면이 완전히 멈춘다.

**왜 좌측 트리에서 고르면 빠른가** — 선택 처리 8단계가 트리를 그 줄로 스크롤하는데, 좌측에서 클릭했으면 그 줄이 이미 보이므로 스크롤이 없고 줄도 적게 바뀐다. 미리보기에서 고르면 트리에서 그 줄이 화면 밖이라 스크롤 + 그 구간 줄 전부 새로 만들기가 걸린다.

## 4. 고친 내용

| 파일 | 무엇 |
|---|---|
| `js/ws_html5_ws20_tree.js` | `fnWs20TreeMarkSelected` 신규 — 공통 트리의 `selectKey(key, false)` 로 **지금 그려진 줄의 강조만** 바꾼다(스크롤·재생성 없음) |
| `js/ws_html5_ws20_tree.js` | 트리 줄 클릭 핸들러의 즉시 하이라이트를 `fnRenderDesignTree()` → `fnWs20TreeMarkSelected()` 로 |
| `js/ws_html5_ws20_attr.js` | `_expandTreePathTo` 가 **실제로 새로 펼친 조상이 있었나**를 반환하도록 |
| `js/ws_html5_ws20_attr.js` | 선택 처리 6단계 — 펼침이 **안 바뀌었으면 강조만**, **바뀌었으면 종전대로 다시 그리기** |

공통 트리의 `selectByKey`(`theme/u4a-ui.js`)는 가상 스크롤에도 선택 키를 넣어 두므로, 그 줄이 화면 밖으로 나갔다 들어와도 강조가 복원된다. **공통 자산은 한 줄도 안 고쳤다** — 이미 있던 기능을 WS20 이 안 쓰고 있었을 뿐이다.

오류코드 접두 `W20T` 신규 등록(`.works/DEV_STANDARD_오류처리.md`). `W20A` 다음 번호 005→006.

## 5. 틀렸던 판정 · 버린 방법

- **「동기 IPC 902ms 는 메시지 조회다」를 확인 없이 단정했다.** 장군님께 그 전제로 수정 제안까지 한 뒤에야 Performance 에서 펼쳐 확인했다(결과적으로 맞았지만 절차가 틀렸다). 이 일로 공통 지침 `always.md` 에 0-3 항목(장군님 말씀도 먼저 검증하고 틀리면 반박한다)을 넣었다.
- **「59%가 메시지 조회」라고 말한 것도 과했다.** 그 886ms 는 **27초 기록 전체의 합계**지 한 번 클릭 값이 아니다.
- **버린 방법: 메시지 글자만 한 번 읽어 캐시하기.** 증상만 덮는다 — 트리를 통째로 다시 그리는 것은 그대로라 스타일 재계산 840ms · 레이아웃 530ms 가 남는다. 원인을 고치면 메시지 왕복은 **고칠 필요 없이 사라진다.**

## 6. 또 밟을 함정

- **선택 표시 하나 바꾸는 데 목록 전체를 다시 그리지 말 것.** 공통 트리에 이미 `selectKey`(강조만)가 있다. 다시 그리기는 **줄 목록이 달라질 때만**(펼침·접힘·데이터 변경).
- **`@electron/remote` 호출은 전부 동기 IPC 다.** 반복문 안에서 부르면 횟수만큼 화면이 멈춘다. 게다가 **객체를 받아 속성을 읽는 것도 왕복**이라 한 줄처럼 보여도 3번이다.
- **처리중 표시가 늦게 꺼지는 것 ≠ 화면 그리기가 느린 것.** 끄기는 ①DOM 조용 ②브라우저 한가 둘 다를 기다린다(`resources/index.js _u4aBusyOffWhenSettled`). 그리고 **DOM 감시는 메인 창만 본다 — 미리보기 iframe 안은 안 센다.**
