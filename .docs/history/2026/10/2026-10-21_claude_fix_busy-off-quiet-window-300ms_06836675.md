# busy 끄기 판정을 0.3초 창으로 바꿈 (requestAnimationFrame 2 frame → 0.3초)

- 작성 2026-10-21 · 세션 06836675 · type=fix
- 지시: 장군님 「busy가 끄는 시점에 mutation을 키고 0.3초마다 체크해서 그려지는게 있는지 감지.
  mutation에서 0.3초 안에 변경 되는 부분이 있을 경우는 다시 기다리다가 0.3초가 지나도 mutation이
  안타면 그 다음에 request idle request를 걸고 거기에 도착하면 0.3초 기다렸다가 busy 끄기」
  → 「4번이면 이미 끝난거라고 보라고」 → 「커밋 푸시 부터 하고 혹시나 되돌아갈걸 대비한 뒤에 고쳐라」

## 1. 바꾼 것

| 파일 | 무엇 |
|---|---|
| `www/ws30/resources/index.js` | 메인 창 전역 busy 끄기 — 판정 방식 교체 |
| `www/ws30/ws10_20/theme/u4a-busy.js` | 별창 공통 busy 끄기 — 같은 방식으로 맞춤 |

되돌릴 지점 = 커밋 `9dd7bbf6` (고치기 전, `git reset --hard 9dd7bbf6`).

## 2. 새 판정 순서

1. 끄라는 신호(`setBusy("")` / `U4ABusy.hide()`)가 오면 MutationObserver 를 켠다
2. **0.3초**마다 확인 — 그 창 안에 변경이 있었으면 **다시 0.3초**
3. 0.3초 동안 변경 0 → `requestIdleCallback` 을 건다(남은 상한만큼 timeout)
4. 도착하면 **0.3초 더 기다린 뒤 무조건 끈다**

- **4번의 0.3초 동안 일어난 변경은 판정에 쓰지 않는다** — 장군님 판정 「4번이면 이미 끝난 것으로 보라」.
  세기만 해서 로그(`lateMut`)에 남긴다. 다시 세기로 하면 조금씩 계속 바뀌는 화면에서 영영 안 꺼진다.
- 상한 5000ms 는 그대로. 2번 자리에서만 본다(계속 바뀌면 거기서 끊고 `BUSY_OFF_LIMIT` 오류 로그).
  4번의 0.3초는 상한 뒤에 붙을 수 있어 최대 5.3초.
- 세대 번호(기다리는 사이 다시 켜면 그 끄기를 버림)는 종전 그대로.

## 3. 왜 바꿨나 — 장군님 지적과 내 답

장군님: 「그리기 전에 타는 거면 busy 끌 때 걸면 의미가 없잖아」 · 「내가 볼 땐 필요 없을 것 같은데?
busy 끄는 건 화면 다 그려진 이후에 끌 텐데 대부분」

내가 답한 것 — `setBusy("")` 를 부르는 시점은 **DOM 을 다 바꾼 직후**이고 화면은 아직 안 그려졌다
(JavaScript 가 한 묶음 끝까지 화면을 안 그린다). 그래서 기다림 자체는 필요하다. 다만 종전 방식
(`requestAnimationFrame` 으로 변경 없는 frame 2번)은 **frame 단위라 간격이 ~16ms** 로 너무 짧아,
UI5 가 조금씩 이어 그리는 사이에 「조용해졌다」로 보기 쉬웠다. 0.3초 창은 그 틈을 덮는다.

## 4. 로그 변화

- `[BUSY]` 개발 모드 한 줄에 `rounds=` 추가 — 0.3초 창을 **몇 번 다시 셌나**(그만큼 화면이 늦게 멈췄다).
- `[RSRC-015]` / `[UBSY-006]` 문구를 `mutations after quiet` → `mutations during final grace` 로.
  뜻이 「조용해짐 확정 뒤」에서 「마지막 0.3초 여유 중」으로 바뀌었다.

## 5. 아직 안 본 것 · 또 밟을 함정

- **앱에서 확인하지 않았다**(장군님이 직접 돌리신다). busy 는 TODO 에 테스트 항목으로 올리지 않는다
  (장군님 지시 2026-10-20 — 전용 도구로 보신다).
- **켤 때 도는 감시는 손대지 않았다.** 그건 개발 모드 전용 측정용(`_u4aBusyWatchStart` /
  `_watchStart`)이고 끄기 판정에 쓰이지 않는다. 「패키징본에서도 한 줄 찍게 할까」는 **미결** —
  지금은 고객사 PC 에서 busy 가 늦게 꺼져도 로그로 알 수 없다.
- **미리보기 iframe 안은 여전히 못 본다.** 두 감시 모두 `document.body` 하나만 관찰하고,
  미리보기는 별도 document 다. 그래서 미리보기 안에서 늦게 바뀌는 것은 이 판정에 안 잡힌다
  (자동 테스트 도구가 CDP 로 잡는 것이 그쪽이다).
- **미리보기 선택 테두리 다시 맞추기는 `requestAnimationFrame` 으로 한 frame 미뤄진다**
  (`design/preview/index.js` `requestPreviewSelectionLayerUpdate`). 이제 0.3초 창 안에 들어오므로
  메인 창 쪽은 덮이지만, 미리보기 iframe 안에서 일어나는 것은 위와 같은 이유로 안 잡힌다.
- **속성값 변경에 원본 마지막 줄(`await selPreviewUI(...)`)이 누락돼 있다** — 이번 수정과 별건이고
  고치지 않았다. 조사 내용은 이 세션에서 보고만 했다.

# [후속 2026-10-21] 창 300ms → 150ms — 전체 0.6초를 0.3초로

- 지시: 장군님 「0.6초도 왠지 느린 거 같은데.. 전체 0.3초로 맞춰바」
- 되돌릴 지점 = 커밋 `15c2a760`

## 1. 바꾼 것 — 상수 한 줄

`theme/u4a-busy.js` 의 `QUIET_WINDOW_MS` 300 → **150**.
그 상수를 쓰는 곳이 3군데(①② 창 반복 · ④ 마지막 여유 · 첫 창 시작)라 **한 줄로 양쪽이 같이** 줄었다.
→ 끄기 신호부터 실제로 꺼지기까지 150 × 2 = **300ms**.

주석에서 「0.3초」라고 박아 둔 표현을 **「조용함을 보는 창」·「한 창 더」** 로 바꿨다(수치는 상수 한 곳에서만
말한다). 고친 파일 = `u4a-busy.js`(머리 주석·본문 4곳) · `resources/index.js` 1767 ·
`ws_html5_ws20_attr.js` 3169. `index.js` 1763~1764 와 `ws_html5_shell.js` 245 는 **과거 사실**이라 그대로 뒀다.

## 2. 반박한 것 (지시대로 하되 밝힘)

창이 짧아질수록 「조용해졌다」로 잘못 보기 쉽다. 잘못 보는 구간은 **UI5 가 이어 그리는 틈이
150~300ms 인 경우**다 — 틈이 150ms 보다 짧으면 ②가 다시 세므로 계속 기다린다.
그 틈이 실제로 얼마인지는 **재 본 적이 없다.** 그래서 「위험하다」고 단정하지 않았고, 지시대로 줄였다.

## 3. 검산하는 방법 (로그)

개발 모드에서 busy 가 꺼질 때마다 `[BUSY]` 줄이 한 줄 찍힌다. 거기서 보는 값:

| 칸 | 뜻 | 보는 법 |
|---|---|---|
| `rounds=` | 창을 **다시 센 횟수** | 0 이 대부분이면 창이 충분하다. 자주 1~2 면 화면이 늦게 멈추는 것 |
| `quiet=` | 조용해진 시점(ms) | 150 근처면 한 창에 끝났다는 뜻 |
| `lateMut=` | ④ 의 한 창 동안 바뀐 건수 | **0 이 아니면 그 창이 짧다** — 다 안 그려진 채 꺼졌을 수 있다 |

★`lateMut` 이 꾸준히 0 보다 크면 150 이 짧은 것이다. 그때는 이 값을 다시 올린다(고칠 자리 = 상수 한 줄).
`[UBSY-006]` WARN 줄도 같은 것을 알려 준다.

## 4. 또 밟을 함정

- **수치를 주석에 박지 마라.** 이번에 「0.3초」라고 적은 주석이 9곳이나 돼 전부 고쳐야 했다.
  수치는 상수 선언 한 곳에서만 말하고, 설명은 「창」·「한 창 더」로 쓴다.
- **상한(SETTLE_LIMIT_MS 5000)은 ② 자리에서만 본다** — ④ 의 한 창은 상한 뒤에 붙을 수 있어
  최악은 5.15초다(종전 5.3초).
