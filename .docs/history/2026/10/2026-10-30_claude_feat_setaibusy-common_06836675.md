# AI 제어용 공통 busy `setAIBusy(bOn, oOpt)` 를 만들었다

- 날짜: 2026-10-30
- 지시: 장군님 「공통 busy 를 하나 더 만들어야 하는데 이 busy는 **기존 busy를 그대로 사용하면서**
  AI 가 ws4.0을 제어할 때 사용하는 busy의 역할이야. 파라미터는 두개, 공통 함수 이름은 `setAIBusy`.
  첫번째 파라미터는 키고 끄는 인자값으로 true, false로 받고, 두번째는 object 형태로 만들어서
  **확장 가능하게** 하되, `desc` 이 필드를 추가해 … **`\n` 이 오면 개행해서 표현**해줘야되는거 알지?」

## 만든 것

| 파일 | 무엇 |
|---|---|
| `www/ws30/ws10_20/theme/u4a-busy.js` | `setAIBusy(bOn, oOpt)` + `_setAIText()` 추가. `U4ABusy.setAIBusy` 와 **전역 `window.setAIBusy`** 둘 다로 내보낸다 |
| `www/ws30/ws10_20/theme/u4a-busy.css` | `.u4aWsBusyText` 에 `white-space: pre-line;` 한 줄 — `desc` 의 개행이 그대로 보이게 |
| `.analy/16` §2.10 | 공통 busy 표에 「AI 가 제어하는 동안」 행 추가 |

```js
setAIBusy(true, { desc: "작업중입니다. \n 잠시만 기다려 주세요" });
setAIBusy(false);
```

## 어떻게 동작하나

- 켤 때: `show()` → **그 다음에** `#u4aWsBusyText` 에 `desc` 를 넣는다.
  **순서가 중요하다** — `<dialog>` 는 처음 `show()` 할 때 스스로 만들어지므로, 먼저 글을 넣으려 하면 자리가 없다.
- 끌 때: `hide(콜백)` 으로 끄고, **busy 가 실제로 꺼진 뒤** 글을 지운다.
  먼저 지우면 busy 가 아직 떠 있는 0.3초 동안 **글만 사라져** 이상하게 보인다.
- 글은 `textContent` 로 넣는다 — `innerHTML` 이 아니다. `desc` 에 태그가 섞여 들어와도 글자로만 보인다.
- 개행은 CSS `white-space: pre-line` 이 그린다. `pre-line` 은 연속 공백을 하나로 합치므로
  **개행이 없는 기존 글(서버 목록 안내·로그인 남은 초·버전 관리)은 보이는 것이 같다.**

## ★아직 안 막은 것 — **겹치면 서로 꺼 버린다** (보고만, 지시 대기)

`setAIBusy` 는 **같은 `<dialog>`** 를 쓴다(「기존 busy 를 그대로 사용」 지시대로).
그래서 AI busy 가 켜져 있는 동안 화면 안 다른 처리가 `U4ABusy.hide()` 를 부르면
**AI busy 도 같이 꺼진다.** 그때 내 콜백은 안 불리므로 **글자가 지워지지 않고 남아**,
다음에 다른 busy 가 켜질 때 그 글이 그대로 보인다.

막는 길은 두 가지다(아직 안 했다).
1. AI busy 가 켜져 있는 동안 `hide()` 를 **무시**한다(AI 가 바깥을 감싼다).
2. 깊이(개수)를 세어 0 일 때만 실제로 끈다 — 2026-09-09 지시의 방식.

둘 다 `hide()` 를 고쳐야 하고 `U4ABusy.hide()` 를 쓰는 자리가 **20곳**이라 영향도 조사가 먼저다.

## 눌러 볼 것 (busy 라 TODO 에 넣지 않는다 — 2026-10-29 지시)

아직 **AI 제어 쪽에서 부르는 자리가 없어** 화면으로는 확인할 데가 없다.
개발자 도구 콘솔에서 한 줄로 볼 수 있다.

```js
setAIBusy(true, { desc: "작업중입니다. \n 잠시만 기다려 주세요" });   // 두 줄로 보이면 OK
setAIBusy(false);                                                      // 꺼지고 글도 사라지면 OK
```

## 미검증

- **앱으로 돌려 보지 않았다.** `node --check` 통과.
- `white-space: pre-line` 이 기존 세 자리(서버 목록·로그인·버전 관리)의 보이는 모양을 바꾸지 않는지
  **눈으로 확인하지 않았다.** 그 글들에 개행이 없다는 것은 소스로 확인했다.

## 또 밟을 함정

- **주석에 역슬래시+n 을 쓰려다 실제 개행이 되어 주석이 두 줄로 갈라졌다**(이번에 세 자리).
  스크립트로 파일을 고칠 때는 그 두 글자를 소스에 직접 쓰지 말고 `chr(92) + "n"` 으로 조합한다.
- **`#u4aWsBusyText` 는 공용 자리다.** 서버 목록(안내 문구) · 로그인(남은 초) · 버전 관리도 쓴다.
  거기에 글을 넣는 기능을 새로 만들면 **끌 때 반드시 비운다** — 안 비우면 다음 busy 에 남는다.

## ① 자물쇠 — AI 제어 중에는 다른 busy 를 막는다

`theme/u4a-busy.js` 에 `bAILocked` 를 두고, 바깥에 내보내는 `show` / `hide` 를 **얇은 래퍼**로 바꿨다.
알맹이는 `_showCore` / `_hideCore` 로 이름만 옮겼다(내용은 그대로).

| | 자물쇠가 풀려 있을 때(평소) | AI 제어 중 |
|---|---|---|
| `U4ABusy.show()` | **전과 똑같다** | 무시 + `[UBSY-008]` 한 줄 |
| `U4ABusy.hide(fn)` | **전과 똑같다** | 무시 + `[UBSY-009]`, 단 **`fn` 은 불러 준다** |
| `setAIBusy` | — | 자기 자신은 `_showCore` / `_hideCore` 를 바로 부르므로 안 막힌다 |

### ★켜기만 막지 않고 **끄기도 막은 까닭**

장군님 말씀은 「켜지는 건 막아라」였지만, **켜기만 막으면 달라지는 것이 없다.**
화면 안 다른 처리는 켜기와 끄기를 **짝으로** 부른다 — 켜기가 막혀도 그 짝인 **끄기가 와서
AI busy 를 꺼 버린다.** 그러면 「AI 제어 중에는 유지한다」는 목적이 전혀 달성되지 않는다.
그래서 끄기도 막았다. **아니라면 되돌린다.**

막을 때도 부르는 쪽이 넘긴 뒷정리(`fnDone`)는 해 준다 — 그쪽은 자기 작업이 끝난 뒤
토스트 등을 띄워야 한다. busy 를 언제 끌지는 AI 쪽이 책임진다.

## 또 밟을 함정

  넣으려면 `chr(92) + "n"` 으로 조합한다. heredoc 을 `<<'EOF'` 로 따옴표 쳐도 **bash 만** 막아 줄 뿐,

- 확인용 사본은 **실제 파일에서 생성**한다. 손으로 붙여 넣으면 실제와 조용히 어긋난다.

## 추가 2026-10-30 (3) — setAIBusy(false) 는 기다리지 않고 바로 끈다

장군님 질문 「setAIBusy(false)를 할때 왜 한참 있다가 busy가 꺼지는 이유가 뭐야?」 → 지시 「1 그렇게 해라」.

### 왜 느렸나 (소스 + 실측)

`setAIBusy(false)` 가 보통 busy 끄기(`_hideCore`)를 그대로 탔다. 그 규칙은:

1. `QUIET_WINDOW_MS`(150ms) 기다림
2. 그 사이 busy 창 **밖**에 DOM mutation 이 하나라도 있었으면 **창을 다시 센다** — 있을 때마다 계속
3. 조용해지면 `requestIdleCallback`
4. 거기서 **또 150ms** → 닫음

빈 화면 실측 **333ms**(= 150 × 2 + idle). 화면이 계속 바뀌면 끝없이 늘어나고,
`SLOW_WARN_MS`(5초)를 넘어도 **끄지 않고 계속 기다린다**(장군님 2026-10-22 결정).

**AI busy 에는 맞지 않는다.** 그 기다림은 「미리보기가 다 그려졌나」를 보는 것인데,
AI busy 는 AI 가 「내 일 끝났다」고 직접 끄는 것이다. 게다가 AI 가 화면을 바꾸는 중이면 2번에 계속 걸린다.

### 고친 것 — `theme/u4a-busy.js` 두 자리

| 자리 | 무엇 |
|---|---|
| `_hideCore(fnDone)` → `_hideCore(fnDone, bNow)` | 두 번째 인자를 받는다 |
| `_hideCore` 안, MutationObserver 분기 **바로 앞** | `bNow === true` 면 `_doHide()` 로 바로 끈다 |
| `setAIBusy` 의 off 분기 | `_hideCore(fn, true)` 로 부른다 |

**`U4ABusy.hide()` 는 한 줄도 안 바뀌었다** — 인자를 안 넘기므로 `bNow` 는 `undefined` 이고 종전 길로 간다.

### 영향도

- `setAIBusy` 를 부르는 곳 = `www` 전체에서 **0건**(새로 만든 것이라 아직 아무도 안 쓴다).
- `_hideCore` 를 부르는 곳 = `hide()` 래퍼 · `setAIBusy` **두 곳뿐**.

### 실측 (확인 페이지, 각 3회)

| | 고치기 전 | 고친 뒤 |
|---|---:|---:|
| `setAIBusy(false)` | 333ms | **0ms** |
| `U4ABusy.hide()` (보통 busy) | 333ms | **333ms** (그대로) |

실제 마우스·키로도 확인 — 키 `4` 를 누른 **직후** `open=false` · mode 해제 · 글자 비움 · 단추 다시 눌림.
AI busy 중 키 `1` 자물쇠도 그대로 작동.

## 또 밟을 함정

- **보통 busy 의 기다림을 없애지 말 것.** 그것은 미리보기가 다 그려지기를 기다리는 장치다
  (장군님 2026-10-20 · 10-22 결정). 이번에 바꾼 것은 **AI 가 직접 끄는 길 하나뿐**이다.

### 왜 모자랐나

자물쇠를 `U4ABusy.show` / `hide` 에만 걸었는데, 화면 코드가 실제로 부르는 것은 **그 바깥의 전역
`setBusy`**(`resources/index.js`)다. 거기서 공통 busy 를 부르기 **전후로** 부수 작업을 한다:

| 부르면 | AI busy 가 어떻게 깨지나 |
|---|---|
| `setBusy("X")` | `setBusyDialog` → 더미 busy 의 `setTitle("")` · `setText("")` 가 `#u4aWsBusyTitle` · `#u4aWsBusyText` 를 **직접 비운다** → AI 의 글이 지워진다 |
| `setBusy("")` | 공통 busy 끄기는 막혀도 **뒷정리 콜백이 그대로 실행**된다 → `document.body.style.pointerEvents = ""` · `setMainCloseBtnDisabled("")` · 포커스 복원 → **창은 떠 있는데 조작이 열린다** |

### 고친 것 — 두 파일

| 파일 | 무엇 |
|---|---|
| `theme/u4a-busy.js` | `isAILocked()` 를 내놓는다(`U4ABusy.isAILocked`). `bAILocked === true` 만 돌려준다 |
| `resources/index.js` | `isAIBusyLocked()` helper 추가 + 전역 `setBusy` 맨 위에서 잠겨 있으면 `RSRC-017` 로그 한 줄 찍고 `return`. 헤더 다음 번호 016 → 018 |

### 영향도

- `setDomBusy` 를 직접 부르는 자리(Login.js 다수 · `ws10_20/index.js` · `views/vw_main/control.js` ·
  `library-preload.js` · `ws_main.js`)는 **그대로 둔다.** 그 길은 `U4ABusy.show/hide` 로 바로 내려가
  **이미 자물쇠에 걸리고**, 부수 작업을 하지 않는다. 또 로그인 화면은 AI 제어 전 단계라 잠길 일이 없다.
- 잠겨 있지 않으면 `isAIBusyLocked()` 가 false 라 **종전과 한 줄도 다르지 않게 돈다.**
- `U4ABusy` 가 없는 창·옛 판에서도 false — 안전.

### 확인한 것 / 못 한 것

| | |
|---|---|
| ✅ `isAILocked()` 동작 | 처음 false · 보통 busy 켜도 false · AI busy 켜면 true · 끄면 false (확인 페이지 실측) |
| ✅ 문법 | 두 파일 `node --check` 통과 |
| ❌ **앱에서의 실제 차단** | `setBusy` 는 메인 창에서만 돈다. **아직 `setAIBusy` 를 부르는 코드가 0건**이라 앱에서 재현할 길이 없다. ws4 스킬이 쓰기 시작할 때 드러난다 |

## 남은 것

- **별창은 자물쇠가 따로다.** AI 가 메인 창을 잠가도 띄워 둔 별창(바인딩 팝업 등)은 그대로 조작된다.
  막으려면 방송(`broadcast-to-child-window_*`)으로 잠금을 알리는 길을 놔야 한다 — **지시 대기.**

## 또 밟을 함정

- **공통 함수에 자물쇠를 걸 때는 「그 함수를 부르는 바깥 함수가 무엇을 더 하는지」를 먼저 읽는다.**
  여기서는 바깥(`setBusy`)이 마우스 막기 · 포커스 · 창 닫기 버튼 · 카드 글자까지 건드렸다.
  안쪽만 막으면 **반쪽만 막혀 더 위험하다**(창은 떠 있는데 조작이 열린다).
