# 별창이 닫힐 때 **방송 BUSY_OFF 를 안 보낸다** — 다른 창들의 busy 가 영영 안 풀린다

- 날짜: 2026-10-30
- 지시: 장군님 「별창 간에 broadcast busy 동작이 새는거 같은데.. ws20에서 다른 창 여러개 띄우고
  바인딩 팝업을 띄웠는데 바인딩 팝업에서 busy가 켜진 상태에서 창을 닫으면 … **ws20 화면은 busy가
  잘 종료 되는데 다른 창에서는 busy가 안꺼져** … 어디가 또 샌거냐?」
- **코드는 한 줄도 안 고쳤다.** 조사만 했다.

## 결론 — 끄는 신호가 **다른 창에 갈 길이 아예 없다**

창이 닫히면 WS20 쪽 오프너가 이것만 한다 (`js/fnDialogPopupOpener.js:1042~1044`):

```js
oBrowserWindow.on('closed', () => {
    parent.setBusy("", {});      // ← WS20 **자기 창**의 busy 만 끈다
    ...
});
```

| 확인한 것 | 결과 |
|---|---|
| 전역 `setBusy` 가 방송도 하나 | **안 한다** — `resources/index.js` 의 `setBusy` 안에 방송이 0건 |
| 바인딩 팝업이 닫히며 `BUSY_OFF` 를 방송하나 | **안 한다** — `onbeforeunload` 는 채널을 `close()` 만 한다 |
| 바인딩 팝업의 `onWindowClose` 가 하나 | **그 함수는 어디에도 정의돼 있지 않다**(부르기만 한다) |
| 바인딩 팝업이 WS20 에 보내는 `SETBUSYLOCK` 이 방송으로 이어지나 | **안 된다** — `send_action_assist.js` 의 `SETBUSYLOCK` 은 `fnSetBusyLock()` 만 부른다. 방송은 **다른 명령(`BROAD_BUSY`)** 이고, 닫을 때 그건 안 쏜다 |

→ **켤 때는 방송으로 모두 켜 놓고, 끌 때는 WS20 한 창만 끈다.** 장군님 증상과 정확히 일치한다.

## 켠 쪽 — 바인딩 팝업이 방송으로 모두 켠다

`Popups/bindPopup/frame.js` 의 `setBusyWS20Interaction`:

```js
oBroad.postMessage({ PRCCD: "BUSY_ON", TITLE, DESC, TYPE: "DIALOG" });
```

정상 흐름에서는 같은 함수가 `{PRCCD:"BUSY_OFF"}` 를 쏴 풀린다.
**창이 닫히면 그 코드가 아예 안 돈다** — 그래서 켜 둔 채로 끝난다.

## ★같은 모양이 더 있다 — `closed` 핸들러 18곳 중 **방송하는 곳은 1곳뿐**

`js/fnDialogPopupOpener.js` 안의 `oBrowserWindow.on('closed', …)` 를 전부 세었다(주석 제외 **18곳**).

| | 자리 | 닫힐 때 무엇을 하나 |
|---|---|---|
| ✅ | `4555` **쇼컷링크 생성 창** | `oMainBroad.postMessage({PRCCD:"BUSY_OFF"})` + `fnSetBusyLock("")` + `focus()` — **올바른 선례** |
| ❌ | `1042` **바인딩 팝업** | `parent.setBusy("", {})` 만 |
| ? | 나머지 16곳 | **아직 한 줄씩 안 봤다** |

★**「16곳도 같은 결함」이라고 말하면 안 된다.** 방송으로 busy 를 켜지 않는 창은 끌 것도 없다.
고칠 때 **창마다 ① 방송으로 켜나 ② 닫힐 때 끄나** 를 표로 뽑아야 한다.

## 고칠 자리 — 오프너의 `closed` 가 맞다

바인딩 팝업 쪽(`onbeforeunload`)에 넣으면 **안 탄다** — busy 중에는 `return false` 로 먼저 빠진다
(`if (bBusy) { return false; }`). 닫기 버튼도 `if (bBusy) { return; }` 으로 막혀 있다.
오프너의 `closed` 는 **어떻게 닫히든 반드시 탄다.** 처방은 쇼컷링크 생성 창의 두 줄 그대로다.

## 또 밟을 함정

- **`parent.setBusy("")` 는 그 창 하나만 끈다.** 방송으로 켠 것은 **방송으로 꺼야** 한다
  (`BROAD_BUSY` / `oMainBroad.postMessage`). 이름이 비슷해 같은 일을 하는 줄 알기 쉽다.
- **`SETBUSYLOCK` 과 `BROAD_BUSY` 는 다른 명령이다.** 앞의 것은 메인 창 하나, 뒤의 것이 전체 방송이다.
- **창이 닫히는 자리의 뒷정리는 창 자신(`onbeforeunload`)에 두면 안 된다** — busy 중에는 그 핸들러가
  먼저 `return false` 로 빠져나가도록 돼 있어 **아무것도 못 한다.** 오프너의 `closed` 에 둔다.

# 후속 (같은 날) — **원본과 대조해 확정하고 고쳤다**

- 지시: 장군님 「원본은 잘 되던 기능인데 원본도 좀 참고해」 · 「미리보기 쪽 끝나면 … busy 를 진행하자」

## 원본은 **세 가지**를 한다 — WS4.0 은 **하나만** 남아 있었다

원본 `U4A_WS3.0.0/www/ws30/ws10_20/js/fnDialogPopupOpener.js` 의 `lf_releaseBindPopupBusy()`:

```js
oAPP.common.fnSetBusyLock("");                           // ① 메인 창 조작 잠금 해제
parent.setBusy("", {});                                  // ② WS20 자기 창 busy 끄기
oAPP.attr.oMainBroad.postMessage({ PRCCD: "BUSY_OFF" }); // ③ ★떠 있는 다른 창 전부에 방송
```

바인딩 창이 닫히면 원본은 이 함수를 부른다. **WS4.0 에는 ② 한 줄만 남아 있었다** — 그래서
WS20 만 풀리고 다른 창은 켜진 채로 남았다. 장군님 증상과 정확히 일치한다.

## 고친 것 — 원본 1:1 이식

`js/fnDialogPopupOpener.js` 의 바인딩 창 opener 안에 `lf_releaseBindPopupBusy()` 를 **원본과 같은 이름·같은 순서**로
만들고, `closed` 에서 `parent.setBusy("", {})` 대신 이 함수를 부르게 했다.

## ★전수 대조 — 나머지는 **전부 원본과 같다**

원본과 WS4.0 의 `oBrowserWindow.on('closed', …)` 를 **하나씩 짝지어** 방송·잠금해제 유무를 비교했다.

| | 원본 | WS4.0 |
|---|---:|---:|
| `closed` 핸들러 수 | 16 | 17 |
| 끄기 방송(`BUSY_OFF`)을 하는 곳 | 9 | 9 (고치기 전 8) |

- 순서대로 짝지은 16쌍의 방송 유무가 **바인딩 1곳 빼고 전부 일치**했다. 그 1곳을 고쳐 **16쌍 모두 같아졌다.**
- WS4.0 에만 있는 1곳 = **MIME 창**(`fnMimeWindowOpener`). 이 창은 **뜨는 순간**
  `BROAD_BUSY`/`BUSY_OFF` 로 형제창 잠금을 푼다(`mimeRepository/frame.js:532`) —
  켜 둔 채로 두지 않으므로 **닫힐 때 또 끌 필요가 없다. 결함이 아니다.**

### 남은 틈 (보고만, 지시 대기)

MIME 창이 **뜨기 전에** 닫히면(문서 로드 실패 등) 형제창 잠금이 켜진 채 남는다.
짝을 맞추는 코드가 「창이 뜬 뒤」에만 있기 때문이다. 이번 지시 밖이라 손대지 않았다.

## 눌러 볼 것 (busy 라 TODO 에 넣지 않는다 — 2026-10-29 지시)

1. WS20 에서 **다른 별창을 두세 개** 띄운다(기술 문서·소스 패턴 등).
2. **바인딩 팝업**을 띄우고, 그 안에서 처리중 표시가 뜨는 조작을 한다.
3. 바인딩 팝업을 **닫는다**.
4. ★**다른 별창들의 처리중 표시도 같이 풀리면** 통과(전에는 WS20 만 풀렸다).

## 미검증

- **앱으로 돌려 보지 않았다.** `node --check` 통과.

## 또 밟을 함정

- **원본에서 「함수 한 줄 호출」을 「그 함수 안의 한 줄」로 펼쳐 옮기면 나머지가 조용히 사라진다.**
  이번이 그랬다 — 원본은 세 줄짜리 함수를 불렀는데 WS4.0 에는 가운데 한 줄만 남았다.
  **원본이 함수를 부르면 그 함수 본문을 끝까지 보고 옮긴다.**

# 후속 2 (같은 날) — ★내 판정 정정 · **「켜는 곳」 기준으로 전수 다시 봐서 7곳 더 고쳤다**

- 지시: 장군님 「**브라우저 닫기 이벤트** 있잖아 거기서 **신호 보내고 닫으면** 되는거아니야?」

## ★정정 — 「③ 방송이 빠졌다」는 **틀렸다**

해제 함수 `lf_releaseBindPopupBusy()` 는 **이미 있었다**(`fnDialogPopupOpener.js:794`).
원본과 똑같이 ①잠금 해제 ②WS20 끄기 ③**방송**을 다 한다. 재사용 경로에서는 그 함수를 쓰고 있었다.

**진짜 문제는 `closed` 핸들러만 그 함수를 안 부르고 `parent.setBusy("", {})` 한 줄로 끝낸 것**이다.

제가 그 함수의 존재를 확인하지 않고 **같은 함수를 하나 더 만들었다.** 뒤에 선언한 것이 이겨
동작은 같았지만 중복이다 — **지우고 원래 함수를 부르도록 바로잡았다.**
`grep "lf_releaseBindPopupBusy"` 를 먼저 하지 않은 탓이다.

## 장군님 기준으로 전수 다시 — **「켜는 곳」이 있으면 닫을 때 끈다**

앞서는 **「닫을 때 끄나」만** 봤다. 그래서 「원본과 같으니 괜찮다」로 끝냈다.
장군님 기준(켜면 닫을 때 끈다)으로 **opener 마다 짝을 맞춰** 다시 셌다
(스크립트 = `scratchpad/pairscan.py`, 일회용).

| | 고치기 전 | 고친 뒤 |
|---|---:|---:|
| 창을 띄우는 opener 중 `closed` 가 있는 것 | 15 | 15 |
| **켜는데 닫을 때 안 끄는 것** | **7** | **0** |

고친 7곳 — 기술 문서 · 옵션 · 소스 패턴 · 일러스트 메시지 미리보기 ·
런타임 클래스 탐색기 · 글꼴 마법사 · 오류 목록 창.

## 공통으로 뺐다

같은 두 줄을 9곳에 복사하지 않도록 **`lf_releaseChildWindowBusy()`** 를 이 파일의 IIFE 안에 하나 두고,
각 `closed` 는 **그 함수를 부르는 한 줄**만 갖는다(MIME 창도 이것으로 바꿨다).
바인딩 별창만은 **원본에 제 함수가 있으므로** 그것을 그대로 쓴다.

## 눌러 볼 것 (busy 라 TODO 에 넣지 않는다)

1. 별창을 두세 개 띄워 둔다.
2. **바인딩 팝업**을 열고 처리중 표시가 뜨는 조작을 한 뒤 **닫는다** → 다른 창도 같이 풀려야 한다.
3. 위 7개 창도 각각 열었다 닫아 본다 → 다른 창이 잠긴 채 남지 않아야 한다.

## 검증 — **통과** (2026-10-30)

장군님이 눌러 보고 「잘된다」고 알려 주셨다. 별창이 떠 있는 상태에서 바인딩 팝업을 닫으면
**다른 창들의 처리중 표시도 같이 풀린다.** 해제 함수 정의 1개 / 호출 2곳, `node --check` 통과.

## 또 밟을 함정

- **「없다」고 말하기 전에 그 이름으로 grep 한다.** 이번에 해제 함수가 이미 있는데 못 보고 또 만들었다.
  JavaScript 는 같은 스코프에 함수를 두 번 선언해도 **조용히 뒤의 것이 이긴다** — 안 터진다.
- **짝은 「끄는 쪽」이 아니라 「켜는 쪽」에서 세어야 한다.** 「닫을 때 끄나」만 보면
  **애초에 켜 놓고 안 끄는 창**이 안 걸린다. 이번에 7곳이 그렇게 숨어 있었다.
