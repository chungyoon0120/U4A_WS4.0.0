# http 서버에서 로그인 쿠키가 유지되지 않는다 — 진단 로그 넣음

- 일시: 2026-10-27
- 유형: investigate
- 보고: 장군님 「서버에 http only 세팅 되어 있으면 로그인 쿠키가 유지가 안 돼. 일렉트론 버전 올리면서 안 되는 것 같은데」

## 장군님 판단이 맞다 — 일렉트론을 올리면서 생긴 문제다

화면이 `u4a-ws://` 로 뜨면서 **진짜 origin 이 생겼다.** 전에는 `file://` 이라 origin 이 사실상 없어
쿠키가 그냥 실려 갔는데, 이제 SAP 서버와 **다른 site** 가 됐다. Chromium 의 두 규칙이 맞물린다.

1. 다른 site 쿠키가 실리려면 `SameSite=None` 이어야 한다.
2. `SameSite=None` 은 `Secure` 를 요구하고, `Secure` 쿠키는 **https 응답만** 저장된다.

→ **http 응답은 헤더를 어떻게 고쳐도 저장되지 않는다.** 그래서 사본 쪽에서 앱이 쿠키를 직접
들고 다니는 모듈(`electron/lib/net/ws_http_cookie.js`)을 만들었고, 그 파일은 우리 프로젝트에 들어와 있다.

## 소스로 확인한 것 (여기까지는 문제 없음)

| 본 것 | 결과 |
|---|---|
| 모듈이 걸리는 자리 | `electron/main.js:523` 에서 모든 session 에 건다 |
| 같은 자리를 다른 코드가 덮나 | **안 덮는다** — 요청·응답 가로채기 두 자리는 이 모듈 한 곳뿐(전수 확인) |
| 쿠키를 싣는 설정(`withCredentials`) | 로그인 · 서버 목록 · 세션 워커 **전부 있다** |
| `electron/lib/` 파일 | 사본과 10개 모두 같다 |

## 못 본 것 — 그래서 로그를 넣었다

- **그 모듈이 실제로 도는지 확인하지 못했다.** 이 프로젝트의 로그 파일은 오늘 **14:55** 가 마지막이라
  일렉트론 45 로 켠 기록이 없다. 장군님 테스트는 사본 폴더 쪽이었을 것이다.
- 의심 자리 2곳(둘 다 **미확인**):
  1. 응답에서 `Set-Cookie` 를 **볼 수 있는지.** Chromium 은 72부터 `Cookie`·`Set-Cookie` 를
     `extraHeaders` 없이는 리스너에 안 보여 준다. **Electron 공식 문서에는 이 얘기가 한 줄도 없다.**
     이 프로젝트의 다른 자리(응답 헤더를 고치는 쪽)는 `set-cookie` 를 실제로 읽고 있어 거기서는 보이지만,
     **쿠키 모듈이 쓰는 자리는 다른 지점**이라 같다는 보장이 없다.
  2. 요청에 붙인 `Cookie` 헤더가 실제로 나가는지. 같은 제약을 탄다.

## 넣은 진단 로그 4곳 (쿠키 값은 안 남긴다 — 이름·개수만)

장군님이 겪는 차례대로 넣었다.

| 순서 | 어디 | 남기는 것 |
|:--:|---|---|
| ① | `install()` 들머리 | `hooked on a session` — 걸릴 때마다 |
| ② | `installAll()` 의 session 생김 | `new session hooked | total=N` — 창마다 session 이 달라 수가 늘어야 정상 |
| ③ | 응답 받는 자리 | `response seen | host= | status= | headerCount= | setCookieCount=` |
| ④ | 요청 나가는 자리 | `request seen | host= | kept=N` |

처음 5번만 남긴다(로그 양 표준).

### 로그로 무엇이 갈리나

- **아무 줄도 안 나온다** → 모듈이 아예 안 걸렸다.
- `response seen` 은 나오는데 `setCookieCount=0` 이 계속 → **`Set-Cookie` 가 우리 눈에 안 보인다.**
  거두는 자리를 응답 헤더를 고치는 쪽으로 옮겨야 한다(그 자리는 이미 `main.js` 가 쓰고 있어 합쳐야 한다).
- `request seen` 이 안 나온다 → 로그인 창의 session 에 안 걸렸다.
- `attached` 까지 나오는데도 로그인이 안 된다 → 붙인 헤더가 실제로는 안 나간다.

## 로그 보는 곳

`%APPDATA%\com.u4a_ws3.app\logs\U4A_WS_<날짜>.log`
★**터미널에는 안 나온다** — 알림 등급은 콘솔로 보내지 않게 돼 있다(`console.level = 'error'`).
개발 모드라도 **로그 파일 이름은 `.dev` 가 안 붙는다**(사용자 데이터 폴더만 `.dev` 가 붙는다).

## 또 밟을 함정

- **「코드를 넣었다」와 「그 코드가 돈다」는 다르다.** 이 모듈은 사본에서 만들어 놓고 **한 번도 안 돌려 봤다**
  (인수인계 지침서 5장이 그렇게 적고 있다). 돌려 보기 전에는 어느 전제가 깨졌는지 알 수 없다.
- **진단 로그는 「성공했을 때」만 남기면 쓸모가 없다.** 「요청이 오긴 했는데 쿠키가 0개」 같은
  **중간 상태**를 남겨야 어디서 끊겼는지 갈린다. 이 모듈은 원래 성공 자리에만 로그가 있었다.

## ★정정 — 내가 「http only」를 잘못 읽었다 (2026-10-27)

장군님 정정: 「지금 서버 호출을 **https://** 로 했고 **서버 보안 설정이 http only** 일 때야」.

- 나는 「http only」를 **주소의 `http://`** 로 읽고 위 조사를 전부 그 전제로 했다. **틀렸다.**
- 실제로는 **서버가 쿠키에 `HttpOnly` 를 붙이는 설정**이고, 호출 주소는 **https** 다.
- 그래서 `ws_http_cookie.js` 는 `http://*/*` 만 보도록 걸려 있어 **안 불린 것이 정상**이다.
  터미널에 요청·응답 줄이 한 줄도 없던 것이 그 증거다. **그 모듈은 이번 증상과 무관하다.**

### 그럼 어디가 유력한가 — `electron/main.js` 의 응답 쿠키 치환

그 자리는 `SameSite=Strict` · `Lax` 를 `None` 으로 **바꾸기만** 한다. 그래서 두 구멍이 있다.

1. **`SameSite` 속성이 아예 없는 쿠키에는 아무것도 안 한다.** 그러면 Chromium 이 기본 `Lax` 로 보고,
   화면이 `u4a-ws://` 라는 **다른 site** 가 된 지금은 그 쿠키를 **안 실어 보낸다.**
   전에는 `file://` 이라 site 판정 자체가 없어 그냥 실려 갔다 — **일렉트론을 올리며 origin 이 생긴 것이
   그대로 이 자리를 때린다.**
2. **`SameSite=None` 으로 바꾸면서 `Secure` 를 안 붙인다.** `Secure` 없는 `SameSite=None` 은 거부된다.
3. 덤으로 **응답 헤더 키를 소문자 `set-cookie` 로만 찾는다.** 서버가 `Set-Cookie` 로 주면 **한 번도 안 돈다.**

★1·2·3 모두 **코드로는 확인했지만 실제 쿠키가 어떤 모양인지는 아직 못 봤다.**

## 넣은 로그 (2026-10-27, 「1번 진행해」)

`electron/main.js` 의 응답 쿠키 치환 자리에 **처음 10번만** 남긴다. **쿠키 값은 절대 안 남긴다.**

| 남기는 것 | 무엇이 갈리나 |
|---|---|
| `header key as sent = "..."` | 서버가 보낸 **실제 대소문자**. `Set-Cookie` 면 3번이 원인 |
| `name= sameSite= secure= httpOnly= domain= path=` | `sameSite=(none)` 이면 1번, `None` 인데 `secure=N` 이면 2번 |

주소는 물음표 앞까지만 남긴다(로그 표준).

### 또 밟을 함정

- **말의 뜻을 먼저 맞추고 조사를 시작한다.** 「http only」 한 마디를 프로토콜로 읽고 한참을 팠다.
  장군님 말씀에 줄임말이 있으면 **무엇을 가리키는지 먼저 확인**한다.
- **응답 헤더 키는 대소문자가 보장되지 않는다.** `details.responseHeaders['set-cookie']` 처럼
  한 가지 글자로만 찾으면 조용히 안 돈다. **키를 훑어 소문자로 비교**해야 한다.

## 조치 — 쿠키 치환 두 자리를 고쳤다 (장군님 지시 2026-10-27 「고쳐바 빨리」)

일렉트론 45 업그레이드 방에서 같은 원인을 찾아 사본에서 먼저 고쳤고, 그 코드를 우리 쪽에 옮겼다.
★그 방 메시지에는 「원본 WS4.0 은 Electron 14 라 당장 고칠 필요 없다」고 적혀 있었지만,
**우리는 오늘 이미 45 로 올렸으므로 지금 바로 영향을 받는다.** 장군님 확인 — 양쪽 폴더 모두 45.

### 결함 3개 (전부 소스로 확인)

| 번호 | 무엇 | 왜 문제인가 |
|:--:|---|---|
| 1 | `SameSite=None` 으로 바꾸면서 **`Secure` 를 안 붙인다** | `None` 인데 `Secure` 가 없으면 Chromium 이 쿠키를 **통째로 거부**한다 |
| 2 | **`SameSite` 속성이 아예 없으면 `.replace()` 가 아무 일도 안 한다** | 속성 없는 쿠키는 `Lax` 취급 → 다른 site 면 안 실린다 |
| 3 | 응답 헤더 키를 **소문자 `'set-cookie'` 로 박아** 두었다 | 서버가 `Set-Cookie` 로 보내면 **못 찾고 그냥 지나간다** |

### 왜 지금까지 멀쩡했나

`electron/main.js` 의 `disable-features` 에 `SameSiteByDefaultCookies`(2번을 덮어 줌) ·
`CookiesWithoutSameSiteMustBeSecure`(1번을 덮어 줌) 가 있다.
**Chromium 93(Electron 14)에서는 그 스위치가 실제로 동작해 두 규칙을 껐다.**
그 기능이 최신 Chromium 에서 없어져 **스위치는 남아 있지만 아무 일도 하지 않는다.**
45 로 올리자마자 결함이 드러났다.

### 고친 자리 — 두 곳을 **같은 모양으로**

| 파일 | 함수 |
|---|---|
| `electron/main.js` | `toCrossSiteCookie` · `findSetCookieKey` · `logCookieFix` · `configureSession` |
| `www/ServerList_v2/ServerList.js` | 같은 것의 그 파일 안 판(이름 앞에 `_`) |

- 다른 site 표시가 있으면 `None` 으로 바꾸고, **없으면 새로 붙인다**
- 보안 표시가 없으면 **붙인다**
- 헤더 키를 **대소문자 가리지 않고** 찾는다
- **https 응답에만** 손댄다 (http 는 `Secure` 쿠키를 저장할 수 없어 `ws_http_cookie.js` 가 맡는다)
- host 마다 **한 번만** 로그를 남긴다. **쿠키 값은 안 남긴다** — 이름과 개수만

★**공통 함수로 감싸지 않고 두 자리에 같은 모양을 두었다**(장군님 표준 — 감싸면 다음 사람이
틀린 코드를 보고 베낀다). 한쪽만 고치면 어긋나므로 두 파일 주석에 서로를 적어 두었다.

### 같이 한 것

- 내가 앞서 넣은 진단 기록(`COOKIE_SEEN`)은 **뺐다** — 고친 코드에 같은 기능이 이미 있다.
- `ServerList.js` 맨 위 오류코드 다음 번호를 003 → **004** 로 올렸다(003 을 썼다).

### 검증

- `node --check` 두 파일 통과.
- 사본과 줄 단위 비교 — `main.js` **0줄 차이**, `ServerList.js` 는 오류코드 번호 줄 1곳만 달랐고 그것도 맞췄다.
- **아직 눌러 보지 않았다.**

### 아직 남은 것

- **`domain=.com` 문제**(업그레이드 방 전달). 이 SAP 서버가 `MYSAPSSO2` 에 `domain=.com` 을 붙여
  보낸 적이 있는데, `.com` 은 공용 접미사라 **`Secure` 를 붙여도 그 쿠키는 거부된다.**
  같은 증상을 또 만나면 이 자리를 본다.
- `electron/main.js` 의 dev deep link 임시 이름(`u4a-ws-dev-elecup`)은 **아직 그대로다**(지시 대기).

### 또 밟을 함정

- **「지금은 멀쩡하다」가 「코드가 맞다」는 뜻이 아니다.** 이 결함은 Chromium 스위치가 덮어 주고 있었을 뿐이다.
  엔진을 올리면 **덮개가 사라지면서 한꺼번에 드러난다.**
- **같은 코드가 두 파일에 복사돼 있다**(앱 본체 · 서버 목록 화면). 한쪽만 고치면 창마다 동작이 갈린다.
