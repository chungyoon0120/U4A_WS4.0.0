# busy 상태를 전역 변수가 아니라 busy 창 DOM 으로 판단하게 바꿈

- 작성 2026-10-21 · 세션 06836675 · type=fix
- 지시: 장군님 「getBusy도 로직을 바꿔야되는게 내부 전역 변수값을 그냥 리턴해 주고 있는데 … 감지되면
  busy를 끄라고 신호 받아도 안끄고 있는 도중인데 이미 전역 변수에는 꺼져있다고 판단할 꺼 아니야?」
  → 「실제 busy dialog의 dom 상태로 판단해서 X냐 '' 냐를 주는 로직으로 바꿔」
  → 「oWS.utill.attr.isBusy ← 이제 이건 필요없어졋으니까 지워라」
  → 「isBusy ← 이거 보는 자리는 getBusy로 바꾸면 되잖아」

## 1. 무엇이 문제였나 (소스 확정)

2026-10-19 부터 끄라는 신호를 받아도 「화면이 다 그려졌는지」를 기다린 뒤에 끈다.
그런데 상태 전역 변수(`oWS.utill.attr.isBusy`)는 **기다리기 전에 이미 "" 로** 바뀌어 있었다.

| 구간 | 전역 변수 | busy 창 | 어긋남 |
|---|---|---|---|
| 끄기 신호 ~ 첫 기다림 끝 | "X" | 떠 있음 | 없음 |
| 첫 기다림 끝 ~ 두 번째 기다림 끝 | **""** | **아직 떠 있음** | **있음** |

그 구간에 `getBusy()` 가 "" 를 돌려주므로, 이 값으로 막던 것들이 **처리중 표시가 떠 있는데 열렸다** —
메뉴 누르기(`fnHmws.js` 10여 곳) · 팝업 열기(`fnDialogPopupOpener.js`) · AI 쪽 · 바인딩 창.

두 번째 결함도 같이 있었다 — **작업표시줄 진행바 함수(`setProgressBar`)가 그 변수를 직접 덮어썼다.**
진행바만 다루는 함수인데 busy 상태까지 바꿔 실제 화면과 어긋났다.

## 2. 고친 내용 — `www/ws30/resources/index.js` 한 파일

| 자리 | 무엇 |
|---|---|
| 29 | busy 창 id 상수(`BUSY_DOM_ID`)를 **파일 맨 위**로. 쓰는 곳(1197·1763)보다 앞에 둔다 |
| 49 | `oWS.utill.attr.isBusy` 선언 **삭제** |
| 937 | 켜기 중복 방지 — 변수 대신 **`util.fn.getBusy()`** 로 |
| 942 | 상태 기록 **삭제** |
| 1031 | `setBusyDialog` 안 상태 기록 **삭제** |
| 1197 | `getBusy()` 가 **busy 창 DOM** 을 본다 — `<dialog>` 면 `open`, 아니면 `display === "flex"` |
| 2312 | 진행바 함수가 상태를 덮어쓰던 줄 **삭제** |

판정 방식은 로그 쪽(`ws_html5_logger.js` 695~705)이 **이미 쓰던 것과 같다** — 새로 지은 방식이 아니다.

## 3. 틀렸던 판정 (내 반박이 틀렸다)

켜기 중복 방지(937행)를 `getBusy()` 로 바꾸는 것에 대해 내가 이렇게 반박했다:
> 「끄기 기다림 중(창이 떠 있음)에 `setBusy("X")` 가 오면 무시되고, 세대 번호가 안 올라가
>   기다리던 끄기가 새 busy 를 꺼 버린다」

**틀렸다.** 세대 번호(`__u4aBusyGen++`)는 전역 `setBusy` 의 **2036행**에서 올라가고,
중복 방지(937행)는 그 **뒤에** 불리는 `oWS.utill.fn.setBusy` 안이다. 무시돼도 세대 번호는 이미 올랐다.

**왜 틀렸나** — 937행만 보고 「그 앞에서 세대 번호가 언제 오르는지」를 확인하지 않았다.
장군님이 「보는 자리는 getBusy로 바꾸면 되잖아」 하신 뒤에야 2036행을 읽었다.

또 하나 확인한 것: 937행에서 무시될 때 못 하는 일(마우스 막기·포커스 저장·닫기 버튼·진행바)은
**앞서 켤 때 이미 걸려 있고 아직 안 풀린 상태**다. 그래서 무시해도 빠지는 것이 없다.

## 4. 영향 범위 (전수 조사)

- `oWS.utill.attr.isBusy` 를 읽던 곳 = **메인 창 2곳뿐**(937 중복 방지 · 1197 getBusy). 둘 다 처리.
- 나머지 `oAPP.attr.isBusy` 20여 곳은 **각 별창·팝업의 자기 변수**다. 이름만 같고 다른 것 — 손대지 않았다.
- `getBusy()` 를 쓰는 곳(메뉴·팝업·AI·바인딩 창)은 호출 방식이 그대로라 고칠 것이 없다.

## 5. 아직 안 고친 것

- **기다림을 두 번 타는 것(1.2초)은 그대로다.** `setBusy("")` 가 바깥에서 0.6초 기다린 뒤
  더미 busy 객체 `close()` → `setDomBusy("")` → `U4ABusy.hide()` 에서 **또 0.6초** 기다린다.
  장군님 지시는 **공통 busy 하나만 부르는 구조로 모으는 것**이고, 그 작업은 이 커밋 뒤에 한다.
  그때 부수 작업 5가지(상태·마우스·포커스·닫기 버튼·진행바)를 `setBusy` 안으로 옮기고,
  **창이 닫힌 뒤에** 풀도록 공통 busy 가 끝남을 알려 주게 해야 한다.
- **앱에서 확인하지 않았다**(장군님이 직접 돌리신다). 문법 확인만 했다.

## 6. 또 밟을 함정

- **busy 상태를 전역 변수로 들고 있으면 반드시 화면과 어긋난다.** 끄기가 비동기(기다림)인 순간부터
  변수와 DOM 은 따로 간다. 상태는 **DOM 에서 읽는다.**
- **한 가지만 다루는 함수가 남의 상태를 덮어쓰는지 보라.** 진행바 함수가 busy 상태를 바꾸고 있었다.
- **중복 방지를 고칠 때는 「그 앞에서 무엇이 이미 실행됐나」를 먼저 읽어라.** 세대 번호가 앞에서
  오르는 것을 안 보고 「위험하다」고 반박했다.
