# 별창이 뜰 때 busy 선행 + 네이티브 창 투명도 페이드 제거

## 요청

장군님 지시: **"나머지도 작업해"** — 2026-09-11 조사에서 남겨 둔 D1(창이 뜰 때 busy 선행) ·
D3(투명도 페이드 제거) · D4(나눠서 진행)를 실행하라는 뜻. 범위는 내가 권한 ①(WS10/WS20/WS30 별창)로 잡았다.

원 증상(2026-09-11): "브라우저 윈도우 실행시 busy부터 키고 시작해야되는데 그렇지 않은데가 상당 수 있어.
느린 pc에서 실행하면 다크테마일 경우, 검은 화면 부터 나오고 조금 뒤에 busy가 실행되."

## 변경 내용

### A. 창이 화면에 나타나는 순간 busy 가 꺼져 있던 창 6개 — busy 선행으로 고침

`CURRWIN.show()` **앞에서** busy 를 켜도록 했다. 해제 시점은 종전과 동일(본문 렌더 완료 1회).

| 창 | 해제 지점 |
|---|---|
| App. Documentation (`docPopup/frame.js`) | `_finishOpen()` |
| U4A MIME Repository (`mimeRepository/frame.js`) | `if-mime-info` → `fnMimeStart` → `lf_loadTree` 성공/실패 분기 |
| 편집기 CSS/JS/HTML (`editorPopup/editorFrame.js`) | `_finishOpen()`(host ready 또는 워치독) |
| Error Page Editor (`errPageEditorPopup/errorPageEditorFrame.js`) | 위와 동일 |
| Version Management (`versionMng/versionMngFrame.js`) | `_finishOpen()` / `_fatal()` |
| OTR Manager (`OTRF4HelpPopup/frame.js`) | `index.js` 가 `/f4serverData` 응답 후 `setBusyLoading('')` |

**안전장치(20초 상한)를 같이 넣었다.** busy 중에는 `onbeforeunload` 가 창 닫기를 막으므로,
IPC/서버 응답이 끝내 안 오면 창이 닫히지 않는 함정이 생긴다. 상한에 닿으면
`U4ALOG.warn("GUARD_EXIT", …)` 로 무엇을 못 기다렸는지 남기고 busy 를 푼다.
정상 수신 시 `clearTimeout` 으로 해제한다(겹침 방지).
- 새로 넣은 곳: MIME · 편집기 · Error Page Editor · OTR Manager
- 이미 있던 곳: App. Documentation(20초) · Version Management(20초) — 그대로 사용

**손대지 않은 창**: Find · Font Style Wizard · Runtime Class Navigator · USP Pattern · 속성 바인딩 ·
오류 메시지 · Shortcut Creator · Data Monitor(이미 show() 전에 busy 를 켠다) / Monaco Snippet Designer ·
Monaco 테마 디자이너 · 옵션 · Text Search · 속성 기본값 팝업 · UI5 Predefined CSS ·
심볼 미리보기 · 일러스트 메시지 미리보기(내용을 다 만든 뒤에 창을 표시한다).
**전부 소스로 확인했다.**

### B. 네이티브 창 투명도 페이드 제거 (13곳)

`oBrowserOptions.opacity = 0.0` + `WSUTIL.setBrowserOpacity(win)`(0→1 ramp) 방식을 걷어내고,
표준(`.analy/16` §2.6)대로 `show:false` + 준비 후 `show()` 로 통일했다.

- opener 가 표시를 맡던 창 → `did-finish-load` 에서 `oBrowserWindow.show()`
  (심볼 미리보기 · 일러스트 메시지 미리보기 · 오류 메시지 · Release Note · UI5 Predefined CSS 구판 · USP New)
- 페이지가 표시를 맡던 창 → opener 의 `opacity` 줄만 제거(페이지의 `show()` 가 그대로 표시)
  (옵션 · Example Open · Property Help · 속성 기본값 팝업 · 편집기 v2 · Version Management v2 ·
  WebDynpro 변환 기록 · 컨트롤러 실행 오류 · 도움말 말풍선 창 3곳)
- Release Note 는 페이드 **완료 콜백**에서 닫기 버튼을 살리고 있었다 → `show()` 직후 실행하도록 옮김.

### C. 추가로 발견해 고친 것

- **Error Page 미리보기** (`fnErrorPageEditorPopupOpen.js`) — 창을 숨겨서 만들지 않아 사용자 HTML 이
  그려지기 전 빈 창이 먼저 보였다. `show:false` + `did-finish-load` 에서 `show()`.
- **extopen 창 안전장치** — opener 3곳을 `show:false` 로 바꿨으므로, iframe 이 끝내 로드되지 않으면
  창이 영영 안 보인다. 20초 상한 + 로그 + 창 강제 표시를 넣었다(닫을 수 있게).
- **도움말 말풍선 창 3곳** — `opacity:0` 로 만든 뒤 `show()` 와 페이드를 **둘 다** 부르고 있었다.
  페이드 함수는 0 에서 시작하므로 이미 보이는 창이 한 번 투명해졌다 돌아오는 모양이었다. 페이드 제거.

## 변경 이유

2026-09-11 전수조사에서 검은 화면의 원인이 둘로 갈렸다.
- 원인 B(공통 busy 의 0.3초 표시지연) → 2026-09-11 해결

원인 A 의 실제 모양: opener 가 창을 만들고 `did-finish-load` 에서 IPC 로 데이터를 보내는데,

# [후속 2026-09-14] 내가 넣은 타임아웃 폴백 5개 전부 철회 — 규칙 위반 수정

## 무엇을 잘못했나

위 작업(2026-09-13)에서 "busy 가 안 풀려 창을 못 닫는 상황"을 막겠다고 **20초 타임아웃으로
busy 를 강제 해제하는 안전장치 5개**를 넣었다. 이는 명시된 규칙 위반이다.

- `.analy/16_공통_화면UX_표준.md` §2.11 — "**타임아웃 폴백은 쓰지 않는다**(실제 이벤트로만)"
- 메모리 `no-timeout-busy-fallback` — 이유까지 적혀 있다:
  > 오류는 회피할 대상이 아니라 해결할 대상. busy 가 안 꺼지면 "뭔가 고장났다"는 신호가 되어
  > 버그를 바로 인지할 수 있는데, 타임아웃으로 busy 만 꺼버리면 화면엔 아무 변화가 없는데
  > busy 만 꺼져서 사용자가 "끝난 줄" 착각하게 됨 — 안 꺼지는 busy 보다 훨씬 더 나쁜 상태.
  > **타임아웃 폴백이 필요하다고 느껴지는 지점은 대개 "실제 실패 이벤트가 안 걸려있다"는 신호다.**

마지막 문장이 정확히 내 경우였다. 아래에서 확인했듯 진짜 원인은 **실패 이벤트가 안 걸려 있던 것**이었다.
