# 로그 - 영어 전환 · 군더더기 제거 · 크래시 보고서 개선

## 요청

장군님, 한 대화에서 순서대로:

1. `crashReporter` 가 잘 도는지 시험할 방법 / 화면이 뻗는 것도 잡히나
2. 개발 실행에서 `process.crash()` 했는데 아무것도 안 남는다 — 왜
3. **텔레그램 전송이 안 된다** — 언제 보내나
4. 덤프 파일을 어떻게 봐야 하나 → **"AI가 보고 판단할 수만 있으면 형태는 상관없다"**
5. **"항상 느린 PC도 고려해"**
6. 크래시 보고서가 AI가 이해할 수준인지 **보수적으로 검토**
7. **"내용을 영어로 작성하게 바꿔줘"** → 이어서 **"로그도 영어로 바꿔"**
8. **"용어를 전문용어 쓰던지 한글 번역이 이상해. 오류 표면화 설치 실패가 무슨 말이냐. 번역하지 마"**
9. **"`[HTML5]` 이딴거 필요없다. 불필요한 정보 다 제거해. 로그도 PC 용량이다. AI가 신속하게 원인 파악할 수준이면 된다"**

## 변경 내용

### A. 크래시 보고서 — 창이 죽어도 잡히게 (결함 2건 수정)

**결함 ①: 창만 죽으면 보고서도 텔레그램도 안 갔다**
- 근거(실측 로그 15:05): `창이 죽음 / 사유 crashed` 는 남았는데 보고서 파일이 0개
- 원인: 앱 본체가 통째로 죽었을 때만 처리했다. 창만 죽으면 앱 본체는 살아 있어 "돌고 있음" 표시가 정상 종료 때 지워지고, 다음 실행에서 "정상 종료"로 판정
- 수정: ① 창이 죽는 순간 그 자리에서 보고서 생성·전송 ② 다시 켤 때 표시가 없어도 **처리 안 한 dump 가 있으면** 보고서 생성

**결함 ②: 「마지막 조작」이 틀린 값**
- 근거: 보고서는 `청윤`(15:04:56)을 가리키는데 로그에는 그 뒤 `테스트`(15:04:57.899)·`개발툴`(15:04:58.881)이 있었다. 크래시는 15:05:04 — **개발툴 누른 지 5.5초 뒤**
- 원인: `ws_error_hook.js` 의 중복 방지 조건(`if (typeof window.U4ALOG !== 'undefined') return;`) 때문에, **화면 쪽 로그 함수가 있는 화면은 앱 본체에 조작을 안 알렸다**
- 수정: `U4ALOG.action()` 이 `u4a-log:last-action` 으로 앱 본체에 직접 알림. 보고서에 window·traceId·Recorded 시각 추가 + "Recorded 와 크래시 시각에 틈이 있으면 log tail 을 믿어라" 안내

### B. 덤프를 우리가 직접 읽어 글로 푼다 (신규)

`electron/lib/log/ws_crash_dump_read.js` **신규**. WinDbg·Visual Studio 없이 minidump 를 파싱.
- 얻는 것: EXCEPTION 코드+이름 / FAULTING MODULE(파일+버전) / read·write·execute / target addr / instruction pointer / threads / crashpad annotations(`process_type=renderer|browser`) / **third-party injected modules**(백신·GPU 도구 판별) / loaded modules
- 못 얻는 것: 우리 JS 의 함수 이름·줄 번호 (덤프에 애초에 없음)
- 실제 파일로 검증: `0xC0000005 ACCESS_VIOLATION / U4A Workspace.exe + 0x323a70 (v3.6.4.0) / write / target 0x0`
- ★crashpad annotation 한 칸 크기는 **12바이트**(문서 아닌 실측). 16으로 읽으면 깨진다

### C. 느린 PC 대응

| 무엇이 문제 | 어떻게 |
|---|---|
| 「3초 뒤에 dump 를 읽는다」로 못 박음 → 8초 걸리는 PC 에서 **반쪽짜리 파일**을 읽음 | 1초마다 보다가 **파일 크기가 안 늘면** 읽음. 상한 60초, 상한에 닿으면 WARN 로그 남기고 dump 없이 보고서 생성 |
| dump 를 `readFileSync` 로 통째 읽음 (수십 MB 가능, 앱 시작 경로에서도 돎) | **필요한 토막만** 읽는 reader(8KB chunk + cache), 상한 2MB. 실측 977KB 중 24KB 만 읽음 |

3가지 경우 실측: 빠른 PC 3.1초 / 느린 PC(8초에 걸쳐 기록) 10.1초 **내용 온전** / dump 없음 60초 뒤 생성 + 이유 로그

## 변경 이유

이 프로그램은 **AI 가 로그만 보고 운영·수정**한다. 그런데
① 창이 죽으면 보고서가 아예 안 만들어졌고 ② 만들어져도 「마지막 조작」이 **틀린 값**이라 AI 가 엉뚱한 버튼을 뒤졌고 ③ 용어가 지어낸 한글이라 소스에서 못 찾았고 ④ 군더더기가 고객사 PC 용량을 먹었다.

## 영향 범위

- **로그 글자만 바뀐다. 로직·흐름·UX 는 안 건드렸다.**
- `[HTML5]` 제거는 **주석은 그대로 두고 console/U4ALOG 호출 안의 것만** 제거(확인: `fnDialogPopupOpener.js` 주석 20곳 잔존, 로그 0곳)

- `_shapeOf()` 반환 모양이 바뀜(`fields: 28` / `lists: T_ATTR=0` / `EMPTY: …`)
- **남의 라이브러리 0곳**

### 실패·헛다리 기록 (다음 agent 참고)

- 처음에 dump 대기를 **「3초 뒤」로 못 박았다** → 느린 PC 에서 반쪽 파일을 읽는다. 시간을 못 박지 말고 **완료를 확인**해야 한다

- shell heredoc 안에서 `\uXXXX` 이스케이프가 파이썬 소스로 잘못 들어가 여러 번 실패했다. **Write 도구로 .py 파일을 만든 뒤 실행**하는 것이 확실하다

### ★스캐너 버그부터 (중요 — 다음 agent 주의)

처음 만든 스캐너의 문자열 정규식에 escape 가 하나 더 붙어
**`n` 이 든 문자열을 통째로 건너뛰었다**(`info` / `content` / `render` …).
그래서 "854곳" "324곳" 같은 앞 숫자는 **전부 적게 나온 값**이다.
제대로 고친 뒤 실제 대상은 **327곳**(70곳은 일부러 남기는 키)이었다.

```
잘못: r"\"([^\"\\n]*)\""      → 문자 클래스가 n 을 제외해 버림
맞게: '"((?:[^"\\\n]|\\.)*)"'
```

### ★두 번째 사고 — 낱말 치환이 낱말 **안쪽**을 깨뜨림

1·2차를 **낱말 사전 치환**(`트리`→`tree`, 조사 `이/가/을/를` 제거)으로 돌렸더니
낱말 한가운데가 잘려 나갔다.

| 깨진 것 | 원래 |
|---|---|
| `레지스tree` | 레지스트리 |
| `브load캐스트` | 브로드캐스트 |
| `업load` | 업로드 |
| `레아웃` `페지` `운데` `뒤로기` `잇 길` | 레이아웃 / 페이지 / 가운데 / 뒤로가기 / 잇는 길 |

→ 16곳을 손으로 바로잡고, **3차부터는 문자열을 통째로 교체**하는 방식으로 바꿨다.
**교훈: 로그 문구 변환에 낱말 단위 치환을 쓰지 말 것. 문자열 전체 매핑만.**
