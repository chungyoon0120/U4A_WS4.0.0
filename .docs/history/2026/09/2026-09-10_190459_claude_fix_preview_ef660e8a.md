## 요청

장군님 지적 — WS10 에서 편집(Change)/조회(Display) 로 WS20 진입할 때, 콘솔 로그를 보면
**진입 도중 busy 가 껐다 켜졌다 한다.** 진입 시작하자마자 busy 를 켜고, 서버를 몇 번 왕복하든
**전체가 끝나고 화면이 다 그려진 뒤 맨 마지막에 딱 한 번만** 꺼야 한다.
중간에 오류가 나면 그때만 busy 를 끄고 오류 후속처리를 한다.

장군님이 콘솔 화면을 캡처해 **꺼졌다 다시 켜지는 구간**을 직접 지목함
(미리보기 iframe 로드 직후 `setBusy ""` 2회 → 이어서 `setBusy "X"` 로 다시 켜짐).

## 변경 내용

`www/ws30/ws10_20/design/preview/index.js` 의 `sap.ui.getCore().attachThemeChanged(...)` 핸들러에
**미리보기 부팅 중이면 busy 를 끄지 않고 그대로 빠져나가는** 가드 추가.

```js
try {
    if (parent.oAPP && parent.oAPP.attr && parent.oAPP.attr.__ws20PrevBooting === true) {
        return;
    }
} catch (e) { /* 부모 접근 실패시엔 원본 동작 그대로 진행 */ }
```

부팅 중이 아닐 때(사용자가 테마를 바꾸는 등 평소 동작)는 **원본 그대로** 둔다.

## 변경 이유

### 원본(as-is) 대조 결과 — 이게 판단의 근거

원본 `U4A_WS_DESIGN/design/js/main.js`:
- `getAppData`(421행): 시작에서 `designAreaLockUnlock(true)` 로 잠금(425행).
  **서버 성공 시 busy 를 끄는 줄이 주석 처리돼 있다** — `//parent.setBusy("");` (602행).
  오류 때만 해제(615행).
- `getLibData`(625행)도 성공 시 안 끔(오류 738행만).
- `setUIAreaEditable`(748행)의 4.2/4.3 경로도 안 끔.
- 원본이 busy 를 푸는 곳 = **미리보기 테마 적용 시 1회**
  (`U4A_WS_DESIGN/design/preview/index.js:5852` `attachThemeChanged` → `setBusy("")`)
  + ROOT 자동선택(5968행 `fireCellClick` → 선택 함수의 잠금/해제).

**즉 원본 = 진입에서 한 번 잠그고 → 서버를 몇 번 왕복하든 안 풀고 → 미리보기 테마 적용 때 푼다.**

### 무엇이 원본과 달랐나

원본은 테마 적용 시 `setBusy("")` 로 대기표시가 사라져도 **UI5 화면잠금(`oAPP.attr.oCore.lock()`)이
살아 있어서 사용자 조작이 계속 막혀 있었다.**

HTML5 이식본은 그 화면잠금이 **아무 일도 안 하는 껍데기**다
(`www/ws30/ws10_20/js/ws_html5_shell.js:57` — `lock: _noop`, `unlock: _noop`, `isLocked: () => false`).
그래서 테마 적용 시 busy 를 끄면 **실제로 조작이 열려 버린다** → 원본에 없던 구멍.
그 직후 ROOT 자동선택이 busy 를 다시 켜기 때문에 로그상 "껐다 다시 켜짐" 으로 보인다.

「기능이 같으면 성공」 기준으로, 그 구간에 busy 를 유지해야 원본과 동등해진다.

## 영향 범위

- WS10→WS20 진입 시 미리보기 부팅 중에는 테마 적용으로 busy 가 꺼지지 않는다.
  최종 해제는 ROOT 자동선택이 끝나는 지점 1회 → **원본과 동일한 시점**.
- 부팅이 아닐 때의 테마 변경 동작은 **변경 없음**(원본 그대로).
- 부모 창 접근이 실패하면 가드를 건너뛰고 원본 동작대로 진행한다(안전 쪽).

## 참고 사항

### 내가 처음에 잘못 판단했던 것 (다음 agent 는 반복하지 말 것)

처음에는 **변환된 HTML5 코드만 보고** 원인을 짚었고, 계획서에
「테마 적용 시 끄기(T1)·ROOT 선택의 껐다 켜기(T2)를 둘 다 억제하자」 고 적었다.
**이건 잘못이었다** — T1·T2 는 **원본에도 똑같이 있는 동작**이라 건드리면 원본을 임의로 바꾸는 것이 된다.
장군님 지적으로 원본을 확인한 뒤 그 방안을 철회하고, 원본에 없는 구멍(껍데기 화면잠금) 때문에
생기는 차이만 메우는 쪽으로 바꿨다.

**교훈: 변환 작업의 원인 분석은 반드시 원본부터 본다.** 변환본만 보면 "원본에도 있는 것" 까지
버그로 오인해 임의 개조를 하게 된다.

### 아직 남은 것

- **원본에 없는데 변환본이 추가한 busy off 가 하나 더 있다** —
  `www/ws30/ws10_20/js/ws_html5_ws20_data.js:388~390` 의
  `finally { if (!oAPP.attr.__ws20PrevBooting) { fnSetBusyLock(""); } }`.
  원본 `main.js:602` 는 주석 처리라 성공 시 끄지 않는다. **이 줄은 원본에 없는 추가분이다.**
  라이브러리 정보가 그 시점에 준비 안 된 경우에만 걸리며(정상 순서에선 안 걸림), 이번 로그에는 안 나왔다.
  → 다음 기회에 제거 검토(계획서 B-0 참조).
- 변환본이 추가한 `__ws20PrevBooting` · `_ws20EngagePrevBusy` / `_ws20ReleasePrevBusy` ·
  "60초 안전장치" 주석(실제 타이머 코드는 없음)도 **원본에 없는 것**이다.
  원본은 이런 장치 없이 테마 적용 한 곳에서만 푼다. 단순화 검토 대상이나, 그 안의 미리보기 정리
  (스탠드인 제거·완료 콜백 등 **busy 와 무관한** 로직)는 남겨야 한다.
