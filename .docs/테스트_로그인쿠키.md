# U4A WS4.0 — 로그인 쿠키 유지 테스트

> 2026-10-29 · U4A Workspace 4.0 (Electron 45 / Chromium 156) · 결과는 3장 각 케이스에 기록
>
> **보고용 웹 문서** → https://claude.ai/artifact/WawYWvjEj8FGwXWmZzy37i (비공개 — 공유해야 열람 가능)

**검증 대상** — WS4.0 이 `Set-Cookie` 응답 헤더에 적용하는 보정 두 가지.

| | 동작 |
|---|---|
| ① | `SameSite` 가 **있으면 `None` 으로 치환**, **없으면 추가** |
| ② | `Secure` 가 **없으면 추가** |

`http://` 는 Chromium 이 `Secure` 쿠키를 저장하지 못하므로, 앱이 쿠키를 **직접 보관했다가 요청에
재첨부하는 모듈**이 대신 처리. 보정·모듈 모두 **코드 작업만 끝났고 실환경 미검증.**

---

## 1. RZ11 파라미터

| 파라미터 | 값 | 동작 | 영향받는 쿠키 속성 | 케이스 |
|---|---|---|---|:---:|
| `icm/HTTP/samesite` | 미확인 (주1) | ICM·Web Dispatcher 가 응답 쿠키에 `SameSite` 를 설정할지와 그 값. ABAP Platform 2020 부터, **기본 설정됨** | `SameSite` | CK4 · CK9 |
| `login/ticket_only_by_https` | 0 / 1 | 1 = 로그온 티켓을 HTTPS 에서만 송수신(`Secure` 설정). SAP 권장 1 | `Secure` | CK4~CK8 |
| `login/ticket_only_to_host` | 0 / 1 | 0(기본) = 도메인 내 모든 서버로 티켓 전송 · 1 = 발급 서버로만 | `domain=` 범위 | CK10 |

**세 파라미터 모두 dynamic** — RZ11 변경 시 즉시 적용, **instance restart 불필요**(2026-10-29 확인).

**(주1)** `icm/HTTP/samesite` 의 **값 형식과 미설정 방법은 미확인.** RZ11 파라미터 설명으로 확인 필요.
근거 = **SAP Note 2893546** (SameSite support in SAP Web Dispatcher and ICM).

**CK11 은 RZ11 이 아니라 SICF_SESSIONS** 에서 HTTP security session 을 비활성화한다.
비활성화 시 세션 쿠키 대신 SSO 티켓만 발급되어 **쿠키 종류가 달라진다.**

## 2. 공통 절차

### 2-1. 원복용 값 기록

| 파라미터 | 테스트 전 값 |
|---|---|
| `icm/HTTP/samesite` | |
| `login/ticket_only_by_https` | |
| `login/ticket_only_to_host` | |

UHA 는 위 세 개가 **RZ10 profile 미등록**(2026-10-29, ADT 로 `TPFET` 조회).
테스트 후 **추가한 값을 삭제**하면 원복된다.

### 2-2. 케이스 공통 조작

① **WS4.0 앱 종료**
② RZ11 에서 해당 케이스의 값으로 변경 → **재조회로 반영 확인**
③ **WS4.0 앱 실행** ★ 케이스마다 필수 — 사유는 2-3
④ 서버 목록에서 해당 케이스의 **접속 URL** 로 등록된 서버 선택
⑤ ID·비밀번호 입력 후 로그인
⑥ **로그인 성공 여부** 확인
⑦ 로그인 후 **앱 하나 열기** ← 서버 **재호출** 확인 단계. 여기서 끊기는 경우가 있음

### 2-3. 로그 확인 — 두 곳

| 위치 | 담당 |
|---|---|
| 앱 실행 **터미널** | 서버 목록 화면 |
| **메인 창** DevTools → **Console** | 로그인 이후 모든 창 |

양쪽에서 **`COOKIE_FIX`** 포함 줄 확인. **쿠키 값은 기록되지 않음.**

```
COOKIE_FIX | host=uha.u4aide.com | count=2 | names=MYSAPSSO2,SAP_SESSIONID_UHA_800 | sameSiteMissing=2 | secureMissing=2
```

| 항목 | 의미 |
|---|---|
| `count` | 서버가 내려준 쿠키 수 |
| `names` | 쿠키 이름 (값 아님) |
| `sameSiteMissing` | `SameSite` 가 **없던** 수 = **WS4.0 이 추가한** 수 |
| `secureMissing` | `Secure` 가 **없던** 수 = **WS4.0 이 추가한** 수 |

> **★ host 당 1회만 기록**(로그량 제어). 동일 서버로 재로그인하면 기록되지 않으므로
> **케이스마다 앱을 재실행**해야 한다(2-2 ①③).

### 2-4. 판정

| 관찰 | 판정 |
|---|---|
| 로그인 성공 + ⑦ 성공 + `COOKIE_FIX` 줄 존재 | **통과** |
| 로그인 성공, ⑦ 에서 끊김(로그인 화면 복귀 · 빈 화면 · 통신 오류) | **실패** — 두 번째 요청부터 쿠키 미첨부 |
| 로그인 실패 | **실패** — 쿠키 미저장 |
| `COOKIE_FIX` 줄 없음 | 보정 코드가 해당 session 에 미적용, 또는 앱 미재실행 |
| `sameSiteMissing=0` · `secureMissing=0` 인데 실패 | 서버가 두 속성을 모두 설정한 상태의 실패 → **다른 원인** |

실패 시 **케이스 번호 · 중단 지점 · `COOKIE_FIX` 줄(양쪽) · 화면 오류 원문**을 전달한다.

### CK4 — 서버가 `SameSite=Strict` 설정, `Secure` 미설정 ★최우선

- **목적** 보정 **두 갈래가 동시에** 걸리는 케이스. `Strict`→`None` **치환**과 `Secure` **추가**가 모두 동작해야 함.
- **설정** `icm/HTTP/samesite` = `Strict` · `login/ticket_only_by_https` = `0` · `https://` · 인증서 정상
- **기대** 로그인·앱 열기 성공. 로그는 `sameSiteMissing=0`(서버가 설정) · `secureMissing > 0`(WS4.0 이 추가)
- **실패 시** `Strict`→`None` 치환이 동작하지 않음
- **결과** ☐

### CK9 — 서버가 `SameSite` 미설정

- **목적** 속성이 **없을 때 추가하는** 갈래 확인(치환이 아닌 추가).
- **설정** `icm/HTTP/samesite` = **미설정** · `login/ticket_only_by_https` = `0` · `https://` · 인증서 정상
- **기대** 로그인·앱 열기 성공. 로그는 `sameSiteMissing > 0` · `secureMissing > 0` (둘 다 WS4.0 이 추가)
- **실패 시** 속성 추가 처리가 동작하지 않음
- **결과** ☐

### CK5 — 서버 인증서 오류 + `Secure` 설정

- **목적** ① 인증서 오류를 무시하는 설정이 **현재 Chromium 에서 유효한지** ② 그 연결에 **`Secure` 쿠키가 저장되는지**.
  **둘 다 미확인.**
- **설정** `icm/HTTP/samesite` = `Strict` · `login/ticket_only_by_https` = `1` ·
  `https://` · 인증서는 **self-signed / expired / CN mismatch** 중 하나
- **기대** 로그인·앱 열기 성공
- **참고** WS4.0 은 `ignore-certificate-errors` 로 인증서 오류를 무시하도록 설정돼 있음
  ([main.js:106·124](C:/Users/socce/Documents/Github/CHUNGYOON0120/U4A_WS4.0.0/electron/main.js:106) — **동일 설정 중복**).
  단, 이번 쿠키 문제 자체가 「switch 는 남았으나 기능이 제거된」 사례였으므로 **이 설정도 검증 필요.**
- **결과** ☐

### CK7 — `http://` + 속성 미설정

- **목적** **`http://` 경로 최초 검증.** Chromium 이 `http://` 응답에 `Secure` 쿠키를 저장할 수 없으므로,
  **앱이 쿠키를 직접 보관·재첨부하는 모듈**이 대신 동작함.
- **설정** `icm/HTTP/samesite` = **미설정** · `login/ticket_only_by_https` = `0` · `http://`
- **기대** 로그인·앱 열기 성공
- **결과** ☐

### CK8 — `http://` + `Secure`·`Strict` 모두 설정

- **목적** 최악 조합. 서버는 `Secure` 를 설정하나 `http://` 라 Chromium 은 저장 불가.
  **앱이 직접 보관하는 방식이므로 그래도 동작해야 함.**
- **설정** `icm/HTTP/samesite` = `Strict` · `login/ticket_only_by_https` = `1` · `http://`
- **기대** 로그인·앱 열기 성공
- **결과** ☐

---

### CK10 — 넓은 `domain=` 설정

- **목적** `login/ticket_only_to_host` = `0`(기본)이면 티켓이 도메인 전체 대상으로 발급되어 쿠키에
  **넓은 `domain=`** 이 설정됨. host 명이 `xxx.com` 처럼 **2단계**면 `domain=.com` 이 되고,
  `.com` 은 **public suffix** 이므로 **Chromium 이 쿠키를 거부.** **과거 실제 발생 사례.**
- **설정** `login/ticket_only_to_host` = `0` · `https://` · 인증서 정상
- **기대** UHA 는 host 명이 `uha.u4aide.com` → `domain=.u4aide.com` 이라 **재현되지 않음.**
  **2단계 host 명 서버에서만 재현.**
- **대응** 발생 시 `login/ticket_only_to_host` = `1` 로 해소
- **결과** ☐

---

### CK11 — HTTP security session 비활성화

- **목적** 비활성화 시 세션 쿠키 대신 **SSO 티켓만** 발급되어 **쿠키 종류가 달라짐.** 양쪽 모두 처리되는지 확인.
- **설정** **SICF_SESSIONS** 에서 비활성화(RZ11 아님) · `https://` · 인증서 정상
- **기대** 로그인·앱 열기 성공
- **결과** ☐
