## 1. 요청과 목표

`oAPP.fn.getServerEventList`는 컨트롤러 클래스의 서버 이벤트 목록을 조회한다. 현재는 조회 함수 안에서 화면 선택용 공백 행을 추가하므로, 호출처가 서버 이벤트 존재 여부나 건수를 판단할 때 공백 행을 제외해야 한다.

사용자가 원하는 책임 분리는 다음과 같다.

- 조회 함수: 서버에서 조회한 실제 이벤트만 전달한다.
- 선택 UI 호출처: 값 해제를 위한 공백 선택지가 필요하면 화면용 배열에 추가한다.
- 검색·존재 여부·건수 판단: 실제 이벤트 배열을 그대로 사용한다.

이 인계서는 이후 AI가 구현할 수 있도록 작성한 것이다. 현재 사용자의 요청은 문서 작성까지이며, 이 문서 자체를 지금 소스 수정 지시로 해석하지 않는다.

## 2. 작업 범위와 용어

여기서 서버 항목은 로그인 화면의 접속 서버 목록이 아니라, `CLSID`에 해당하는 **서버 이벤트 메소드 목록**이다.

기존 항목 구조는 유지한다.

```js
// 서버 응답
{ EVTNM: "EV_SEARCH", DESC: "Search" }

// 호출처에 전달하는 항목
{ KEY: "EV_SEARCH", TEXT: "EV_SEARCH", DESC: "Search" }
```

서버 응답의 `EVTLT`를 그대로 반환하도록 구조를 바꾸는 작업이 아니다. `KEY`, `TEXT`, `DESC` 매핑과 서버 항목 순서는 유지하고, 조회 함수가 인위적으로 넣던 다음 행만 제거한다.

```js
{ KEY: "", TEXT: "", DESC: "" }
```

서버가 직접 내려준 비정상 항목의 필터링, 중복 제거, 정렬 변경은 이번 요청에 포함되지 않는다. 필요하면 별도 근거와 요구사항을 확인한다.

## 6. 조회 함수의 정상 반환 계약

구현 시 두 서버 조회 함수 모두 정상 성공에 대해 다음 계약을 맞춘다.

```js
// 조회 성공, 이벤트 있음
[{ KEY: "EV_SEARCH", TEXT: "EV_SEARCH", DESC: "Search" }]

// 조회 성공, 이벤트 없음
[]
```

- 내부 목록 초기값은 `[]`로 한다.
- 실제 이벤트의 기존 매핑은 유지한다.
- callback이 있으면 실제 이벤트 배열을 전달한다.
- Promise도 성공 시 실제 이벤트 배열로 완료한다.
- `bSkipUnLock`는 화면 잠금 해제 책임을 조절하는 인자다. 성공 Promise 완료 여부를 조절하는 용도로 사용하지 않는다.
- callback과 Promise 완료 시점, 잠금 해제 순서의 기존 의존성을 불필요하게 바꾸지 않는다.

### 기존 Promise 차이에 대한 주의

디자인 영역 구현은 성공 시 `resolve()`만 호출한다. callback이 없고 `bSkipUnLock === true`이면 `resolve()` 자체를 호출하지 않는 경로도 있다. 따라서 공백 행 초기화 한 줄만 바꾸면 HTML5 호출처가 기대하는 Promise 계약과 차이가 남는다.

향후 두 구현을 같은 계약으로 보완한다면, 성공 경로에서 callback 유무와 관계없이 배열로 Promise를 완료하도록 함께 검토한다. 이는 기존 차이에 대한 보완이며, 이미 구현되었다고 가정하지 않는다.

## 8. 실패 처리와 비동기 흐름의 경계

정상 0건과 조회 실패는 의미가 다르다. 이번 문서에서 새로운 실패 API를 확정하지 않는다.

현재 구현은 다음과 같다.

- 두 조회 구현 모두 `RETCD !== "S"` 또는 통신 오류에서 성공 callback을 호출하지 않는다.
- HTML5 구현은 실패 시에도 초기 목록으로 Promise를 완료한다. 공백 초기값을 `[]`로 바꾸면 실패 Promise 결과도 `[]`가 된다.
- 디자인 구현은 실패 시 `undefined`로 Promise를 완료한다.
- 디자인 callback 래퍼 3곳은 성공 callback만 기다리므로 실패 시 대기가 끝나지 않을 수 있다. 기존 문제이며 공백 행 분리만으로 해결되지 않는다.
- HTML5 이벤트 선택 목록은 성공 callback에서만 미등록 검사를 수행한다. 이 구분을 반드시 유지한다.
- 검색 팝업은 실패 시에도 Promise 완료를 통해 데이터 전달/화면 처리를 이어가는 구조다.

따라서 실패를 새롭게 `reject()`하도록 변경하거나 결과 객체를 도입하려면 별도 설계와 호출처 전수 검토가 필요하다. 이번 변경에 임의로 포함하지 않는다. 실패를 성공 0건으로 오인하여 기존 이벤트 값을 삭제하거나 미등록 오류로 표시해서는 안 된다.

`bSkipUnLock`, `parent.setBusy`, `designAreaLockUnlock`, shortcut lock, UI5 core lock의 해제 책임도 목록 변경을 이유로 이동하지 않는다. 기존 예외 경로를 보완해야 한다면 범위를 구분하여 보고하고 검증한다.

## 9. 구현 순서

1. 현행 전체 소스에서 `getServerEventList`를 다시 검색한다. 새 호출처·재정의·백업 여부를 구분한다.
2. 두 조회 정의와 7개 직접 호출처가 여전히 같은 계약인지 확인한다. 실제 로드 경로도 확인한다.
3. 변경할 파일 목록을 보고하고 프로젝트 규칙에 따라 백업한다.
4. 조회 함수의 정상 성공 반환을 실제 이벤트 배열로 맞추고, 선택 UI 5곳에 화면용 공백 행을 추가한다. 두 변경을 하나의 작업 단위로 적용한다.
5. 검색 경로에는 공백 행을 추가하지 않는다. 실제 배열을 mutate하는 코드가 새로 생기지 않았는지 확인한다.
6. 아래 검증을 수행하고, 실제 실행하지 못한 항목은 미검증으로 남긴다.
7. 프로젝트 작업 이력을 작성한다. 승인 없이 커밋·푸시하거나 CURRENT.md를 갱신하지 않는다.

## 10. 검증 및 완료 기준

가능한 범위에서 stub 기반 계약 검증과 실제 UI 검증을 나눈다. 서버 응답 stub만으로 실제 화면·잠금 동작까지 통과했다고 보고하지 않는다.

| 구분 | 입력/조작 | 기대 결과 |
|---|---|---|
| 성공 0건 | `RETCD: "S", EVTLT: []` | callback과 성공 Promise의 실제 목록은 `[]`. 선택 UI에는 공백 1개 |
| 성공 여러 건 | 실제 이벤트 N개 | 반환 길이 N, 화면 목록 N+1. 항목 순서와 DESC 유지 |
| 호출 방식 | callback 있음/없음, skip true/false | 성공 시 Promise가 모두 완료되고 실제 배열 반환. 잠금 해제 책임 유지 |
| 현재 값 공백 | 클릭/F4/HTML5 선택 목록 열기 | 공백이 맨 위에 정확히 1개. 미등록 오류 없음 |
| 현재 값 정상 | 등록 이벤트에서 공백 선택 | 값 해제 가능. 기존 변경 반영·저장 흐름 유지 |
| 현재 값 미등록 | 삭제된 이벤트 값으로 목록 열기 | 기존 경로의 현재 값 보존·오류 표시 유지 |
| 동일 속성 적용 | UI5/HTML5 팝업에서 값 있음/없음 | 공백 선택 가능. 현재 값 보존 및 적용 동작 유지 |
| 검색 | 최초 열기 및 새로고침 | 실제 이벤트 설명·단축키 설명 매핑 정상, 공백 행 추가 없음 |
| 반복 열기 | 같은 목록 여러 번 열기 | 공백 행 누적 없음, 실제 반환 배열 길이 불변 |
| 서버 업무 오류 | `RETCD !== "S"` | 성공 callback 미호출 유지. 기존 값을 미등록으로 오판하지 않음 |
| 통신 오류 | 실패 callback 실행 | 새 busy/lock 고착이나 미처리 rejection이 생기지 않음. 기존 대기 문제는 별도 기록 |

검증 결과에는 적용된 조회 구현, 실행 환경, 실제 UI 실행 여부를 함께 적는다. 디자인 구현을 실행할 수 없다면 그 경로는 정적 검토/계약 검증까지만 수행했다고 명시한다.

## 11. 이번 분석의 한계와 인계 시 확인할 사항

- 현재 소스에 대한 정적 분석이다. 서버 요청이나 실제 UI 실행 검증은 수행하지 않았다.
- 외부 WS3 원본 저장소와의 비교는 수행하지 않았다.
- `pes-work-checklist`의 공용 Notion 체크리스트 조회는 이 PC의 전용 토큰 미등록으로 수행하지 못했다. 이를 테스트 면제 근거로 사용하지 않는다.
- 향후 구현 시 사용자 지시가 이 문서와 다르면 최신 사용자 지시를 우선한다. 특히 실패 반환 계약은 미확정 사항으로 취급한다.
