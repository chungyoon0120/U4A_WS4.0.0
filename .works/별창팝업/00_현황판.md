### 전략1. 커스텀 헤더 별창의 "최소화 후 복원 불가" 문제

| 구분 | 내용 |
|---|---|
| 문제 | 별창 제목줄을 직접 그린 화면(커스텀 헤더)에서 parent를 지정한 채 최소화하면, 작업표시줄에 안 뜨거나 다시 꺼낼 방법이 화면에 없음 |
| 원인 | 원본은 창 제목줄이 OS 기본이라 parent 여부와 무관하게 문제없었음. HTML5에서 제목줄을 직접 그리면서 드러남. 근거: [바인딩 팝업 현황판](../bindpopup/00_현황판.md) "그룹 WM"에서 최대화(WM2)는 확인 완료(✅ O), 최소화(WM1)는 아직 미확인(☐)으로 남아있어 설명과 일치 |
| 채택 전략 | BrowserWindow 생성 시 **parent 옵션을 뺀다** → 최소화해도 작업표시줄에 독립적으로 남아 복원 가능 |
| 영향 범위(소스 확인) | ① 거의 모든 별창이 쓰는 "이미 열려있으면 새로 안 열고 그 창을 앞으로 가져오기" 기능이 parent 기반 자식창 탐색 방식이라 함께 깨짐(`ws_common.js` `getCheckAlreadyOpenWindow`, `fnDialogPopupOpener.js` 안에서 15곳 이상 이 방식 사용) → parent 없으면 항상 "안 열려있음"으로 판단해 매번 새 창이 뜸. ② 화면 녹화의 모니터 선택 창처럼 parent가 있어야 걸리는 "뒤 화면 조작 막기"도 같이 빠짐. ③ **WS20 뒤로가기 시 열려있는 별창을 한꺼번에 닫는 기능도 같은 방식(parent 기반)이라 함께 깨짐 — 아래 전략1-③ 참고**. ④ **화면에 팝업이 뜨거나 busy(로딩 표시) 도는 동안 같은 부모의 별창들을 잠깐 숨겼다가 끝나면 다시 보여주는 기능도 같은 방식(parent 기반)이라 함께 깨짐 — 아래 전략1-④ 참고** |
| 상태 | ✅ 방향 전부 확정 — parent 제거·①③④ 대체 컨셉(브라우저키 비교), ②(뒤 화면 막기)는 대체 없이 제외. 구현 착수 가능 |

#### 전략1-① 조사 결과: "이미 열린 창 찾기"를 대신할 식별 정보가 이미 있는가

> 장군님 질문: "현재 별창 팝업 실행 시, 각 별창이 어떤 브라우저키와 세션키로 인해 떴는지 정보를 전부 다 알고 있는지 조사해"

**결론: 있음.** 지금 뜨는 별창 31개(+새로 확인된 컨트롤러 오류 안내 포함) **전부**, 창을 열 때 아래 세 가지 식별 정보를 같이 넣고 있음을 소스로 확인함.

| 식별 정보 | 뜻 | 값이 결정되는 시점 |
|---|---|---|
| 세션키(sessionKey) | 어느 **로그인(서버 접속)**에서 열린 창인지 | 로그인 한 번 할 때 하나 발급, 그 로그인에서 여는 모든 창(메인 창·별창 전부)이 같은 값을 물려받음 |
| 브라우저키(browserKey) | 같은 로그인 안에서, 어느 **WS10/20/30 메인 창**에서 열린 창인지 | 메인 창을 하나 새로 열 때마다(같은 로그인이라도) 새로 하나씩 발급 |
| 팝업 종류 이름(OBJTY) | 그 창이 **어떤 별창**인지(바인딩/MIME/옵션 등) | 별창 종류마다 코드에 고정값으로 있음(예: BINDPOPUP, MIMEPOP) |

- 거의 모든 별창이 부모 창(`parent`)의 세션키·브라우저키를 그대로 물려받아 저장한 채로 뜸(31개 중 확인된 예외 없음). 다만 **화면 녹화 안의 보조 창들(조작판·모니터 선택 등)은 이 정보를 저장 위치(webPreferences)가 아니라 창 주소(URL) 안에 실어 나르는 방식**이라 코드 위치는 다르지만, 정보 자체는 똑같이 있음.

**세션키 vs 브라우저키, 정확한 차이(2026-09-07 추가 확인)** — 장군님 질문: "너 혹시 브라우저 키와 세션키의 정확한 차이와 의미를 알고 있니?"

| 구분 | 세션키(sessionKey) | 브라우저키(browserKey) |
|---|---|---|
| 정체 | Electron이 **실제로 쓰는 브라우저 저장 공간 구분값**(`partition`) — 창을 만들 때 `webPreferences.partition`에 그대로 들어감 | Electron 기능과 무관한, **앱이 직접 관리하는 식별표**(무작위 문자열) |
| 실제 효과 | 같은 세션키를 쓰는 창들은 **쿠키·로컬저장소·캐시를 실제로 공유**함(다른 세션키 = 완전히 분리된 저장 공간) | 저장 공간과는 무관, "어느 메인 창에서 열렸는지" 표시만 함 |
| 범위(단위) | **로그인 하나** — 같은 로그인으로 메인 창을 여러 개 열어도 전부 같은 값 | **메인 창 하나** — 같은 로그인이어도 메인 창을 새로 열 때마다 다른 값 |

- 결론: 세션키가 브라우저키보다 **더 넓은 단위**(로그인 전체)이고, 브라우저키가 **정확히 "이 메인 창 하나"**를 가리킴. 그래서 "지금 이 창에서 연 별창만" 골라내려면 **브라우저키만 보는 게 정확**하고, 세션키까지 보면 같은 로그인의 다른 메인 창 별창까지 섞여버림.
- **이 근거로 전략1-①·③·④(이미 열린 창 찾기·뒤로가기 닫기·팝업·busy 중 숨기기) 전부 브라우저키만 비교하는 것으로 확정**(2026-09-07, 장군님 지시).
- **이미 이 정보만으로 "이미 열려있으면 새로 안 열고 그 창을 앞으로 가져오기"를 하는 팝업이 1개 존재**(MIME 저장소, `fnDialogPopupOpener.js` 118~130행) — parent(부모 지정) 없이도 "전체 창 목록에서 팝업 종류 이름이 같은 것 찾기" 방식으로 이미 동작 중. 즉 **전략1의 부작용(중복 방지·뒷화면 막기 무력화)을 풀 방법의 실제 선례가 이미 코드 안에 있음.**
**해결 방향 확정(2026-09-07, 장군님 지시 — "같은 브라우저키 비교 컨셉으로 통일해서 적용해")**: MIME 저장소의 선례(전체 창 목록에서 팝업 종류 이름 비교)에 **브라우저키 비교를 추가**해서 전체 별창에 통일 적용한다. 즉 "이미 열려있는지" 판단 기준을 **"팝업 종류 이름이 같다" + "브라우저키가 같다"** 둘 다로 좁혀서, 다른 로그인/다른 메인 창에서 연 같은 종류 팝업과 안 섞이게 한다(전략1-③과 동일한 컨셉으로 통일).

#### 전략1-② 설명: "뒤 화면 조작 막기"가 정확히 무엇인가

> 장군님 질문: "뒤 화면 막기 대체가 무슨 말인지 모르겠음"

**화면으로 설명하면**: 화면 녹화 기능에서 "녹화할 모니터 선택" 창을 열면, 그 창이 떠있는 동안 **뒤에 있는 원래 화면을 마우스로 눌러도 반응하지 않게 막혀버립니다**(그 선택 창을 닫거나 선택을 끝내야 다시 뒤 화면을 누를 수 있음).

- 이 "뒤 화면 못 누르게 막기"는 지금 **parent를 지정했을 때만 되는 Electron 자체 기능**입니다(Electron 용어로 "모달"). 소스 확인: `Popups\screen_record\popups\monitor-select\window.js` 81번째 줄 `modal: !!parentWindow` — parent가 있을 때만 이 막기가 켜지도록 돼있음.
- **전략1로 parent를 빼면, 이 "뒤 화면 못 누르게 막기"도 같이 사라집니다.** 즉 모니터 선택 창이 떠있어도 뒤 화면을 그냥 누를 수 있게 됨(원본과 다른 동작).
- **결정(2026-09-07, 장군님 지시 "어짜피 모달은 뒤 선택이 안되기 때문에, 모달은 제외")**: 이 "뒤 화면 막기"(모달)는 **대체 로직을 만들지 않고 이번 작업 범위에서 제외**한다. parent를 빼면서 자연히 없어지는 채로 둔다.

#### 전략1-③ 조사 결과: WS20 "뒤로가기" 시 열려있는 별창을 한꺼번에 닫는 로직

#### 전략1-④ 조사 결과: 팝업·busy 실행 중 같은 부모의 별창을 숨겼다가 끝나면 다시 보여주는 로직

> 장군님 질문: "현재 실행된 화면에 팝업 또는 busy가 실행될 경우 같은 브라우저키나 세션키에 해당되는 별창들을 숨겼다가 팝업이나 busy가 끝나면 다시 활성화하는 내용도 있어 알고있니?"

**결론: 있음.** 두 가지 경로로 동작하고 있음을 소스로 확인.

1. **자동 감시 방식** — 화면 안에 인앱 팝업(Dialog)이 하나라도 뜨면, 그걸 감시하고 있는 감시자(`_setDialogObserver`, `ws_fn_03.js`)가 자동으로 별창들을 숨기고, 팝업이 다 닫히면 자동으로 다시 보여줌. 코드 안 설명 그대로 옮기면: *"화면에 자식 윈도우 창이 여러개 떠있을 경우, 메시지 팝업·Dialog 등이 화면에 떠있으면 자식 윈도우에 가려져서 사용자가 인지를 못하므로, Dialog가 뜨는 걸 감지해서 자식 윈도우를 비활성화 했다가 Dialog가 닫히면 자식 윈도우를 활성화 시키는 목적"*.
2. **직접 호출 방식** — 활성화(Activate)·저장(Save) 버튼처럼 로딩 표시(busy)가 도는 구간, 그리고 "저장할지" 확인창이 뜨는 구간에서는, 그 처리 시작 직전에 별창을 숨기고 끝난 직후(또는 취소 시)에 다시 보여주는 코드가 곳곳에 직접 짝지어 들어가 있음(`ws_events.js`, `usp/ws_usp.js`, `usp/ws_html5_usp.js` 등 다수).
- 두 경로 다 실제로 숨기고 보여주는 함수는 같은 곳(`fnChildWindowShow`, `ws_fn_02.js`) — 역시 **"현재 창의 자식 창 목록"(`getChildWindows()`, parent 기반)** 을 훑는 방식.
- **숨김 예외 목록**(숨기지 않고 그대로 두는 별창) — `fnCheckPopupHideException`:

| 목록에 있는 이름 | 우리 인벤토리에서의 정체 | 확인 |
|---|---|---|
| VIDEOREC | 화면 녹화 | 일치 — 확인됨 |
| WINSHOWHIDE | 창 흐리게 보기 | 일치 — 확인됨 |
| EXAMPLE | WS10 헤더의 "예제 열기" 버튼(Ctrl+F1) | 확인 완료 — 전략1-③ 표와 동일 근거 |

- **이 기능도 parent(자식 창 목록) 기반이라 parent를 빼면 함께 깨짐** — 위 전략1 "영향 범위 ④"에 반영함. **해결 방향 확정**: 전략1-①·③과 동일하게 "전체 별창 중 브라우저키가 같은 것만" 방식으로 통일(세션키는 안 씀 — 근거는 위 전략1-①의 "세션키 vs 브라우저키, 정확한 차이" 참고).

### 전략2. 별창 팝업 간 busy 방송(연계) 검수 — 원본대로 제대로 됐는지

> 장군님: "우선 하고자 했던 내용은 별창 팝업관련된 연계 부분이야. 그리고 원본 소스에서 별창 팝업간 broadcast 로 busy 실행하는 로직이 있는 걸로 알고 있어. 그 부분도 다시 소스를 깊게 조사해서 제대로 잘 적용 되어 있는지 검수좀 보수적으로 아주 빡시게 해줘.. 예를 들어, 별창 팝업이 2개가 있다. 한쪽 별창 팝업에서 뭔가 저장 등 행위를 하려고 한다. 그런데 저장 질문 팝업이 떴다. 그러면 다른 나머지 별창에서는 별다른 액션을 하지 못하게 busy를 키게 하는데 이게 broadcast로 신호를 보내서 현재 별창 팝업에서 작업중인걸 집중 시키고 다른 창에서의 액션을 막기 위해 이런 설계가 들어가 있다.. 그래서 원본 소스를 깊게 철저히 분석해서 이런 내용을 정확하게 구현해야함.."

**확인된 메커니즘(소스 확인)**: WS10/20/30 메인 창과 그 창에서 연 모든 별창은 **같은 이름의 방송 채널**(`broadcast-to-child-window_` + 브라우저키)을 하나씩 만들어 공유한다. 이 채널로 "BUSY 켜짐"/"BUSY 꺼짐" 신호를 보내면, **보낸 자기 자신을 뺀 나머지 전부**(메인 창 + 다른 형제 별창들)가 그 신호를 받아 busy를 켜거나 끈다. 장군님이 말씀하신 시나리오(별창 하나가 저장 확인창을 띄우면 다른 별창들이 다 잠김)와 정확히 일치하는 설계.

**신호를 받는 쪽은 정상.** 다만 착각하기 쉬운 **죽은 폴더 1건**과, 원본에도 있던 **잠금 안 풀리는 결함 몇 건**을 확인함. 전부 원본 대조 완료 — **새로 생긴 문제는 없고, 전부 원본에 이미 있던 것을 그대로 옮긴 것**.

- **원본 대조**: 결함 항목(잠금 안 풀리는 결함)은 원본(`U4A_WS_DESIGN`)에도 줄 번호까지 똑같이 존재 — 변환 과정에서 생긴 새 버그가 아니라 원본부터 있던 것.

**"3곳 조기종료 지점" 재추적 상세(2026-09-08, 직접 소스 재확인)** — 별도 조사(배경 작업)에서 "이 3곳이 무조건 잠금을 못 푼다"는 주장이 나왔으나, 아래처럼 끝까지 쫓아간 결과 **틀린 주장으로 확인**:
- 3곳(`attrChangeAutoGrowingProp`·`attrChangeDropAbleProp`·`attrDocumentProc`의 UI 테마 분기) 모두, 어떤 경로로 빠지든 **예외 없이** `oAPP.fn.updateBindPopupDesignData()`를 호출함(코드 3곳 전체 줄 단위로 재확인).
- 이 함수(`design\bindPopupHandler\broadcastChannelBindPopup.js` 583번째 줄)는: 바인딩 팝업이 **안 열려있으면** 그 자리서 바로 전체 별창에 잠금 풀림을 방송하고, **열려있으면** 데이터를 바인딩 팝업에 보내기만 함.
- 바인딩 팝업 쪽 수신부(`Popups\bindPopup\wsDesignHandler\bindBroadcast.js` `_updateDesignData`)는 데이터를 받아 처리한 뒤, **성공하든 오류가 나든 무조건 실행되는 마무리 구간(`finally`)**에서 ①WS20 쪽 잠금을 풀어주는 신호와 ②바인딩 팝업 자신의 로딩 표시 끄기(이것도 전체 별창에 잠금 풀림으로 다시 방송됨, `frame.js` 확인)를 둘 다 실행함.
- 즉 "바인딩 팝업이 열려있든 없든" 두 경우 다 결국 잠금이 풀리는 구조 — **처음 의심은 왕복 구조를 끝까지 안 쫓아가서 생긴 착오**였음.

**바인딩 성공 시 최종 잠금 해제(미확인 → 확인 완료, 2026-09-08)**: 필드를 실제로 끌어다 바인딩을 성공시켰을 때도 **위와 똑같은 왕복 구조**를 그대로 씀 — 바인딩 팝업은 성공해도 스스로 잠금을 풀지 않고(`designArea.js` 784번째 줄 주석 "★busy 자기해제 안 함 — WS20 가 반영 후 BUSY_OFF 방송으로 해제"), WS20이 데이터를 받아 반영을 끝낸 뒤 방송으로 풀어주는 걸 기다림. 이 구간은 과거(2026-08-09)에 이미 한 차례 검수돼 코드 주석으로 설계 의도가 남아있음 — **정상 확인**.

**모나코 테마·스니펫 디자이너 "확인창 열린 채 닫기" 안전장치 누락(미확인 → 문제 아님으로 정정, 2026-09-08)**: 이 두 팝업은 애초에 **다른 별창을 잠그는 방송 자체를 보내지 않음**(원본부터 "받기 전용"으로 만들어짐 — 코드 안에 "이 팝업은 수신 전용 — opener는 BUSY_ON을 쏘지 않는다(원본 동일)"라는 설명이 두 팝업 다 그대로 있음). 저장 확인창이 자기 안에서 뜨는 동안 다른 별창을 잠그는 동작 자체가 원본부터 없었으므로, "확인창 열린 채 닫으면 잠금이 안 풀린다"는 걱정은 **해당 사항 없음**.

- 모나코 테마·스니펫 디자이너 "확인창 열린 채 닫기" 안전장치 누락 의심 → 이 두 팝업은 애초에 다른 별창을 잠그는 방송을 보내지 않도록 원본부터 설계돼 있어(수신 전용), 해당 사항 없음. **문제 없음**.
