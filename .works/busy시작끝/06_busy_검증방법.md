# busy 검증 방법 — 눈이 아니라 로그 순서로

> 2026-09-16 · 소스로만 확인 · **코드는 한 줄도 안 고쳤다.**
> 장군님 지적: 「단순히 busy가 켜지고 꺼지는지에 대한 테스트는 의미가 없어」 · 「속도 빠른 pc에서는 체감이 안될 수도 있어 사람의 눈으로는 한계가 있다」

## 1. 정해 주실 것 (제 생각 먼저)

| 물음 | 제 생각 |
|---|---|
| busy 로그는 **상시인가, 테스트 때만인가** (장군님 물음 2026-09-16) | **끈 자리 1줄만 상시, 나머지는 테스트용** — §6. 켠 자리만 알면 「어디서 못 껐나」를 못 가린다(장군님 지적). **끈 자리 줄이 없다는 사실**이 곧 「거기까지 못 갔다」는 증거다 |
| busy 켠 순간·끈 순간을 로그로 남길까 | **남긴다.** 켜고 끄는 공통 두 곳(busy 표시 `setDomBusy`→`U4ABusy`, 조작 잠금 `setBusy`)에서만, **상태가 실제로 바뀔 때만** 한 줄씩. 부른 코드 자리를 같이 남긴다. 사건 이름 `BUSY_ON` · `BUSY_OFF` 를 로그 표준 사건 표에 추가한다. 한 처리에 2줄이라 양 규칙(V5) 안쪽 |
| 새창 로드 단계 시각도 같이 남길까 | **남긴다.** 창 보임(`show()`) · 스크립트 목록 로드 시작/끝(실패하면 그 파일 이름) · 메인 본문 등장 완료. 이게 있어야 「리소스보다 먼저 켜졌나」를 시각으로 판정한다 |
| 창이 **숨겨져 있는 동안** 로드되는 `<head>` 리소스도 「busy 보다 먼저 로드되면 안 되는 것」에 넣나 | **뺀다.** 창이 안 보이고 누를 수도 없는 구간이다. 대신 로그로 **`BUSY_ON` 이 창 보임보다 앞서는지**, 창 보인 뒤 스크립트 목록 로드가 **`BUSY_ON` 뒤에** 시작하는지를 본다. §3 첫 줄 사실 참고 |
| 개발 모드로 테스트한 것도 로그 **파일**에 남길까 | 지금 표준은 **포장한 앱에서만 파일**(로그 표준 §6). 장군님이 개발 모드로 테스트하시면 제가 읽을 파일이 없다. **제 생각: 이 busy·로드 단계 줄은 개발 모드에서도 파일로 남긴다.** 로그 쪽 코드를 얼마나 고쳐야 하는지는 아직 안 봤다(미확인) |
| 오류 갈래는 어떻게 시험하나 | 스크립트 파일 로드 실패 같은 오류는 정상 조작으로 안 난다. **시험용 강제 실패 스위치**를 넣는다 — 포장본에서는 절대 안 돌게 막는다(`app.isPackaged` 가드). 어느 자리를 실패시킬지 목록은 로그를 넣은 뒤 따로 드린다 |
| §4 에서 찾은 구멍을 지금 고칠까 | **로그부터 넣고, 로그로 실제 확인한 뒤 고친다.** 지금은 보고만 |

## 5. 로그가 생기면 이렇게 판정한다

| 장군님이 보시려는 것 | 로그에서 보는 것 |
|---|---|
| 1 리소스 전에 켜짐 | `BUSY_ON` 시각 < 창 보임 시각 < 스크립트 목록 로드 시작 시각 |
| 2 다 끝난 뒤 꺼짐 | `BUSY_OFF` 의 코드 자리가 끝점(메인 본문 등장 완료 등)이고, 그 뒤에 같은 처리의 서버 응답·화면 그리기 줄이 없다 |
| 3 중간 해제 0 | 한 처리 안에서 `BUSY_OFF` 가 1줄뿐이다. `BUSY_OFF` 뒤에 `BUSY_ON` 이 다시 나오면 중간 해제 |
| 4 오류 시 | 오류 줄 뒤에 `BUSY_OFF` 가 있고, 메시지를 띄운 흔적이 있다 — 메시지 흔적을 어디서 남길지는 §3 미확인 해소 뒤 정한다 |

장군님께는 **조작만** 부탁드리고, 판정은 제가 로그로 한다. 조작 표는 로그 코드를 넣은 뒤 이 폴더 현황판에 따로 드린다.

## 6. 상시로 남길 것 · 테스트 때만 둘 것 (장군님 물음 2026-09-16)

**장군님 판단: busy 로그는 테스트용이다.** 운영에서 busy 가 안 풀려도, 지금 남는 줄로 「사용자가 무슨 조작을 하다가 그 상태까지 갔는지」가 유추된다.

### 지금 이미 남는 것 — 소스로 확인

| 남는 줄 | 담긴 것 | 근거 |
|---|---|---|
| 버튼 누름 | 창 이름 · 화면 이름 · 추적 번호 · **화면에 적힌 버튼 글자**. 누른 즉시 가로채 남기므로 빠지지 않는다 | `ws_html5_logger.js` 1018·712줄 |
| 서버 요청 | 보냄 · 끝남 · 늦어짐 · 실패(서버가 준 내용 포함). 공통으로 지나가는 한 곳에서 남긴다 | 로그 표준 §4-3 |
| 오류 줄 | **그 순간 busy 가 켜져 있었는지**가 같이 붙는다 | `ws_html5_logger.js` 826·646줄 |

→ 「이 버튼을 눌렀고 → 이 요청까지 갔고 → 거기서 멈췄다」까지는 이미 나온다. **조작을 알면 그 처리의 끝점은 소스에서 찾는다.**

### 「어디서 못 껐나」는 어떻게 아나 (장군님 물음 2026-09-16)

**안 끈 자리는 로그로 못 남긴다.** 일어나지 않은 일이라 남길 코드가 지나가지 않는다.
알 수 있는 것은 **그 처리가 어디까지 갔나**뿐이고, 그 다음이 「빠진 끝점」이다. 그래서 세 조각이 필요하다.

| # | 조각 | 줄 수 | 무엇을 알려 주나 |
|---|---|---|---|
| ① | busy 를 **켠 자리** | **0** (기억만 하고, 이미 나가는 오류·누름 줄에 덧붙인다) | 어느 처리가 걸어 놨나 |
| ② | busy 를 **끈 자리** | 처리 1건당 **1줄** | 어느 끝점으로 끝났나. **이 줄이 없으면 = 그 처리가 그 끝점에 못 갔다** → 빠진 끝점이 어디인지는 켠 자리부터 소스에서 따라간다 |
| ③ | **짝이 안 맞을 때** | 이상할 때만 **1줄** | 중간에 풀렸나(장군님 목표 3) |

②가 없으면 「끝까지 가서 껐다」와 「도중에 멎었다」를 **로그로 구분할 수 없다.** 그래서 ②는 **상시**가 맞다 — 앞 턴에서 테스트용으로 내렸던 줄을 여기로 되돌린다.
여러 창이 섞여도 **줄마다 창 이름이 자동으로 붙는다**(로그 표준 §4-3).

### 그래서 이렇게 한다

| 무엇 | 상시 / 테스트용 | 왜 |
|---|---|---|
| busy **끈 자리** 1줄 (켠 자리 · 걸린 시간 포함) + 짝 안 맞음 경고 | **상시** | 위 ②③. 처리 1건당 1줄이라 하루 수십~수백 KB |
| busy **켠 순간**을 따로 남기기 | **테스트용** (기본 꺼짐, 스위치로 켠다) | 순서를 촘촘히 볼 때만 필요하다 |
| 새창 로드 단계 (창 보임 · 스크립트 목록 로드 시작/끝 · 메인 본문 등장 완료) | **테스트용** — 같은 스위치 | 순서 판정에만 쓴다 |
| **강제 실패 스위치** (오류 갈래 시험용) | **테스트용** — 포장본에서는 절대 안 돌게 막는다(`app.isPackaged` 가드) | 일부러 고장 내는 코드다. 고객사 PC 에서 돌면 안 된다 |

### 다만 이것만은 상시로 두는 것이 이득이라고 본다 (정해 주실 것)

오류 줄에는 이미 busy 상태가 붙는다. 거기에 **마지막으로 busy 를 켠 자리** 한 토막만 덧붙이면 **줄 수는 하나도 안 늘면서** 「누가 켜 놓고 안 껐나」가 바로 나온다.

### 스위치를 어디에 두나 (정해 주실 것)

개발 모드로 돌리면 **로그 파일이 아예 안 생긴다**(실측, §3 표). 그래서 테스트용 로그를 제가 읽으려면 둘 중 하나다.

| 방법 | 제 생각 |
|---|---|
| ⓐ **포장본 + 스위치로 켜기** | **이쪽이 낫다.** 운영과 같은 조건에서 보게 된다. 스위치를 어디에 둘지(텔레그램처럼 설정 파일 하나)는 **아직 확인 안 했다(미확인)** |
| ⓑ 개발 모드에서도 이 줄만 파일로 남기기 | 로그 쪽을 더 고쳐야 한다 |

### 6-1. 양을 줄이는 방식 (장군님 지적 2026-09-16 「로그가 너무 많이 쌓이는 것도 생각해야 한다」)

앞서 「켜기 1줄 + 끄기 1줄」이라고 적었던 것을 **처리 1건당 1줄**로 줄인다.

| 언제 | 남기나 | 무엇을 |
|---|---|---|
| busy 를 **켤 때** | **안 남긴다** | 켠 자리와 시각은 **기억만** 해 둔다(줄 0) |
| busy 를 **끌 때** | **1줄 (INFO)** | 켠 자리 → 끈 자리, 걸린 시간. 이 한 줄에 왕복이 다 들어간다 |
| 상태가 **안 바뀌는 호출** (켜짐→켜짐, 꺼짐→꺼짐) | **안 남긴다** | 겹쳐 들어온 호출로 줄이 불어나지 않는다 |
| **짝이 안 맞을 때** (켠 적 없는데 끄기 · 끈 뒤 같은 처리가 다시 켜기) | **1줄 (WARN)** | 중간 해제 의심 자리. 이게 장군님이 보시려는 3번이다 |
| busy 가 **안 풀린 채 있을 때** | **새 줄을 안 만든다** | 이미 남는 누름·오류 줄에 busy 상태가 찍힌다. 거기에 **마지막으로 켠 자리**만 덧붙인다(줄 수 증가 0) |
| 스위치를 켠 테스트 중 | 켤 때도 남긴다 | 순서를 촘촘히 봐야 한다. 스위치가 꺼진 평소에는 busy 줄이 **아예 안 나간다**(§6) |

**어림 계산** — 줄 하나가 약 130 글자다(로그 표준 §3 예시 줄 기준). 하루에 busy 가 걸리는 조작이 1,000 번이라고 **가정**하면 약 130 KB.
로그 표준 §5 기준(하루 8시간에 5 MB 안쪽)의 3% 수준이다. 실제 조작 횟수는 안 재 봤다(**미확인**) — 로그를 넣고 하루 써 본 뒤 실측해서 이 문서에 적는다.

새창 로드 단계는 **창 하나당 3~4줄**이라 창을 백 번 열어도 수백 줄이다.
