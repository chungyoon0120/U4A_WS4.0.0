# 렌더 완료 아키텍처 — 무엇을 만들고 코드가 어떻게 바뀌나

> 2026-09-21 · 장군님: **「어떤 아키텍처로 할지 이해가 안 된 상태다. 그걸 정확히 알아야 진행할지 말지 결정하겠다.」**
> **소스로만 조사. 코드는 한 줄도 안 고쳤다.** 배경 = [08_DOM_다그려진뒤_busy끄기.md](08_DOM_다그려진뒤_busy끄기.md)

---

## 1. 정해 주실 것

| # | 물음 | 제 생각 |
|---|---|---|
| 1 | **공통 함수를 만드나** (§5) | **busy 끄는 공통 함수 = 안 만든다.** busy 쪽은 손 안 댄다. **대기 도우미 파일 1개만** 만든다 — 그림·안쪽 화면·글 편집기처럼 기다리는 방법이 같은 것들을 묶는 용도. **원본도 딱 이 모양**이다 |
| 2 | **화면을 그리는지 뭘로 판단하나** (§6) | **이미 도는 감시 프로그램이 실제로 걸어낸 곳**을 씁니다. 소스 grep 은 놓치는 게 있어 **점검표로만** 씁니다 |
| 3 | 진행 여부를 지금 정할까 | **아니오.** 먼저 **대상이 몇 곳인지** 보신 뒤 정하시는 게 맞다고 봅니다 (§7) |

## 2. 한 줄 요약

**새 장치를 만드는 게 아니다.** 그리는 함수가 **끝났다는 약속(Promise)을 돌려주게** 하고,
busy 를 끄는 쪽이 그 약속을 **기다린 뒤에** 끈다. 원본이 UI5 에서 하던 것과 같은 모양이다.

## 3. 지금 코드는 이렇게 생겼다 (실물, 조회 2026-09-21)

어플리케이션 복사 팝업 (`js/fnAppCopyPopupOpen.js` 253~297줄):

```
busy ON
  → 서버 호출
      → 응답 콜백에서 ── 팝업 닫기
                      └─ 서버가 준 SCRIPT 실행 (화면 전환까지 일어난다)
        busy OFF        ← 여기
```

**문제**: `busy OFF` 가 **「그리기가 끝났다」 자리가 아니다.** 그냥 **코드 줄 순서상 거기**일 뿐이다.
그 뒤에 도는 화면 전환·팝업 열기가 DOM 을 더 건드린다.
실제로 소스 주석에도 **「화면전환/CTS 팝업이 busy 가드에 막히지 않게 먼저 해제」** 라고 적혀 있다 —
**끝나서 끄는 게 아니라, 다음 동작을 통과시키려고 미리 끄고 있다.**

> ※ 이 파일을 지금 고치자는 말이 아니다. **지금 구조가 어떤 모양인지 보여 드리는 실물 예시**다.

## 4. 무엇이 없어서 이렇게 됐나

| 원본(UI5) | 지금(HTML5) |
|---|---|
| UI5 가 `onAfterRendering` 을 불러 준다 | **없다** |
| 원본이 그걸 Promise 로 감싸 `await` 했다 (`design/js/previewRender/setOnAfterRender.js` 15줄) | **그 자리가 비었다** |
| 글 편집기·차트·팝업 열림은 **추가로 더 기다렸다** (같은 파일 주석, 2025-01-15) | **안 기다린다** |

**즉 빠진 건 「이벤트」가 아니라 「기다리는 약속」이다.** 그래서 만들 것도 이벤트가 아니다.

## 5. 공통 함수를 만드느냐 — **두 개를 나눠서 답한다** (장군님 물음 2026-09-21)

> **먼저 정정**: 제가 앞 문서(08번 §10.4)에서 **「공통 함수 하나를 둔다」** 고 썼고,
> 이 문서 처음 판에서는 **「만드는 것 없다」** 고 썼다. **앞뒤가 달랐다.** 아래로 확정한다.

| 무엇 | 만드나 |
|---|---|
| **busy 를 끄는 공통 함수** | **안 만든다.** busy off 는 지금 쓰는 그대로 두고, **부르기 전에 `await` 를 붙일 뿐**이다 |
| **기다리는 방법이 같은 것들을 묶은 작은 도우미** | **만든다.** 그림 파일 읽기 완료 · 안쪽 화면 읽기 완료 · 글 편집기 준비 완료 — 화면마다 똑같은 코드를 다시 쓰지 않게 |

**원본도 딱 이 모양이다.** 디자인 영역 `design/js/previewRender/setOnAfterRender.js` 한 파일 안에
대기용 함수가 **여러 개** 들어 있다 — 팝업이 다 열렸다는 신호 대기, 글 편집기 안쪽 문서 준비 대기,
예외 대상 대기. **busy 를 끄는 공통 함수는 원본에도 없다.**

### 5.1 그래서 코드가 이렇게 바뀐다

```
[ 지금 ]                          [ 바뀐 뒤 ]
화면 그리기();                     await 화면 그리기();      ← await 한 글자 추가
busy 끄기;                        busy 끄기;               ← 그대로. 안 건드린다
```

그리고 `화면 그리기()` 안에서, **기다릴 게 있을 때만** 도우미를 쓴다:

```
function 화면 그리기() {
    ... DOM 채우기 ...
    return 도우미.그림읽기완료(이미지들);   ← 기다릴 게 있으면 이것만
}                                          ← 없으면 그냥 끝 (return 없음)
```

| | |
|---|---|
| **새로 만드는 파일** | 대기 도우미 **1개** (그 안에 함수 두셋) |
| **busy 쪽 손대는 것** | **없음** |
| **화면 쪽 손대는 것** | `await` 한 글자 + (기다릴 게 있는 화면만) 도우미 호출 한 줄 |

## 6. 「화면을 그리는지」는 뭘로 판단하나 (장군님 물음 2026-09-21)

**기계로 100% 가려낼 수 없다.** 그리기가 다른 함수 안에 숨어 있으면 grep 이 못 본다.
방법이 두 가지이고, **제 권고는 ②** 다.

### ① 소스로 후보를 뽑는다 — 불완전

busy 를 끄는 자리 **위쪽**에 DOM 을 건드리는 것이 있는지 본다.

| 보는 것 | 예 |
|---|---|
| DOM 을 직접 건드리는 호출 | 자식 붙이기·지우기, 안쪽 내용 넣기, 속성·class 바꾸기 |
| 이 프로젝트의 그리기 공통 부품 호출 | tree 만들기, table 만들기, 입력칸 만들기 |

- **장점**: 앱을 안 켜도 된다. 359곳을 한 번에 훑는다.
- **단점**: **놓친다.** 그리기가 서버가 준 SCRIPT 안에 있거나(§3 사례), 다른 함수 두세 겹 안에 있으면 안 잡힌다.
  반대로 **글자만 보고 아닌 것을 후보로 넣기도** 한다.

### ② 이미 도는 감시 프로그램이 **실제로 걸어낸 곳만** — **권고**

장군님 말씀대로 **감시하는 프로그램은 이미 따로 있다.**
그게 **「busy 를 끈 뒤에 DOM 이 바뀐 곳」** 을 실제로 집어낸다.

- **장점**: **추측이 0.** 걸린 곳이 곧 고칠 곳이고, 그게 곧 증거다.
  359곳을 다 훑을 필요가 없다 — **실제로 문제가 나는 곳만** 고친다.
- **단점**: 그 화면을 **한 번은 열어 봐야** 잡힌다. 안 열어 본 화면은 목록에 안 뜬다.

### ③ 둘을 섞는 것이 현실적

①로 **후보 목록**을 만들어 두고, ②가 **실제로 걸어낸 것부터** 고친다.
①은 「아직 안 열어 본 화면」 을 빠뜨리지 않기 위한 **점검표**로만 쓴다.

## 7. 규모 — 이게 진행 여부의 핵심입니다

| 세어 본 것 | 수 |
|---|---|
| busy 를 끄는 자리 (`js/` 안) | **359곳** |
| 그중 **실제 대상**(서버 다녀와서 화면을 그리는 것) | **아직 안 셌다** |

**359곳이 전부 대상이 아니다.** 팝업 닫기·취소·오류 종료처럼 **그릴 게 없는 곳**이 많다.
→ **먼저 그 숫자를 보신 뒤** 진행 여부를 정하시는 게 맞다고 봅니다.
숫자 없이 정하면 도중에 규모가 드러나 멈추게 된다.

## 8. 안 하면 / 하면

| | |
|---|---|
| **안 하면** | 지금처럼 **「코드 줄 순서상 거기」** 에서 busy 가 꺼진다. 덜 그려진 화면을 사용자가 조작할 수 있는 틈이 남는다. 재현이 어려운 고장으로 나타난다 |
| **하면** | busy OFF 자리가 **「끝났음이 증명된 자리」** 가 된다. 이미 도는 감시 프로그램이 그걸 그대로 확인해 준다 |

## 9. 위험

| 위험 | 내용 |
|---|---|
| **약속이 영영 안 이행되면** | busy 가 안 꺼진다. 지금은 「일단 끄고 본다」 라 이 고장이 없었다. **기다리는 대상마다 실패 갈래를 반드시 만들어야 한다** |
| **`async` 전파** | 한 함수를 `async` 로 바꾸면 그걸 부르는 쪽도 기다려야 할 수 있다. 어디까지 번지는지는 **대상 목록을 뽑아 봐야 안다**(§6) |
| **한꺼번에 하면** | 359곳 근처를 한 번에 건드리면 되돌리기 어렵다. **한 화면씩, 그 화면 테스트를 통과한 뒤 다음**으로 간다 |

## 10. ★ 정정 — 「원본에 busy 끄는 공통 함수가 없다」 는 **틀렸다** (2026-09-21)

> 장군님: **「busy 를 끄는 공통 함수는 원본에도 없다니 무슨 개소리야.
> 함수 이름이 달랐을 뿐 실제 실행하는 공통 함수는 있는데.」**

**장군님 말씀이 맞습니다. 확인 안 하고 단정했습니다.** §5 의 그 문장을 철회합니다.

### 10.1 원본에 실제로 있는 것 (조회 2026-09-21)

| 무엇 | 어디 |
|---|---|
| 켜고 끄는 **단일 통로** | 원본 `www/ws30/resources/index.js` **1544줄** `setBusy(bIsBusy, oOptions)` |
| 그 안에서 갈라지는 실체 | 같은 파일 **901줄** (일반 busy) · **995줄** (안내 글 있는 busy) |
| 창·팝업별 래퍼 | `oAPP.fn.setBusy` · `oAPP.common.fnSetBusyLock` 등 여러 곳 — **결국 위 한 곳으로 모인다** |

**지금 작업 폴더의 것도 이 원본을 그대로 가져온 것**이다(본문 동일, 작업 폴더 같은 파일 1646줄).

### 10.2 제가 말하려던 것과 실제로 쓴 문장이 달랐다

| 제가 쓴 문장 | 틀림 |
|---|---|
| 「busy 를 끄는 공통 함수는 원본에도 없다」 | **완전히 틀렸다.** 있다 |
| 제가 말하려던 것 | 「**렌더 완료를 기다린 뒤** 끄는 전용 장치는 없었다」 — 이건 맞다. 다만 **확인 없이** 단정한 것 자체가 잘못 |

### 10.3 ★ 이게 설계를 바꾼다

**켜고 끄는 통로가 이미 하나로 모여 있다면, 거기가 자연스러운 자리다.**
제가 A 안을 권한 근거 하나(「원본에도 공통이 없다」)가 **사실이 아니었으므로**, 권고를 다시 답니다.

| | **A 안** — 호출처마다 기다리기 | **B 안** — 공통 통로에서 기다리기 |
|---|---|---|
| 손대는 곳 | 기다릴 게 있는 화면 + **그 화면의 busy 끄는 줄** | **공통 통로 1곳** + 기다릴 게 있는 화면 |
| busy 끄는 자리 359곳 | 대상만 손댐 | **안 건드림** |
| 소스에서 보이나 | **보인다** (기다리는 코드가 그 자리에 있음) | 공통에 숨는다 |
| 안 해 주면 | 예전과 똑같이 동작 | 예전과 똑같이 동작 (**둘 다 같음**) |
| 위험 | 기다리는 곳이 안 풀리면 busy 안 꺼짐 | **같음** + 등록해 놓고 안 풀면 **다른 화면까지** 잠길 수 있음 |
| 원본과의 거리 | 원본 디자인 영역이 하던 모양 그대로 | 원본에 없던 **새 개념**(등록 창구) |

**제 판단**: 손대는 **화면 수는 두 안이 같다**(기다릴 게 있는 화면만). 차이는 그 화면에서
**기다리느냐 / 등록하느냐** 뿐이다. 그렇다면 **짝을 안 맞춰도 되는 A 가 더 안전**하다고 봅니다 —
B 는 등록해 놓고 안 풀면 **다른 화면의 busy 까지** 못 끄게 된다.

**다만 근거 하나가 무너졌으므로 강하게 밀지 않습니다. 장군님이 정해 주십시오.**
