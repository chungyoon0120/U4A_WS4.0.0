# 서버 다녀온 뒤 「DOM 이 다 그려진 다음」 busy 끄기 — 가능한가

> 2026-09-21 · 장군님 물음: **busy 를 먼저 켜고 → 서버 갔다 와서 → 그 데이터로 화면을 그리고 → DOM 이 완전히 다 그려졌을 때 busy 를 끄는 로직.**
> **소스로만 조사. 코드는 한 줄도 안 고쳤다.**

---

## 1. 정해 주실 것

> **과제 = 「UI5 가 주던 렌더 완료 이벤트가 HTML5 에 없다. 무엇으로 대신할 것인가」** (장군님 정정 2026-09-21)
> 실측·감시가 과제가 아니다. 감시하는 프로그램은 따로 있다. **§10 이 본론, §11 이 정정이다.**
>
> **⚠ §2·§7 은 제가 처음에 쓴 것이고, 그중 「rAF 2번」 은 §11 에서 철회했다.** 남겨 둔 건 경위 기록용이다.

| # | 물음 | 제 생각 |
|---|---|---|
| 1 | 무엇으로 대신할까 | **원본과 같은 모양**입니다 — 그리는 쪽이 끝에서 알리고, 부르는 쪽이 `await`. 원본도 UI5 이벤트를 그대로 쓴 게 아니라 **Promise 로 감싸서** 기다렸습니다(§10.2) |
| 2 | rAF 2번은 | **철회합니다**(§11). 재는 것이 달랐고, 원본에도 없었고, 2번으로 막지도 못합니다 |
| 3 | rAF 로 예약된 조작은 | **같은 원칙** — 예약하는 쪽이 끝났음을 알려 줍니다. 프레임 수로 못 박지 않습니다 (§11.4) |
| 4 | 그리는 함수마다 다 고칠까 | **아닙니다.** 공통 함수 하나를 두고, 각 화면은 **「내가 기다려야 할 것」만 넘깁니다** (§10.4) |
| 5 | 미리보기 영역은 | **건드리지 않습니다.** 거긴 아직 UI5 가 살아 있고 그 장치가 지금도 돕니다 (§10.3) |

## 2. 답 — 가능하다

**결론: 된다.** 다만 「DOM 이 다 그려졌다」를 알려주는 **단일 API 는 브라우저에 없다.**
(`document.readyState` 는 문서 최초 로드용이지, 나중에 데이터로 다시 그린 것과는 무관하다.)

실제로 쓸 수 있는 신호는 **`requestAnimationFrame` 을 두 번 겹치는 것**이다.

- 첫 rAF 콜백 = 다음 프레임의 layout·paint **직전**. 이 시점은 **아직 안 그려진 상태**다.
- 그 안에서 rAF 를 한 번 더 걸면, 그 콜백은 **앞 프레임이 paint 를 끝낸 뒤** 불린다.
- 즉 **double rAF = 「화면에 실제로 나온 다음」**. 여기서 끄면 장군님이 원하시는 그림이 된다.

이 프로젝트에 이미 같은 패턴이 쓰이고 있다 — 값도움 팝업에서 목록을 다시 그린 뒤 마우스 자리 강조를
되살리는 자리(`www/ws30/ws10_20/js/fnAppF4PopupOpen.js` 300줄), 미리보기 다시 맞추는 자리
(`fnP13nDesignPopupOpen.js` 882줄). rAF 사용처는 `js/` 안에만 25곳이다.

## 3. rAF 만으로는 모자란 것 — 각자 자기 완료 신호를 기다려야 한다

double rAF 가 보장하는 건 **그 시점에 DOM 에 들어가 있는 것들의 첫 paint** 다.
아래는 그 뒤에 따로 채워지므로, 그것까지 기다리려면 **그 대상의 완료 신호**를 같이 기다려야 한다.

| 대상 | 기다릴 신호 |
|---|---|
| `<img>` | `img.decode()` 또는 `onload` |
| `<iframe>` (미리보기 등) | `onload` |
| webfont | `document.fonts.ready` |
| Monaco editor | Monaco 자신이 주는 완료 이벤트 |
| virtual scroller 목록 | **전체 DOM 이 애초에 없다** — 첫 화면분만 그려진다. 「다 그려짐」을 **첫 화면분 paint** 로 정의해야 한다 |

그래서 공통 함수는 **「rAF 2번 + (있으면) 이 대상들의 완료」** 를 묶어 기다리는 모양이 된다.

---

## 4. 함정 — 창이 숨겨지면 rAF 가 멈춘다

`requestAnimationFrame` 은 그 창이 **숨겨지거나 최소화되면 콜백이 오지 않는다.**
별창을 열어 두고 다른 창으로 가 버리면 **busy 가 영영 안 꺼진다.**

그래서 상한(watchdog)이 필요하다. 다만 이건 **정상 경로가 아니라 고장 알림용**이다 —
상한에 닿으면 끄면서 **무엇을 기다리다 못 기다렸는지 ERROR 로그**를 남긴다
(`.works/DEV_STANDARD_로그.md`). 정상일 땐 언제나 rAF 쪽이 먼저 온다.

느린 PC 규칙(「N초 뒤에 하면 되겠지」 금지, 끝난 것을 확인하고 넘어가라)과도 이 모양이 맞다 —
**시간을 못 박는 게 아니라 프레임 신호를 기다리고**, 상한은 고장일 때만 쓰인다.

## 6. 만든다면 이런 모양 (아직 안 만들었다)

- 공통 함수 하나를 두고(예: 화면이 다 나온 뒤 콜백을 주는 함수), 각 화면은 **그리기 끝 → 그 함수 → busy off** 만 쓴다.
- 기다릴 대상(이미지·iframe·Monaco)은 **부르는 쪽이 넘긴다**. 공통이 알아서 찾아다니지 않는다.
- 실패·조기 return 갈래에서도 busy 를 끄는 건 종전 그대로. 이 함수는 **성공 끝점만** 뒤로 민다.
- 로그: 기다리기 시작 / 몇 프레임 만에 나왔는지 / 상한에 닿았으면 무엇을 못 기다렸는지 (영어).

## 7. 「왜 2번이냐 · 3번은 안 나오냐 · PC 속도 타지 않느냐」 (장군님 물음 2026-09-21)

### 7.1 2번이면 끝이다 — 프레임을 세는 게 아니라 **단계를 통과**하는 것

브라우저가 한 프레임을 처리하는 **순서는 HTML 표준에 정해져 있다.**

```
[ 한 프레임 ]
  ① rAF 콜백들을 실행한다
  ② style 계산 → layout → paint / composite
```

그래서 이렇게 된다.

| 시점 | 무슨 일 |
|---|---|
| 지금 (서버 데이터로 DOM 을 채운 직후) | DOM 에는 들어갔지만 **아직 안 그려짐** |
| **rAF #1 콜백** | 다음 프레임의 ① 자리. **아직 안 그려진 상태** |
| (같은 프레임 ②) | ← **여기서 내 화면이 그려진다** |
| **rAF #2 콜백** | 그 다음 프레임의 ① 자리. **앞 프레임의 ② 를 이미 지나왔다** |

**rAF #2 가 불렸다는 사실 자체가 「그리기 단계를 한 번 통과했다」는 증거**다.
시간이 얼마나 걸렸는지와 무관하다. 그래서 **3번·4번은 아무 정보도 더 주지 않는다** — 똑같은 사실을
한 번 더 확인할 뿐이다. 횟수를 늘리는 건 답이 아니라 **못 박기**(느린 PC 규칙 위반)가 된다.

### 7.2 PC 속도 — 안 탄다

| PC | rAF #2 가 오는 시각 | 순서 |
|---|---|---|
| 빠른 PC | 약 30ms 뒤 | ①②①② **동일** |
| 느린 PC | 약 500ms 뒤, 더 걸릴 수도 | ①②①② **동일** |

**빠르면 빨리 오고 느리면 늦게 올 뿐, 순서는 같다.** 「몇 초 뒤」로 못 박는 방식과 정반대로,
**끝난 것을 확인하고 넘어가는** 방식이다. 이게 느린 PC 규칙이 원하는 모양이다.

- 빠른 PC 쪽 부작용: busy 가 너무 짧게 떴다 사라져 **깜빡임**으로 보일 수 있다
  (기존 사례 = busy 가 서서히 나타나는 동안 짧은 busy 를 삼킨 건).
- 느린 PC 쪽 부작용: 없다. 늦게 꺼질 뿐이고, 그게 원래 의도다.

### 7.3 진짜 위험은 「횟수」가 아니라 **「거는 시점」** 이다

rAF 2번이 보장하는 범위 = **rAF 를 거는 그 순간 DOM 에 이미 들어가 있던 것**까지다.

그 뒤에 **비동기로 더 채우는 코드**가 있으면 몇 번을 돌려도 소용없다.

| 이런 코드가 있으면 | 왜 안 되나 |
|---|---|
| 그리기 함수가 `setTimeout` 으로 나머지를 이어 채움 | rAF #2 시점엔 아직 안 채워짐 |
| virtual scroller 가 프레임마다 조금씩 채움 (이 프로젝트에 다수 — 값도움·CTS·동적 목록·F4 검색도움말 등) | 프레임을 아무리 세도 끝을 모른다 |
| `<img>` · `<iframe>` · Monaco editor | 자기 완료 신호가 따로 있다 (§3) |

→ **해법은 횟수 늘리기가 아니라, 그 대상의 완료 신호를 받은 다음에 rAF 2번을 거는 것**이다.
순서: `데이터 다 채움 → (필요하면 그 컴포넌트 완료 신호 대기) → rAF ×2 → busy off`.

### 7.4 모니터 픽셀은 신경 쓰지 않는다 — **기준은 DOM** (장군님 결정 2026-09-21)

> 장군님: **「PC 사양 따라 한 프레임 더 걸릴 수 있는 건 당연하다. DOM 상에서 정확하게 다 그려진 뒤
> busy 를 끄고, 그 뒤로 MutationObserver 같은 감시장치에 안 걸리기만 하면 된다.」**

그래서 **합격 기준을 이렇게 못 박는다.**

| | |
|---|---|
| **기준** | busy 를 끈 **그 뒤로** DOM 이 더 안 바뀌면 통과 |
| **안 보는 것** | GPU·모니터에 실제 픽셀이 언제 나왔나 (사람 눈으로 구분 못 하고, 아는 API 도 없다) |

이 기준은 §7.3 의 **진짜 위험(뒤늦게 비동기로 더 채우는 코드)을 정확히 잡아낸다.**
프레임을 몇 번 셌느냐가 아니라 **결과로 판정**하는 방식이라 더 낫다.

## 8. 검증 — MutationObserver 에 안 걸리면 통과

### 8.1 왜 이게 통하나 (순서)

| 순서 | 무슨 일 |
|---|---|
| ① | 서버 데이터로 DOM 을 채운다 |
| ② | **MutationObserver 콜백** — microtask 라서 **rAF 보다 먼저** 온다. ① 의 변경은 여기서 다 소진된다 |
| ③ | rAF #1 → paint → rAF #2 |
| ④ | **busy off** |
| ⑤ | **여기서부터 감시 시작** — 잡히는 게 있으면 **늦게 채우는 코드가 있다는 증거** |

MutationObserver 는 **등록되기 전의 변경은 못 본다.** 그래서 ④ 직후에 붙이면 **자기가 끈 busy 자신의
DOM 변경도 안 잡힌다** — 이미 지나간 일이다. 우리 목적에 정확히 맞는다.

### 8.2 감시 범위 (장군님 기준 그대로)

| 볼 것 | 안 볼 것 |
|---|---|
| `childList` · `attributes` · `characterData` · `subtree` | layout·paint 결과. CSS 로 크기가 변한 것, 글꼴 로드로 줄이 밀린 것은 **DOM 변경이 아니라 안 잡힌다** |

장군님 기준이 **「DOM 상에서」** 이므로 이게 맞다. 못 잡는 게 아니라 **범위 밖**이다.

### 8.3 잡음 — 실제로 확인한 것 (조회 2026-09-21)

| 의심 | 실제 |
|---|---|
| 글꼴 아이콘이 DOM 을 바꿔치기하지 않나 | **안 한다.** 이 프로젝트는 CSS(webfont) 방식으로만 읽는다 (`index.html` 38줄 등). DOM 을 SVG 로 갈아치우는 JS 방식은 화면에서 안 쓴다 → **잡음 0** |
| 이미 도는 감시장치와 부딪치지 않나 | **안 부딪친다.** 지금 3곳뿐이고 전부 **보기만** 한다 — 팝업 열림·닫힘 감시(`ws_fn_03.js` 422줄, 대상이 팝업 영역으로 한정), 테마 class 감시(`ws10_html.js` 1472줄), 글자 폭 캐시 버리기(`theme/u4a-ui.js` 705줄) |
| 그래도 남을 잡음 | 마우스 올렸을 때 바뀌는 표시, 스크롤바, 툴팁. **검증 중에는 마우스를 화면 밖에 두면 된다** |

### 8.4 붙이는 방법 (아직 안 만들었다)

- **개발용 검증 하네스**로 붙인다. 패키징본에서는 안 돌게 막는다(기존 규칙: 테스트용 임시 코드는 가드).
- busy off 직후 감시 시작 → 잡히면 **ERROR 로그**: **무엇이**(태그·id) · **어떤 종류**(childList/attributes/…) ·
  **busy off 뒤 몇 ms 만에** 바뀌었는지. 그래야 늦게 채우는 코드를 바로 찾는다.
- 잡음 제외 목록은 **처음엔 비워 두고**, 실제로 걸린 것을 보고 판단한다. 미리 넣으면 진짜 고장을 가린다.

## 9. ★★★ 목적 — 이건 탐지기가 아니라 **완료 판정 기준**이다 (장군님 지시 2026-09-21)

> 장군님: **「busy 가 꺼지는 시점에서는 DOM 조작이 일어나지 않아야 한다」가 팩트다.**
> **「DOM 조작을 하지 말라는 게 아니다. busy 를 켜고 끄기 전까지는 얼마든지 해도 된다.
> busy 가 꺼졌는데 DOM 조작을 한다는 건 정상적인 완료로 볼 수 없고, 완료 전에 busy 를 끄는 건
> 사용자에게 혹시 모를 버그를 유발할 가능성을 품고 있으므로 이를 막으려는 것이다.」**

### 9.1 규칙 한 줄

| | |
|---|---|
| **busy ON ~ busy OFF 사이** | DOM 조작 **얼마든지 해도 된다** |
| **busy OFF 시점** | 그 처리의 DOM 조작이 **전부 끝나 있어야 한다** |
| **busy OFF 이후** | 그 처리 때문에 DOM 이 더 바뀌면 = **완료가 아닌데 완료라고 선언한 것** = 버그 씨앗 |

**왜 버그 씨앗인가**: busy 가 꺼진 순간부터 사용자는 누를 수 있다. 그런데 화면이 아직 채워지는 중이면,
**사용자는 덜 그려진 화면을 조작**하게 된다. 그 틈이 곧 「왜 가끔 이상하게 동작하지?」 의 정체다.

이건 표준 `.works/DEV_STANDARD_busy.md` §1-3 「끝점에서만 끈다」 를 **기계가 판정할 수 있게** 만든 것이다.
종전에는 사람이 소스를 읽어 「여기가 끝점이 맞나」 를 판단했다 — 이제 **결과로 증명**한다.

### 9.2 기준 — **busy 가 꺼진 이후에는 DOM 조작이 없어야 한다.** 끝 (장군님 지시 2026-09-21)

> 장군님: **「감시 구간을 사용자 첫 입력까지라고 하는 것보다, 우선 busy 가 꺼진 이후에
> DOM 조작이 없어야 하는 기준으로 해.」**

제가 냈던 「사용자 첫 입력까지로 구간을 끊자」 는 **버린다.** 기준을 복잡하게 만들지 않는다.

| | |
|---|---|
| **기준** | busy OFF 이후 DOM 조작 = **없어야 한다** |
| **감시 종료** | **다음 busy ON** (= 새 처리가 시작됨). 그때까지 잡힌 건 **전부 기록** |
| **거르기** | **안 한다.** 사용자 조작으로 생긴 것이든 독립 타이머든 **일단 다 남긴다** |

**왜 안 거르나**: 미리 거르면 진짜 위반이 같이 묻힌다. **먼저 실물로 무엇이 잡히는지 보고**,
그때 장군님께 보고해서 판단받는다. 제외 목록은 그다음이다.

참고로 이런 것도 같이 잡힐 것이다 — 마우스 올렸을 때 바뀌는 표시, 화면 아래 메시지가 10초 뒤
스스로 사라지는 것(`ws_html5_shell.js` 426줄). **그래도 지운다**. 실물을 본 뒤 판단한다.

### 9.3 위반을 찾으면 그다음

검증이 위반을 찾아내면, 그 처리의 **busy OFF 를 진짜 끝점으로 미는 수정**이 따라온다.
**수정은 별도 지시를 받고** 한다 — 이 검증 자체는 **찾아서 보고**까지다.

### 9.4 로그에 남길 것 (위반 1건마다)

- **무엇이** 바뀌었나 — 태그·id (실제 값 그대로)
- **어떤 종류** — childList / attributes / characterData
- **busy OFF 뒤 몇 ms** 만에 바뀌었나
- **어느 처리**의 busy 였나 — 그래야 어느 흐름의 끝점이 틀렸는지 안다

## 10. ★ 본론 — UI5 가 주던 렌더 완료 이벤트를 무엇으로 대신하나 (장군님 정정 2026-09-21)

> 장군님: **「이미 감시하는 프로그램은 따로 있다. 내 말은, 기존 UI5 는 DOM 이 다 그려진 이후에
> 호출해 주는 이벤트가 있었는데 지금은 그런 장치가 없으니 이걸 어떻게 할지가 고민이고 과제다.
> 실측하자는 말이 아니다.」**

### 10.1 UI5 가 주던 것의 정체

`onAfterRendering` — control 마다 있는 life cycle hook. 남의 control 에도 `addEventDelegate` 로 끼워 넣을 수 있었다.
**UI5 가 렌더링을 일괄 관리했기 때문에** 「이 control 의 DOM 을 방금 넣었다」를 프레임워크가 알려 줄 수 있었다.

HTML5 로 바꾼 영역에는 그 주체가 없다. 그리는 게 내 코드라서 **「다 그렸다」를 아는 건 내 코드뿐**이다.
실제로 변환할 때 **생략했다는 기록도 남아 있다** (`ws_html5_ws20_attr.js` 4862줄 주석).

### 10.2 ★ 원본은 그 이벤트를 **그대로 쓰지 않았다** — Promise 로 감싸 기다렸다

원본(디자인 영역) `design/js/previewRender/setOnAfterRender.js` 15줄 `setAfterRendering` 이 그것이다.

```
Promise 를 만든다
  → 대상 control 에 onAfterRendering delegate 를 끼운다
  → 불리면 delegate 를 떼고 resolve
```

부르는 쪽은 `await` 한다 — `design/js/callDesignContextMenu.js` 571~585줄:
`setAfterRendering` 으로 약속을 먼저 걸고 → 미리보기를 갱신하고 → `rerender()` 한 뒤 → **`await`**.

**여기가 핵심이다.** UI5 이벤트는 「알림」일 뿐이고, **기다릴 수 있게 만든 건 원본 개발자다.**
그러니 HTML5 에서 할 일은 **없어진 이벤트를 흉내 내는 게 아니라, 같은 약속 구조를 그대로 두는 것**이다.
바뀌는 건 **약속을 이행하는 쪽이 UI5 → 내 코드**라는 것뿐이다.

### 10.3 ★ 원본도 `onAfterRendering` 만으로는 부족했다 — 그래서 더 기다렸다

같은 파일 주석에 **원본 개발자가 직접 적어 놓았다**:

> 「미리보기 영역의 예외처리 UI에 대해 추가 waiting 처리.
> (am5 차트, richtextEditor과 같이 onAfterRendering 이후에 UI 내부에서 사용하고 있는
> 다른 라이브러리를 통해 화면이 그려지는것을 기다리는 로직)」 — 2025-01-15

실제로 추가로 기다리는 것이 세 가지다 — 글 편집기의 준비 완료 신호, 팝업이 다 열렸다는 신호, 차트 그리기 완료.

**즉 §3 에서 제가 말씀드린 「rAF 만으론 모자라니 대상별 완료 신호를 같이 기다려야 한다」 는
제 창작이 아니라, 원본이 이미 그렇게 하고 있던 것**이다. 구조를 그대로 가져오면 된다.

그리고 **미리보기 영역은 지금도 UI5 라서 이 장치가 살아 있다** — 작업 폴더에도 그대로 있다
(`design/js/previewRender/setOnAfterRender.js`). **거기는 건드릴 게 없다.**

### 10.4 그래서 HTML5 에서 만들 것 — 같은 구조, 주체만 바뀐다

| 원본(UI5) | HTML5 |
|---|---|
| UI5 가 `onAfterRendering` 을 불러 준다 | **그리는 함수가 끝에서 스스로 알린다** |
| `setAfterRendering` 이 그걸 Promise 로 감싼다 | **같은 자리에 공통 함수 하나** |
| 부르는 쪽이 `await` 한다 | **똑같이 `await`** |
| 글 편집기·차트·팝업 열림은 추가로 기다린다 | **똑같이 추가로 기다린다** (Monaco·iframe·이미지) |
| — (UI5 에 없던 것) | **끝에 rAF 2번**을 한 겹 더 얹는다 |

**rAF 2번은 원본보다 한 발 더 나간 것**이다. UI5 의 `onAfterRendering` 은 「DOM 에 넣은 직후」라
**paint 전**이다. 원본 수준만 맞추려면 rAF 없이도 되지만, 장군님 기준(§9)이 「busy 끈 뒤 DOM 조작 0」
이므로 한 겹 더 얹는 게 맞다고 봅니다.

**작업량 걱정에 대해**: 그리는 함수를 전부 고치는 게 아니다. **busy 를 끄는 자리**가 공통 함수를 부르고,
각 화면은 **기다릴 게 있을 때만 넘긴다**. 넘길 게 없으면 rAF 2번 돌고 끝난다.

### 10.5 남는 물음 (제 생각을 못 정한 것)

- 「그리는 함수가 끝에서 알린다」를 **어디까지 강제할 것인가** — 새로 쓰는 것만 규약으로 할지,
  이미 있는 화면도 훑을지. 후자면 대상 목록부터 뽑아 보고드려야 한다.

## 11. ★ 정정 — rAF 2번은 근거가 약하다. 빼는 게 맞다 (2026-09-21)

> 장군님: **「rAF 2번이 좀 찝찝한데… 왜 2번이지? 무슨 기준으로?」**

따져 보니 **제가 두 가지를 섞었습니다.** §7 에서 권한 rAF 2번을 **철회**합니다.

### 11.1 재는 것이 다르다

| | rAF 2번이 재는 것 | 장군님 기준(§9)이 재는 것 |
|---|---|---|
| | **paint 가 됐나** | **DOM 조작이 끝났나** |

DOM 조작은 **내 코드가 하는 것**이다. 내 코드가 다 끝냈으면 그 시점에 이미 기준을 채운다.
paint 가 됐는지는 **DOM 조작 여부와 아무 상관이 없다.** 다른 자를 들이댄 것이다.

### 11.2 원본은 rAF 를 판정에 안 쓴다 (조회 2026-09-21)

원본 rAF 사용 = WS3.0.0 쪽 57곳, 디자인 쪽 40곳. **전부 「다음 프레임에 무언가 하기」 용도**다.

| 곳 | 용도 | 횟수 |
|---|---|---|
| `design/js/previewRender/setOnAfterRender.js` 454줄 | 글 편집기 크기 다시 맞추기 | **1번** |
| `design/insertUIPopop/index.js` 1537줄 | 화면 나누는 막대 크기 동기화 한 번 더 | **1번** |

**원본 어디에도 rAF 를 겹쳐 「다 그려졌나」 를 판정하는 코드는 없다.**
판정은 언제나 `onAfterRendering` Promise 로 한다(§10.2). **rAF 2번은 원본에 없는 제 창작이었다.**

### 11.3 그래도 rAF 가 필요해 보였던 이유 — 그리고 그것도 안 통한다

유일한 실질 근거는 **다른 코드가 rAF 로 예약해 둔 DOM 조작을 흡수하는 것**이었다.
작업 폴더에 rAF 30곳이 있으니 실재하는 문제다 — busy 를 그냥 끄면 그 예약된 조작이 **busy OFF 뒤에** 돈다.

**그런데 2번으로도 못 막는다.** rAF 콜백은 **등록 순서대로** 돈다. 내 rAF #1 콜백 안에서
누군가 rAF 를 또 걸면, 그건 내 rAF #2 **보다 뒤에** 등록되어 **busy 를 끈 다음에 실행된다.**
→ 3번으로 늘려도 같은 일이 반복된다. **횟수로 푸는 문제가 아니다.**

### 11.4 결론 — 근본은 §10 하나다

**rAF 는 빼고, 「그리는 쪽이 끝에서 알린다」 로만 간다.** 원본이 하던 그대로다.

rAF 로 예약해 둔 조작도 **같은 원칙으로 푼다** — 예약하는 쪽이 **그 예약이 끝났음을 알려 주면 된다.**
「몇 프레임 기다리면 되겠지」 가 아니라 **끝났다는 것을 받는다.**

이건 느린 PC 규칙(「N초 뒤에 하면 되겠지」 금지, 끝난 것을 확인하고 넘어가라)과도 같은 말이다.
**rAF 횟수 못 박기 = 프레임판 「N초 뒤」** 였다.
