# busy 를 언제 끄나 — 기준 · 설계 · 검증 (한 파일)

> 장군님 지시 2026-09-21 ~ **2026-10-19 통합**(「md 파일 하나로 합쳐서 정리해, 너무 산재되어 있어서」).
> 종전 세 파일(08 DOM 다그려진뒤 / 09 렌더완료 아키텍처 / 10 렌더완료 정의)을 **이 파일로 합쳤다. 그 세 파일은 지웠다.**
> 코드는 아직 **한 줄도 안 고쳤다.** 적용은 장군님 결정 뒤(§10).

## 1. 한 장 요약

```
[조회 버튼]
    │
    ├─ setBusy("X")                 ← 시작 맨 위. 지금과 똑같음 (손 안 댐)
    │
    ├─ 서버 호출 ─────────────► 응답 콜백
    │                               │
    │                        await 화면그리기()      ← ★ 바뀌는 것: await 한 글자
    │                               │
    │                   ┌───────────┴───────────┐
    │                   │ DOM 채우기 = 동기      │  return 하면 그걸로 완료.
    │                   │ (물어볼 대상이 없다)   │  완료 이벤트 장치 안 만든다
    │                   └───────────┬───────────┘
    │                               │
    │                   기다릴 게 있을 때만 그것만 await  (§4 의 5자리)
    │                               │
    └─ setBusy("")              ← 자리 그대로. 앞에 await 가 붙은 것뿐
            │
            └─[합격 판정] 이 뒤로 DOM 이 바뀌면 위반 → ERROR 로그
                           감시 끝 = 다음 setBusy("X")
```

| | |
|---|---|
| **한 줄 전략** | `setBusy("")` **자리는 그대로**, 그 앞 그리기 호출에 **`await`** 를 붙인다 |
| **합격 기준** | busy 끈 뒤 **DOM 조작 0** |
| **안 하는 것** | `rAF` 횟수로 판정(§7) · 「몇 초 기다리다 포기」 · busy 끄는 새 공통 함수 |

## 2. 기준 — 장군님 말씀 그대로 (2026-09-21)

> 「DOM 조작을 하지 말라는 게 아니다. busy 를 켜고 끄기 전까지는 얼마든지 해도 된다.
> busy 가 꺼졌는데 DOM 조작을 한다는 건 정상적인 완료로 볼 수 없고, 완료 전에 busy 를 끄는 건
> 사용자에게 혹시 모를 버그를 유발할 가능성을 품고 있으므로 이를 막으려는 것이다.」

> 「PC 사양 따라 한 프레임 더 걸릴 수 있는 건 당연하다. **DOM 상에서** 정확하게 다 그려진 뒤
> busy 를 끄고, 그 뒤로 MutationObserver 같은 감시장치에 안 걸리기만 하면 된다.」

| 구간 | 규칙 |
|---|---|
| busy ON ~ OFF 사이 | DOM 조작 **얼마든지 해도 된다** |
| busy **OFF 시점** | 그 처리의 DOM 조작이 **전부 끝나 있어야 한다** |
| busy OFF **이후** | 그 처리 때문에 DOM 이 바뀌면 = **완료가 아닌데 완료라고 선언한 것** |

**왜 버그 씨앗인가**: busy 가 꺼진 순간부터 사용자는 누를 수 있다. 화면이 아직 채워지는 중이면
**덜 그려진 화면을 조작**하게 된다. 그 틈이 「왜 가끔 이상하게 동작하지?」 의 정체다.

**안 보는 것**: 모니터에 픽셀이 언제 나왔나(사람 눈으로 못 보고 아는 API 도 없다) ·
layout·paint 결과(CSS 로 크기 변한 것, 글꼴 로드로 줄 밀린 것은 DOM 변경이 아니라 **범위 밖**).

### 2.1 지금 실물 — 끝나서 끄는 게 아니다 (조회 2026-09-21)

어플리케이션 복사 팝업 `js/fnAppCopyPopupOpen.js` 253~297줄:

```
busy ON → 서버 호출 → 응답 콜백 ─ 팝업 닫기
                              └ 서버가 준 SCRIPT 실행 (화면 전환까지 일어난다)
                   busy OFF   ← 여기
```

그 소스 주석에 **「화면전환/CTS 팝업이 busy 가드에 막히지 않게 먼저 해제」** 라고 적혀 있다 —
**끝나서 끄는 게 아니라, 다음 동작을 통과시키려고 미리 끄고 있다.** `busy OFF` 가
「그리기가 끝난 자리」가 아니라 **그냥 코드 줄 순서상 거기**다.
(※ 이 파일을 지금 고치자는 말이 아니다 — 실물 예시다.)

## 3. 완료의 정의 — HTML5 는 물어볼 것이 없다

```
element.appendChild(child);   ← 이 줄이 끝나면 DOM 에 들어가 있다. 끝.
element.innerHTML = "...";    ← 마찬가지
```

> **그리는 함수가 `return` 한 시점 = 그리기 완료.**

- **확인함(조회 2026-09-21)**: 이 프로젝트의 공통 그리기 부품(`tree`·`table`·입력칸 생성)은
  `theme/u4a-ui.js` 안에 있고 **그 파일 전체에 `async` 가 0건** — 전부 동기다.
- **UI5 가 완료 이벤트(`onAfterRendering`)를 준 이유는 UI5 의 그리기가 비동기였기 때문**이다.
  control 을 고치면 즉시 안 그리고 표시만 해 두었다(invalidate) → 그래서 물어봐야 했다.
- HTML5 는 그리는 주체가 **내 코드**다. **그 이벤트를 흉내 낼 이유가 없다.**
- ※ **미리보기 영역은 아직 UI5** 라 원본 장치(`design/js/previewRender/setOnAfterRender.js`)가
  지금도 돈다 — **거기는 건드리지 않는다.**

## 4. ★ 기다려야 하는 자리 — 비동기가 섞일 때만, 5가지로 유한하다

| # | 자리 | 완료 신호 | 상태 |
|---|---|---|---|
| 1 | 서버를 **또** 다녀온다 | 응답 콜백 | 이미 있다 |
| 2 | `iframe` 을 읽는다 | 읽기 완료 신호 | 이미 있다 |
| 3 | 그림 파일을 읽는다 | 읽기 완료 신호 | 이미 있다 |
| 4 | 남의 라이브러리가 스스로 그린다(글 편집기·차트) | 그 라이브러리 신호 | **확인 필요** |
| 5 | **내 코드가 뒤로 미뤄 놨다**(`setTimeout`·`rAF`) | **없다** | **★ 진짜 문제** |

**이 5가지 말고 HTML5 에서 「나중에 그려지는」 일은 없다.**

### 4.1 5번 — 실측 건수 (`js/` 안, 조회 2026-09-21)

| | 건수 |
|---|---|
| `setTimeout` | **55** (지연 0 = 32곳은 순서 보장돼 안전 / 0 이 아닌 값 = 약 19곳이 위험 후보) |
| `requestAnimationFrame` | **25** |

→ 이 **80곳**이 「지금 안 하고 나중에 한다」고 예약해 둔 자리다. 그중 **DOM 을 건드리는 것**이
busy 를 끈 뒤에 돌면 곧 위반이다. **답은 세 가지뿐**:

| 답 | 내용 |
|---|---|
| ① 안 미룬다 | 미룰 이유가 없으면 그 자리에서 한다. **가장 좋은 답** |
| ② 끝났음을 알린다 | 꼭 미뤄야 하면(레이아웃 계산 등) 그 예약이 **약속을 돌려주게** 한다 |
| ③ busy 밖으로 뺀다 | 그 처리와 상관없는 일(뒷정리 등)이면 애초에 그 처리 안에 두지 않는다 |

**①·③ 이 대부분이고 ② 는 정말 필요한 곳만**이라고 봅니다.
※ 19곳이 전부 위반은 아니다 — **기다림 대용이 아니라 기능**인 것이 섞여 있다(예: 화면 아래 메시지가
10초 뒤 스스로 사라지는 것). 하나씩 봐야 갈린다.

## 5. 코드가 어떻게 바뀌나 · 무엇을 만드나

```
[ 지금 ]                          [ 바뀐 뒤 ]
화면그리기();                      await 화면그리기();      ← await 한 글자
setBusy("");                      setBusy("");            ← 그대로. 안 건드린다
```

```
function 화면그리기() {
    ... DOM 채우기 ...                       ← 동기. 여기서 끝나면 완료
    return 대기도우미.그림읽기완료(이미지들);   ← 기다릴 게 있을 때만 이 한 줄
}
```

| | |
|---|---|
| **만든다** | **대기 도우미 파일 1개** — 그림·`iframe`·글 편집기처럼 기다리는 방법이 같은 것들을 묶는다. (원본도 이 모양 — `setOnAfterRender.js` 한 파일에 대기 함수가 여러 개 들어 있다) |
| **만든다** | **위반 감시**(§6) — 개발용. 패키징본에선 안 돌게 가드(`app.isPackaged`) |
| **안 만든다** | busy 끄는 새 공통 함수 · 렌더 완료 이벤트 장치 · `rAF` 횟수 판정 · 타임아웃 폴백 |
| **손 안 댄다** | `setBusy` 공통 통로(`www/ws30/resources/index.js` 1678줄)와 그 래퍼들 · 끄는 자리 630곳 |

**`await` 를 어디에 붙이나** — 호출처마다(제 권고) vs `setBusy` 공통 통로 한 곳. 손대는 **화면 수는 같고**,
공통 통로에 두면 **등록해 놓고 안 풀 때 다른 화면 busy 까지** 못 끄게 된다. 그래서 호출처가 안전하다.

## 6. 검증 — MutationObserver 에 안 걸리면 통과

| 순서 | 무슨 일 |
|---|---|
| ① | 데이터로 DOM 을 채운다 |
| ② | MutationObserver 콜백 — microtask 라서 ① 의 변경은 여기서 다 소진된다 |
| ③ | **busy OFF** |
| ④ | **여기서부터 감시 시작** — 잡히면 **늦게 채우는 코드가 있다는 증거** |

- MutationObserver 는 **등록 전의 변경은 못 본다** → busy OFF 직후에 붙이면 자기가 끈 busy 의 변경도 안 잡힌다.
- 보는 것 = `childList` · `attributes` · `characterData` · `subtree`. **감시 종료 = 다음 busy ON.**
- **거르지 않는다.** 사용자 조작이든 독립 타이머든 **일단 다 남긴다** — 미리 거르면 진짜 위반이 묻힌다.
  실물을 본 뒤 장군님께 보고해 판단받는다.
- **위반 1건마다 남길 것**(ERROR 로그, 영어): 무엇이(태그·id) · 어떤 종류 · busy OFF 뒤 몇 ms ·
  **어느 처리**의 busy 였나.

**잡음 — 실제로 확인한 것(조회 2026-09-21)**: 글꼴 아이콘은 CSS(webfont) 방식만 써서 DOM 을 안 바꾼다(잡음 0) ·
지금 도는 감시장치 3곳은 전부 **보기만** 한다(팝업 열림·닫힘 `ws_fn_03.js` 422줄 / 테마 class `ws10_html.js` 1472줄 /
글자 폭 캐시 `theme/u4a-ui.js` 705줄) · 남을 잡음은 마우스 올렸을 때 바뀌는 표시·스크롤바·툴팁 →
**검증 중에는 마우스를 화면 밖에 둔다.**

## 7. ★★ 또 밟을 함정 — `rAF` 횟수로 판정하지 마라

**처음 판에서 내가 「`rAF` 2번 겹치면 paint 끝난 뒤」라고 권했다. 장군님 「왜 2번이지? 무슨 기준으로?」
→ 철회했다.** 세 가지가 틀렸다.

| # | 왜 틀렸나 |
|---|---|
| 1 | **재는 것이 다르다** — `rAF` 는 **paint 가 됐나**를 재고, 기준(§2)은 **DOM 조작이 끝났나**를 본다. 다른 자다 |
| 2 | **원본에 없다** — 원본 `rAF` 97곳(WS3.0.0 57 · 디자인 40) 전부 「다음 프레임에 무언가 하기」 용도로 **1번씩**. 판정은 언제나 `onAfterRendering` Promise 로 한다 |
| 3 | **2번으로 막지도 못한다** — `rAF` 콜백은 등록 순서대로 돈다. 내 1번째 콜백 안에서 누가 `rAF` 를 또 걸면 그건 내 2번째 **뒤에** 등록돼 **busy 를 끈 다음에** 실행된다. 3번으로 늘려도 같다 |

**`rAF` 횟수 못 박기 = 프레임판 「N초 뒤」** 다 — 느린 PC 규칙 위반이다.

> ⚠ **2026-10-19 에 내가 또 같은 안을 냈다**(「끄는 함수 안에서 `rAF` → `setTimeout 0` 뒤에 끄자」).
> 이 문서를 먼저 찾아보지 않은 탓이다. **busy 끄는 시점을 다룰 때는 이 §7 을 먼저 읽는다.**

## 8. 느린 PC · 새로 생기는 위험

| | |
|---|---|
| **이 설계가 강한 이유** | **시간을 안 본다.** 동기 실행의 순서 보장에만 기댄다 — 느린 PC 는 그 함수가 **오래 걸릴 뿐**, `return` 했으면 DOM 에 들어가 있다. 빠른 PC 와 결과가 같다 |
| 1~3 (서버·`iframe`·그림) | 늦어질 뿐 **순서가 안 바뀐다.** 실패 신호도 있다 (서버는 실패 콜백을 **안 넘기면 안 온다** — 기존 규칙) |
| **4 (남의 라이브러리)** | **신호가 아예 안 올 수 있다 → busy 가 영영 안 꺼진다.** 그래서 **신호가 오는지 확인된 것만** 기다린다. 확인 안 된 것은 지금처럼 둔다 |
| 여러 비동기가 섞이면 | 완료 **순서가 PC 마다 다르다.** 「A 가 끝났으니 B 도 끝났겠지」 금지 — **전부 모아서** 기다린다 |
| 기다리는 중에 화면이 사라지면 | 그 약속은 영영 안 끝난다 → **대상이 아직 화면에 있는지 확인하는 갈래**가 필요하다. 없어졌으면 기다림을 접고 busy 를 끈다(로그 남기고) |
| **종전과 달라지는 것** | 지금은 「일단 끄고 본다」라서 **busy 가 안 꺼지는 고장이 없다.** 기다리게 만들면 **생긴다** |

## 9. 규모 · 할 순서 · 적용 전 숙제

| 세어 본 것 | 수 |
|---|---|
| busy 켜는 호출 `setBusy("X")` (`www` 전체, 2026-10-19) | **217곳** |
| busy 끄는 호출 `setBusy("")` (`www` 전체, 2026-10-19) | **630곳** (`js/` 안만 세면 359곳) |
| 그중 **실제 대상**(서버 다녀와서 화면을 그리는 것) | **아직 안 셌다** — 팝업 닫기·취소·오류 종료처럼 그릴 게 없는 곳이 많다 |

**할 순서**
1. **5번 80곳**을 ①안 미룬다 / ②알린다 / ③밖으로 로 가른 **목록**을 만든다
2. 1~4 의 **기다리는 방법**을 확정한다 (4번은 신호가 오는지 확인된 것만)
3. **감시를 켜고, 실제로 걸린 화면부터 한 화면씩** 고친다 — 630곳을 다 훑지 않는다

**적용 전 숙제 — 이게 안 끝나면 적용하면 안 된다**
- ① 남의 라이브러리가 **정말 끝 신호를 주는지** 하나씩 확인 (안 주면 안 기다린다)
- ② 시간 못 박은 **19곳**을 「기다림 대용 / 기능」 으로 가른다
- ③ 모든 기다림에 **실패 갈래 · 대상 소멸 갈래**를 둔다

**위험**: 한꺼번에 하면 되돌리기 어렵다 → **한 화면씩, 그 화면 테스트를 통과한 뒤 다음**으로.
`async` 가 어디까지 번지는지는 **목록을 뽑아 봐야 안다.**
