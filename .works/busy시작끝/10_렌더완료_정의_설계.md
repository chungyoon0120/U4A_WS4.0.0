# 「화면 렌더링 완료」를 무엇으로 정의할 것인가 — HTML5 기준 아키텍처

> 2026-09-21 · 장군님 지시 2건이 이 문서의 전제다.
>
> ① **「설계가 안 됐는데 적용 위치부터 조사하는 게 순서상 맞느냐」** → 맞지 않다. 이 문서가 먼저다.
> ② **「전체 프로그램 아키텍처가 완전히 달라졌다는 걸 반드시 머리에 박아라. 기존은 UI5 기반이라
> API 가 있었던 거고, 지금은 순수 HTML5 로 컨버전하는 거니 그런 API 가 없는데 기능을 만들어야
> 하니까 방법을 찾는 거다.」** → **원본 흉내가 아니라 HTML5 의 성질에서 답을 낸다.**
>
> **소스로만 조사. 코드는 한 줄도 안 고쳤다.**

---

## 1. 정해 주실 것

| # | 물음 | 제 생각 |
|---|---|---|
| 1 | **「완료 신호 장치」를 만들 것인가** | **안 만듭니다.** HTML5 에서 DOM 그리기는 **동기**라 **함수가 return 한 시점이 곧 완료**입니다 (§3). 물어볼 대상 자체가 없습니다 |
| 2 | 그럼 무엇을 만드나 | **비동기가 섞인 자리를 빠짐없이 기다리는 것**뿐입니다. 그 자리는 **5가지로 유한**합니다 (§4) |
| 3 | 그중 진짜 문제는 | **5번 「내 코드가 뒤로 미뤄 놓은 것」** 입니다 (§5). 나머지 4가지는 각자 완료 신호가 이미 있습니다 |

---

## 2. UI5 가 그 API 를 줬던 진짜 이유

**UI5 의 그리기는 비동기였다.** control 을 고치면 즉시 안 그린다 — **표시만 해 두고(invalidate)
나중에 렌더 큐가 돈다.** 그리는 주체가 내 코드가 아니라 프레임워크였다.

**그래서 「언제 끝나나」를 물어봐야 했고, 그래서 UI5 가 그 API 를 줬다.**

---

## 3. ★ HTML5 는 **물어볼 것이 없다**

```
element.appendChild(child);   ← 이 줄이 끝나면 DOM 에 들어가 있다. 끝.
element.innerHTML = "...";    ← 마찬가지
```

**HTML5 에서 DOM 조작은 동기다.** 미뤄지지 않는다. 그리는 주체가 **내 코드**다.

**확인했다 (조회 2026-09-21)**: 이 프로젝트의 공통 그리기 부품(tree·table·입력칸을 만드는 것들)은
`theme/u4a-ui.js` 안에 있고, **그 파일 전체에 `async` 가 0건**이다 — **전부 동기**다.

### 3.1 그래서 완료의 정의는 이것이다

> **그리는 함수가 return 한 시점 = 그리기 완료.**

**새로 만들 개념이 아니다.** UI5 의 완료 이벤트를 흉내 낼 이유도 없다 —
그건 **비동기라서 필요했던 것**이고, HTML5 는 비동기가 아니다.

---

## 4. ★ 그럼 문제는 어디서 생기나 — **비동기가 섞일 때만**, 그리고 그 자리는 유한하다

| # | 비동기가 섞이는 자리 | 완료 신호 | 상태 |
|---|---|---|---|
| 1 | **서버를 (또) 다녀온다** | 응답 콜백 | 이미 있다 |
| 2 | **안쪽 화면(iframe)을 읽는다** | 읽기 완료 신호 | 이미 있다 |
| 3 | **그림 파일을 읽는다** | 읽기 완료 신호 | 이미 있다 |
| 4 | **남의 라이브러리가 스스로 그린다** (글 편집기·차트) | 그 라이브러리가 주는 신호 | 이미 있다 |
| 5 | **내 코드가 뒤로 미뤄 놨다** (`setTimeout` · `requestAnimationFrame`) | **없다** | **★ 진짜 문제** |

**이 5가지 말고 HTML5 에서 「나중에 그려지는」 일은 없다.**

1~4 는 **각자 완료 신호가 이미 있으므로** 그것을 기다리면 된다 — 새 장치가 필요 없다.

---

## 5. ★ 진짜 문제는 5번 — 「뒤로 미뤄 놓기」

### 5.1 실제 건수 (내 파일 `js/` 안, 조회 2026-09-21)

| | 건수 |
|---|---|
| `setTimeout` | **55** |
| `requestAnimationFrame` | **25** |
| `async` 붙은 함수 | 113 |

이 80곳(55+25)이 **「지금 안 하고 나중에 한다」** 고 예약해 둔 자리다.
그중 **DOM 을 건드리는 것**이 busy 를 끈 뒤에 돌면 곧 위반이다.

### 5.2 이게 UI5 때는 안 보였던 이유

UI5 때도 이런 예약은 있었다. **하지만 UI5 가 그리기를 일괄 관리하니 대부분 프레임워크 안으로
들어갔다.** HTML5 로 오면서 **그 일을 내 코드가 직접 하게 되었고, 예약도 내 코드에 드러났다.**

### 5.3 답 — 세 가지뿐이다

| 답 | 내용 |
|---|---|
| **① 안 미룬다** | 미룰 이유가 없으면 그 자리에서 한다. **가장 좋은 답** |
| **② 미룬 것이 끝났음을 알린다** | 꼭 미뤄야 하면(레이아웃 계산 등), 그 예약이 **약속을 돌려주게** 한다 |
| **③ 미루는 것을 busy 밖으로 뺀다** | 그 처리와 상관없는 일이면(뒷정리 등) 애초에 그 처리 안에 두지 않는다 |

**①·③ 이 대부분이고, ② 는 정말 필요한 곳만**이라고 봅니다.

---

## 6. 정리 — HTML5 아키텍처에서의 답

| 질문 | 답 |
|---|---|
| 완료 신호 장치를 만드나 | **아니다.** HTML5 그리기는 동기 — **함수 return 이 곧 완료** |
| UI5 의 그 API 를 흉내 내나 | **아니다.** 그건 **UI5 가 비동기였기 때문에** 필요했던 것 |
| 그럼 무엇을 하나 | **비동기가 섞인 5자리를 빠짐없이 기다린다.** 1~4 는 신호가 이미 있고, **5번만 새로 다룬다** |
| 5번은 어떻게 | **안 미루거나 / 끝났음을 알리거나 / 밖으로 뺀다** |

**즉 「새 장치」 가 아니라 「규약」 이다.**
HTML5 가 오히려 단순하다 — **프레임워크가 뒤에서 뭘 하는지 몰라 물어봐야 했던 게 UI5 고,
지금은 전부 내가 쓴 코드다.**

## 9. ★★ 느린 PC · 시점 차이 검증 (장군님 지시 2026-09-21)

> 장군님: **「느린 PC, 시점 차 고려 좃도 안 하고 제안했다가는 욕만 10시간 먹을 줄 알아라.」**

제안을 내기 전에 **제가 먼저 따졌다.** 아래가 그 결과다.

### 9.1 ★ 이 설계의 핵심 강점 — **시간에 의존하지 않는다**

> **「그리는 함수가 return 한 시점 = 완료」는 PC 속도와 무관하게 성립한다.**

동기 실행은 **순서가 언어 차원에서 보장**된다. 느린 PC 는 그 함수가 **오래 걸릴 뿐**,
return 했으면 DOM 에 들어가 있다. **빠른 PC 와 결과가 같다.**

| | 못 박기 방식 (제가 냈다가 철회한 것) | 이 설계 |
|---|---|---|
| 「N초 뒤」 · 「rAF 2번」 | **느린 PC 에서 깨진다** | — |
| 「함수가 return 했나」 | — | **안 깨진다.** 시간을 안 본다 |

### 9.2 비동기 5자리 — 느린 PC 에서 무엇이 달라지나

| # | 자리 | 느린 PC 에서 | 순서 뒤집히나 | 실패 신호 있나 |
|---|---|---|---|---|
| 1 | 서버 재호출 | 응답이 늦게 온다 | **아니오** | **있다** — 통신 실패 콜백. **단 안 넘기면 안 온다**(기존 규칙) |
| 2 | 안쪽 화면(iframe) | 늦게 끝난다 | **아니오** | **있다** — 읽기 오류 |
| 3 | 그림 파일 | 늦게 끝난다 | **아니오** | **있다** — 읽기 오류 |
| 4 | 남의 라이브러리 | 늦게 끝난다 | **아니오** | **★ 확인 필요** — 라이브러리마다 다르다 |
| 5 | 뒤로 미뤄 놓기 | **§9.4 참조** | **★ 못 박은 것은 뒤집힌다** | 만들 수 있다 |

**1~3 은 느린 PC 에서 늦어질 뿐 순서가 안 바뀐다.** 위험은 4·5 다.

### 9.3 ★ 새로 생기는 위험 — **busy 가 안 꺼진다** (느린 PC 에서 더 자주)

지금은 **「일단 끄고 본다」** 라서 이 고장이 **없다.** 기다리게 만들면 **생긴다.**

| 기다리는 대상 | 신호가 안 오면 |
|---|---|
| 1~3 | 실패 신호가 오므로 **끌 수 있다** |
| **4 (남의 라이브러리)** | **신호가 아예 안 올 수 있다** → **영영 안 꺼진다** |

→ **4번은 라이브러리마다 「끝났다는 신호가 실제로 오는지」 를 하나씩 확인해야 한다.**
확인 안 된 것은 **기다리지 않는다**(지금처럼 둔다). **확인된 것만 기다린다.**

**「몇 초 기다리다 포기」 는 쓰지 않는다** — 그게 곧 느린 PC 에서 깨지는 못 박기다.

### 9.4 ★ 시간을 못 박아 둔 자리 — 실측 (`js/` 안, 조회 2026-09-21)

| 지연 | 곳 |
|---|---|
| **0** (다음 차례로 미루기) | **32곳** — PC 속도 무관, **순서 보장됨. 안전** |
| **0 이 아닌 값** (10 · 120 · 200 · 250 · 300 · 400 · 500 · 600 · 1000 · 2000 · 3000 · 8000 · 10000) | **약 19곳** — **느린 PC 에서 깨질 후보** |

※ 여러 줄에 걸친 것까지 세었으나 **형태가 특이한 것은 놓쳤을 수 있다. 정확한 수는 하나씩 봐야 한다.**

**단, 19곳이 전부 위반은 아니다.** 그중에는 **기다림 대용이 아니라 기능**인 것이 섞여 있다 —
예: 화면 아래 메시지가 10초 뒤 스스로 사라지는 것. **하나씩 봐야 갈린다.**

### 9.5 ★ 시점 차이 — 「A 가 끝났으니 B 도 끝났겠지」 금지

여러 비동기가 섞이면 **완료 순서가 PC 마다 다르다.** 빠른 PC 에서 서버 응답이 먼저 오던 것이
느린 PC 에서는 그림 읽기가 먼저 끝날 수 있다.

→ **하나를 보고 다른 것을 가정하지 않는다. 전부 모아서 기다린다.**
이건 「몇 개 기다리는지」 만 맞으면 순서와 무관하게 성립한다.

### 9.6 기다리는 중에 화면이 사라지면

느린 PC 는 **기다리는 시간이 길다** → 그 사이에 사용자가 창을 닫거나 다른 화면으로 갈 확률이 **올라간다.**
그러면 그 약속은 영영 안 끝난다.

→ **기다리는 대상이 아직 화면에 있는지 확인하는 갈래가 필요하다.**
없어졌으면 **기다림을 접고 busy 를 끈다**(로그 남기고).

### 9.7 결론 — 이 설계가 느린 PC 에 강한 이유와, 남은 숙제

| | |
|---|---|
| **강한 이유** | 시간을 안 본다. **동기 실행의 순서 보장**에만 기댄다 |
| **숙제 ①** | 남의 라이브러리가 **정말 끝났다는 신호를 주는지** 하나씩 확인 (안 주면 기다리지 않는다) |
| **숙제 ②** | 시간 못 박은 **19곳**을 「기다림 대용 / 기능」 으로 가른다 |
| **숙제 ③** | 모든 기다림에 **실패·대상 소멸 갈래**를 둔다 (없으면 busy 가 영영 안 꺼진다) |

**숙제 ①③ 이 안 끝나면 이 설계는 적용하면 안 된다** — 느린 PC 에서 busy 가 안 꺼지는 고장이
지금보다 나쁘다.
