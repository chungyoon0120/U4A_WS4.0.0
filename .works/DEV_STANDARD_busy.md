# 개발 표준 — busy: 시작에 켜고, 중간에 안 끄고, 끝에서만 끈다

> **장군님 지시 (2026-09-15)** — 이 문서의 조항은 **어떤 편의·판단보다 위**다.
>
> > 모든 로직에는 시작과 끝은 있을거야. 시작로직에 busy 키고 처리할 꺼 다 처리 할때까지는 중간에 busy를 끄는 로직이 없어야하고.. 최종적으로 로직이 완료 되면 busy 끄는게 이게 그렇게 어려워?
> > 새창 흐름에만 넣는게 아니고 모든 로직에서는 어떤 처리 과정 중에 조작을 하지 못하게 우선 막고 시작해 제발

---

## 1. ★★★ 절대 규칙

| # | 규칙 |
|---|---|
| 1 | **모든 처리 로직은 시작점 맨 위 첫 줄에서 busy 를 켠다.** 새창·팝업·서버 호출·저장만이 아니다 — 버튼 하나 눌러 도는 처리도 전부 |
| 2 | **시작점부터 끝점까지 사이에 busy 를 끄는 코드가 하나도 없어야 한다.** 그 사이에 불리는 함수 안에 있어도 **중간 해제**다 |
| 3 | **끝점에서만 끈다.** 끝점 = 성공 완료 · 실패로 끝나는 갈래 · 조기 return 갈래 **전부**. 하나라도 빠지면 busy 가 안 풀린다 |
| 4 | **타이머로 끄지 않는다**(`.analy/16` §2.11 계열 기존 금지 그대로). 안 풀리면 빠진 끝점을 찾는다 |
| 5 | 겹치는 처리는 **깊이(개수)를 세어** 0 일 때만 실제로 끈다(기존 규칙 그대로) |

---

## 2. 순서 — 증상 자리부터 고치지 마라

| 단계 | 할 것 | 하지 말 것 |
|---|---|---|
| ① | 그 처리의 **시작점**을 소스로 찾는다 — 사용자가 누른 버튼의 핸들러, 창이 뜨면 처음 불리는 처리 | 「검은 화면이 보이는 자리」「창을 보이게 하는 줄」 같은 **증상 자리**에 busy 넣기 |
| ② | 그 처리의 **끝점을 전부** 찾는다 — 성공 끝, catch, 조기 return, 실패 콜백 | 성공 끝 하나만 보고 끝내기 |
| ③ | 시작~끝 사이에 불리는 함수를 따라가며 **busy 끄는 코드**를 찾는다 | 이름만 보고 "안 끄겠지" 로 넘기기 |
| ④ | 시작점 첫 줄 켜기 · 중간 해제 제거 · 끝점마다 끄기 | 중간 해제를 남긴 채 끝점에 하나 더 넣기 |
| ⑤ | 로그: 끝점 중 **실패·조기 return** 갈래는 무엇 때문에 끝났는지 남긴다(`.works/DEV_STANDARD_로그.md`) | 조용히 끄고 끝내기 |

## 3. 실제 사고 — 이렇게 하지 마라

| 날짜 | 무엇 | 잘못 |
|---|---|---|
| 2026-09-14 | 「새창 띄우면 busy 없이 검은 화면」 | 창 첫 화면 초기 처리에 busy 를 넣었다 — **로그인 후 새창은 그 경로를 안 지난다.** 흐름을 확인 안 했다 |
| 2026-09-15 | 같은 증상 재발 | 창을 보이게 하는 **줄 바로 앞**(증상 자리)에 넣었다. 시작점이 아니다 |
| 2026-09-15 | 같은 흐름 | 흐름 **중간**(첫 화면 본문 그리기)에 busy 를 끄는 코드가 있었는데 못 봤다. 끝점 중 **조기 return 갈래**는 busy 를 안 끄고 있었다(중간 해제에 가려져 있었다) |

고친 결과(새창 흐름): 시작 = 창 문서의 메타 정보 수신 맨 위 / 중간 해제 제거 = 첫 화면 본문 그리기 / 끝 = 메인 본문 등장 완료 · 조기 return · 실패 catch.
