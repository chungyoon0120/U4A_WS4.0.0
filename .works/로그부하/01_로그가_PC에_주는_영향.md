# 로그가 PC 에 주는 영향 — 실측

> 2026-09-16 · 장군님 물음 「busy 뿐 아니라 다른 각종 이벤트에서도 로그를 남기는데 PC 에 영향은 없을까?」
> 소스 + **실제 로그 파일 실측**으로 확인. **코드는 한 줄도 안 고쳤다.**

---

## 1. 정해 주실 것 (제 생각 먼저)

| 물음 | 제 생각 |
|---|---|
| **같은 줄 하나가 로그의 93% 를 차지하고 있다**(§2). 이걸 줄일까 | **줄인다.** 데이터 감시 도구가 조작할 때마다 「이 model 에는 oData 가 없다」를 매번 남긴다. 같은 자리·같은 내용이라 두 번째부터는 새 정보가 0 이다 — 로그 표준 §5 V1·V5 위반이다. 남이 만든 라이브러리가 아니라 우리 파일이다 |
| 로그 파일 쓰기를 **비동기로 바꿀까** | **지금은 바꾸지 말자** — 장군님 물음(순서가 바뀔 소지)을 확인해 보니 **창 사이 순서가 뒤바뀔 수 있다**(§6). 위 반복 줄만 줄여도 부하의 93% 가 빠진다. 그것부터 하고 **다시 실측한 뒤에** 판단하는 것이 맞다고 본다. (앞서 「바꾸는 쪽이 맞다」고 적었던 것을 이 근거로 뒤집는다) |
| busy 로그를 넣어도 되나 | **된다.** 처리 1건당 1줄이라 분당 몇 줄이다(§4). 지금 부하의 주범은 busy 가 아니라 위 두 가지다 |

## 2. 실측 — 로그의 93% 가 같은 줄 하나

포장한 앱이 실제로 남긴 파일을 셌다 (`%APPDATA%\com.u4a_ws3.app\logs\U4A_WS_2026_9_11.old.log`, 조회 2026-09-16).

| 항목 | 값 |
|---|---|
| 줄 수 | 9,290 줄 |
| 시간 폭 | 15:32 ~ 19:26 (3시간 54분) |
| 파일 크기 | 1.0 MB |
| 분당 | 약 40 줄 |
| **같은 줄 하나** (데이터 감시 도구의 「이 model 에는 oData 가 없다」 경고) | **8,686 줄 = 전체의 93%** |
| 그 줄을 뺀 나머지 | 604 줄 = 분당 약 2.6 줄 |

그 줄은 `www/ws30/ws10_20/js/ws_html5_datamon.js` 232줄이다. 사용자가 조작할 때마다 상태를 담는데(635줄에서 조작 이벤트에 걸어 둠), 담을 때마다 oData 없는 model 마다 한 줄씩 남긴다.
**포장한 앱에서 돌고 있다** — 이 파일에는 포장본에서 꺼지는 가드가 없다(검색 0건).

## 3. 줄 하나가 얼마나 비싼가 — 동기 디스크 쓰기

| 사실 | 근거 |
|---|---|
| 화면 쪽 `console.log`·`warn`·`error` 가 **통째로 로그 함수로 바뀌어 있다** | `www/ws30/ws10_20/js/ws_log.js` 153줄 |
| 로그 라이브러리(electron-log 4.4.8)는 **기본이 동기 쓰기**다 — 줄마다 `writeFileSync` | `node_modules/electron-log/src/transports/file/index.js` 37줄 `sync = true` · `file.js` 140줄 |
| 우리 코드에서 이 설정을 끄는 곳은 **없다** | 검색 0건 |
| 그래서 줄 하나마다 **그 줄을 남긴 쪽(화면 창)의 JS 흐름이 파일 쓰기를 기다린다** | 위 두 줄의 결과 |
| 파일 크기 상한을 **0 으로 두었다**(넘어가면 잘라 쓰는 기능을 끔) | `ws_log.js` 147줄 · `electron/lib/log/ws_main_log.js` 154줄. 3개월 지난 파일은 앱 켤 때 지운다(로그 표준 §6) |

느린 PC·백신이 파일을 들여다보는 PC 에서는 이 기다림이 길어진다. 분당 40줄이면 조작 한 번에 여러 줄이 몰리는 순간이 생긴다.
**한 줄당 실제로 몇 ms 인지는 안 재 봤다(미확인).**

## 5. 결론

지금 PC 에 부담을 주는 것은 **로그를 남긴다는 사실 자체가 아니라** 두 가지다.

1. **같은 줄 하나가 93%** — 조작할 때마다 되풀이된다.
2. **줄마다 동기 디스크 쓰기** — 화면 창이 그때마다 기다린다.

busy 로그는 처리 1건당 1줄이라 여기에 거의 얹히지 않는다.

## 6. 비동기로 바꾸면 순서가 바뀌나 (장군님 물음 2026-09-16) — **바뀔 수 있다**

| 물음 | 답 | 근거 (라이브러리 소스, 읽기만 함) |
|---|---|---|
| **한 창 안**에서 순서가 바뀌나 | **안 바뀐다.** 줄을 큐에 넣고 **한 번에 하나씩** 순서대로 쓴다 | `node_modules/electron-log/src/transports/file/file.js` 131~137·186~205줄 |
| **창이 여러 개일 때**는 | **바뀔 수 있다.** 창마다·앱 본체마다 큐가 **따로** 돌고, 셋이 같은 파일에 덧붙인다. A 창이 먼저 남긴 줄이 B 창 줄보다 **뒤에 적힐 수 있다** | 같은 파일 255~268줄(파일 목록은 프로세스마다 따로) |
| 지금(동기)은 안 바뀌나 | 지금도 완전히 보장되지는 않지만, **부른 그 자리에서 바로 덧붙이므로** 어긋나는 폭이 훨씬 작다 | `file.js` 140줄 |
| 시각은 믿을 수 있나 | **믿을 수 있다.** 시각은 **로그를 부른 순간**에 찍힌다(쓰는 순간이 아니다). ms 까지 있어 **시각으로 정렬하면 원래 순서를 되살릴 수 있다** | `log.js` 15줄 `date: new Date()` |
| 같은 ms 에 두 줄이면 | 시각만으로는 못 가른다. 줄마다 순번을 붙이지 않는 한 **구분 불가** | 지금 줄 모양에 순번 없음 |

**busy 검증에 왜 중요한가** — 새창 흐름은 **부모 창과 새창 두 창이 섞인다.** 비동기로 바꾸면 「부모가 busy 를 끈 시점 vs 새창이 켠 시점」을 **파일에 적힌 순서로 믿으면 안 되고 시각으로 정렬해야** 한다. 판정을 제가 하므로 정렬은 제가 하면 되지만, 같은 ms 가 겹치면 갈 수 없다.

**그래서 §1 에서 「지금은 바꾸지 말자」로 뒤집었다.** 반복 줄(93%)만 없애도 부하가 크게 줄고, 순서는 지금 그대로 안전하다.
