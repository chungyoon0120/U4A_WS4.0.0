# 「UI 하나 만들 때마다 진입 기록」이 무슨 말인가 — 쉬운 설명

> 작성 2026-10-06 · 장군님 물음 「어떤 상황인지, 무슨 의미인지 설명해 달라」

## 1. 왜 이 이야기가 나왔나

**이 프로그램은 운영에 들어가면 AI 가 로그만 보고 원인을 찾아 고칩니다.**
그래서 지침서 2(2026-10-01 착수)에서 「오류가 났을 때 로그에 더 많이 남게」 하는 작업을 했습니다.
그 작업의 항목 중 하나가 **「어느 길을 지났는지 남기기」** 였고, 이름을 `ENTER` 로 정했습니다.

지침서가 이 항목에 대해 **「무엇을 남길지 먼저 보고하고 승인받아라」** 고 적어 둬서,
제가 **일부만 넣고 하나는 보류**했습니다. 그 보류분이 지금 여쭙는 것입니다.

---

## 2. 「진입 기록」이 무슨 뜻인가

로그 파일에 **「이 함수에 들어왔다」** 는 줄 하나를 남기는 것입니다. 모양은 이렇습니다.

```
ENTER | drawPreview |
ENTER | refreshPreview | OBJID=ROOT
```

- 오류가 아닙니다. **지나갔다는 발자국**입니다.
- 왜 필요한가: 오류가 났을 때 **그 코드가 아예 안 불렸는지**, **불렸는데 안에서 터졌는지**를 가릅니다.
  이게 없으면 AI 가 둘을 구분할 수 없어 엉뚱한 곳을 팝니다.

---

## 3. 이미 넣은 곳 — 4군데 (2026-10-01, 커밋 완료)

| 어디 | 언제 한 번 돌까 |
|---|---|
| 디자인 미리보기 전체를 그리는 곳 | 미리보기를 **한 번 그릴 때 1번** |
| 미리보기를 다시 그리는 곳 | 다시 그릴 때 **1번** (어느 객체인지 같이 남김) |
| WS30 화면 만드는 곳 (2군데) | 화면 만들 때 **1번** |

**전부 「한 번에 1줄」** 자리입니다. 그래서 양이 안 늡니다.

---

## 4. 지금 여쭙는 자리 — 왜 다른가

보류한 자리는 **UI 객체 하나를 실제로 만들어 붙이는 함수**입니다
(`createUIInstance`, `www/ws30/ws10_20/design/preview/index.js:5045`).

- **디자인 트리에 있는 UI 한 줄마다 1번** 돕니다. 소스로 확인한 사실입니다.
- 즉 **UI 50개짜리 앱 = 50줄 / 100개짜리 = 100줄**이 미리보기를 그릴 때마다 쌓입니다.
- 미리보기는 속성을 바꿀 때마다 다시 그립니다 → **같은 줄이 계속 반복됩니다.**

| | 넣으면 | 안 넣으면 |
|---|---|---|
| 얻는 것 | 어느 UI 에서 멈췄는지 **줄 단위로** 보인다 | 어느 UI 에서 멈췄는지는 **오류 줄로** 본다 |
| 잃는 것 | 로그가 **앱마다 수십~수백 줄씩** 늘어난다. 고객사 PC 용량이다 | 성공한 UI 의 발자국은 없다 |

---

## 5. 제 생각 — 넣지 않는다

**이 함수가 실패하면 이미 필요한 것이 다 찍힙니다.**
지난번 작업(2026-09-29)에서 이 자리 오류 줄에 **객체 이름(OBJID)** 과 **UI5 class 이름(LIBNM)** 을
같이 남기게 해 뒀습니다. 그러니 **터진 UI 는 오류 줄 하나로 바로 짚힙니다.**

여기에 진입 기록을 더하면 **성공한 UI 까지 전부** 찍히는데, 그건 AI 가 원인을 짚는 데 안 쓰는 글자입니다.
로그 표준에도 **「AI 가 원인을 짚는 데 안 쓰는 글자는 한 글자도 남기지 않는다」** 고 적혀 있습니다
(장군님 지시 2026-09-11).

### 다만 이런 길도 있습니다

**평소엔 안 남기고, 로그 등급을 올렸을 때만 나오게** 할 수 있습니다.
등급을 올리는 기능(`U4ALOG.setConsoleLevel`)은 이미 넣어 뒀습니다(지침서 2, 커밋 완료).
그러면 **평소엔 양이 0, 원인을 쫓을 때만 켜서** 봅니다.
단점은 **고객사에서 문제가 터진 그 순간에는 안 켜져 있다**는 것 — 재현이 돼야 쓸 수 있습니다.

# 7. 장군님 반론 (2026-10-06) — "조합 때문에 터진 건 어떻게 찾느냐"

> 장군님 말씀 그대로: *"PAGE 밑에 input을 넣었을때 오류난건지? 아니면 PAGE 밑에 vbox 넣고
> 뭐 넣고 뭐넣고 여기까지는 성공인데 **특정 ui의 조합에 의해서** 오류가 발생된건 어떻게
> 무슨수로 원인 분석하고 버그를 고칠려고 하는거냐?"*

**맞는 지적입니다. 제 5번 절의 「넣지 않는다」 근거에 구멍이 있었습니다.**

## 7-1. 지금 로그에 실제로 남는 것 — 소스로 확인

UI 하나를 만들다 터질 때 남는 줄은 **터진 UI 하나만** 가리킵니다.

| 남는 것 | 안 남는 것 |
|---|---|
| 터진 UI 의 객체 이름(OBJID) | **부모가 누구인지** |
| 그 UI 의 UI5 class 이름(LIBNM) | **ROOT 부터 거기까지의 경로** |
| 오류 원문 + stack | **형제가 몇 번째인지 · 그 앞에 무엇이 붙었는지** |

즉 **「PAGE 밑의 Input 이 터졌다」 와 「PAGE > VBox > … > Input 조합에서 터졌다」 를 구분할 수 없습니다.**
제가 5번 절에서 "이미 필요한 것이 다 찍힌다" 고 쓴 것은 **틀렸습니다.**

## 7-2. 다만 구조는 그 순간 메모리에 있다 — 소스로 확인

디자인 트리는 **평면 목록(각 줄에 자기 객체 이름 OBJID + 부모 객체 이름 POBID)** 으로
model 의 `TREE` 경로에 들어 있고, 그것을 중첩 구조로 바꿔 화면에 그립니다.
→ **터진 그 순간에 ROOT 부터의 경로를 즉석에서 만들 수 있습니다.** 미리 줄줄이 쌓아 둘 필요가 없습니다.

## 7-3. 그래서 안이 셋입니다

| 안 | 무엇을 남기나 | 평소 양 | 조합을 알 수 있나 |
|---|---|---|---|
| **1** | **터졌을 때만** 그 자리에서 `ROOT > Page > VBox > Input` 처럼 **경로 한 줄** + 형제 몇 번째인지. 구조가 바뀐 직후의 첫 그리기에서만 트리 전체를 한 덩어리로 | **0줄** (성공하면 아무것도 안 남음) | **된다** — 터진 조합이 경로로 바로 보인다 |
| **2** | 미리보기를 **한 번 그릴 때마다** 트리 전체를 한 덩어리로 | 그릴 때마다 1덩어리 (UI 100개면 수 KB) | **된다.** 그 함수 밖(UI5 가 그리는 단계)에서 터져도 구조가 남는다 |
| **3** | **UI 하나마다 한 줄** (원래 보류분) | UI 100개면 100줄, 다시 그릴 때마다 또 | 된다 (순서까지 보인다) |

### 안마다 약점

- **1번** — 오류가 **그 함수 안에서 터질 때만** 경로가 남습니다. UI5 가 나중에 그리는 단계에서
  터지면 그 자리를 안 지날 수 있습니다(**미확인** — 재현해 본 적 없음). 그래서 「구조가 바뀐 뒤
  첫 그리기에 트리 한 덩어리」를 같이 둬서 그 구멍을 막습니다.
- **2번** — 속성 하나만 바꿔도 미리보기를 다시 그리므로, **구조가 안 바뀌었는데도** 같은 덩어리가
  반복 저장됩니다. 「구조가 바뀌었을 때만」 조건을 달지 않으면 양이 큽니다.
- **3번** — 조합·순서까지 가장 확실히 보이지만 **양이 가장 큽니다.** 로그 표준의
  「AI 가 원인을 짚는 데 안 쓰는 글자는 한 글자도 남기지 않는다」 와 정면으로 부딪힙니다.

## 7-4. 제 생각 — 1번

터졌을 때만 경로를 남기면 **장군님이 물으신 것(어떤 조합에서 터졌나)에 그대로 답이 되고**,
성공했을 때는 한 글자도 안 남습니다. 3번이 주는 추가 정보는 「성공한 UI 들의 순서」인데,
그건 **구조 한 덩어리**로 똑같이 알 수 있습니다 — 줄줄이 쌓을 이유가 없습니다.

## 7-5. 1번으로 정하시면 제가 할 일

| 순서 | 무엇을 |
|---|---|
| ① | UI 하나 만드는 함수의 실패 자리에서 **ROOT 부터의 경로**와 **형제 몇 번째**를 같이 남기게 고친다 |
| ② | **구조가 바뀐 뒤 첫 그리기**에만 트리 전체를 한 덩어리로 남긴다(속성만 바뀐 다시 그리기는 안 남김) |
| ③ | 로그 표준 문서에 사건 이름 한 줄 추가 |
| ④ | 현황판에 테스트 항목을 만들어 올린다(장군님 확인용) |
| ⑤ | 커밋 — 지시받은 뒤에만 |

# 8. 최종 결정 (2026-10-06) — 트리 전체는 남기지 않는다

7-3 의 **1번안으로 시작했는데, 거기 들어 있던 「구조가 바뀐 뒤 첫 그리기에 트리 한 줄」 을 빼기로 바뀠다.**

## 8-1. 왜 뺐나 — 장군님 지적

> *"특정 어플리케이션의 UI 총 갯수가 1000단위가 넘는데"*
> *"그런 어플리케이션에서 변경 됐을 경우 그 로그는 감당 되는거냐?"*

**감당 안 된다.** 계산(추정 — 실제 앱으로 재 본 것 아님):

| | 값 |
|---|---|
| 한 자리(`OBJID<부모OBJID(UI5 class 이름)`) 길이 | 대략 40자 |
| UI 1000개 → 한 줄 크기 | **약 40KB** |
| 구조를 바꾸는 조작 | UI 추가·삭제·이동·붙여넣기 — **평상 작업이다** |
| 화면 하나 만들며 300번 건드리면 | **약 12MB** — 로그 표준의 「하루 5MB 안쪽」을 혼자 넘긴다 |
| 자르는 길이를 키우면 | 양이 더 커진다 |
| 그대로 4000자면 | 90% 가 잘려 쓸모가 없다 |

추가로 **느린 PC 문제**도 있다 — 구조가 바뀔 때마다 1000줄마다 UI5 class 이름을 찾아 글자를 이어붙인다.
조작 한 번마다 멈칫이 생길 수 있다(**미확인**).

→ 장군님 확인: **"그게 가장 현실적이다"**

## 8-2. 최종 — 터졌을 때만, 그 자리 주변만

| 언제 | 무엇을 |
|---|---|
| 미리보기에서 UI 하나를 만들다 **터졌을 때만** | ① ROOT 부터 그 UI 까지의 **경로** ② **형제 몇 번째** ③ **그 부모 밑에 붙어 있던 UI 들(형제 목록)** |
| 성공했을 때 | **한 글자도 안 남긴다** |

남는 모양:

```
PATH=ROOT(sap.m.App) > P1(sap.m.Page) > V1(sap.m.VBox) > I1(sap.m.Input) IDX=2/3 SIBLINGS=L1(sap.m.Label) I1(sap.m.Input) B1(sap.m.Button)
```

이 한 줄로 장군님이 물으신 **「PAGE 밑에 vbox 넣고 뭐 넣고 뭐넣고… 그 조합」** 이 바로 보인다.
크기는 **깊이 + 형제 수**에만 묶이므로 UI 가 1000개여도 수백 자다.

### 방어장치

| 무엇 | 값 | 왜 |
|---|---|---|
| circular | 이미 지난 UI 를 다시 만나면 거기서 끊고 표시 | 부모 고리가 돌면 영원히 돈다 |
| max depth | 100 | 위와 같은 이유 |
| 형제 목록 | 앞 30개 + `...(n more)` | 한 부모 밑에 UI 가 수백 개일 수 있다 |
| 한 줄 길이 | 1000자에서 자름 | 그래도 길어지는 경우 대비 |

## 8-3. 안 쓰기로 한 것

- 사건 이름을 새로 만들지 않았다(`UI_TREE` 를 넣었다가 **뺐다**) — 터진 줄에 붙이는 것이라 새 사건이 필요 없다
- 로그 표준 문서도 되돌렸다
- 오류코드는 `PREV-002` 하나만 쓴다(경로 만들기 실패)
