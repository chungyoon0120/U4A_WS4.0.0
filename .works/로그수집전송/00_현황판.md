## ★★서버 통신이 실패했는데 서버가 뭐라고 했는지가 없던 것 — 고침 (2026-09-08)

**장군님이 화면으로 보여 주신 것**: 서버가 500 을 돌려줬는데 로그에는 이 한 줄뿐이었다.

```
[오류] ... 끝남 | unlock_app #11 | 실패: 통신 오류 | 0.5초
```

어느 주소로 보냈는지, 서버가 뭐라고 했는지가 **통째로 없다.** 이걸로는 못 고친다.

**두 가지가 잘못돼 있었다**

| 무엇 | 상태였던 것 |
|---|---|
| 실패 사유 | 상태 번호를 안 보고 **무조건 "통신 오류"** 라고 적었다. 서버가 500 을 돌려준 것도 여기로 온다 |
| 서버가 준 내용 | **하나도 안 남겼다.** 원인을 짚을 유일한 단서인데 버리고 있었다 |

**이제 실패했을 때 남기는 것** (성공은 지금처럼 한 줄만 — 다 남기면 로그가 터진다)

| 남기는 것 | 왜 필요한가 |
|---|---|
| 보낸 곳 (주소·방식) | 어느 기능인지 특정 |
| 서버 상태 번호와 뜻 | 서버 잘못인지 우리 잘못인지 가름 |
| **서버가 준 내용 전체** (길면 앞 4000자) | **터진 프로그램·줄 번호·예외 이름이 여기 들어 있다** |
| 오류를 알리는 응답 표시 값 | 세션 끊김·거절 구분 |
| 보낸 항목 이름 (값은 안 남김) | 무엇을 보내다 터졌는지 |

**실제로 500 을 내서 확인한 결과**

```
[오류] ... 끝남 | unlock_app #11 | 실패: 서버가 상태 500 를 돌려줌 | 0.5초
[오류] ... 서버통신 실패 상세 | 보낸 곳: POST https://…/u4a_ipcmain/unlock_app (뒤쪽 정보는 가림)
[오류] ... 서버통신 실패 상세 | 서버 상태: 500 Internal Server Error
[오류] ... 서버통신 실패 상세 | 서버가 준 내용: Exception: CX_SY_REF_IS_INITIAL
                                Program: /U4A/CL_WS_IPCMAIN…CP
                                Line: 142
                                Message: Access via NULL object reference not possible.
[오류] ... 서버통신 실패 상세 | 보낸 항목: PRCCD, APPID, SESSKEY
```

이제 **어느 프로그램 몇 번째 줄에서 무엇 때문에 터졌는지**까지 로그에 남는다.
본화면과 별창 4곳(속성 바인딩·MIME 저장소·값도움 OTR·단축키 만들기) 전부 같이 넣었다.

## ★★개발로 돌릴 때도 로그가 쌓이고 텔레그램이 나가던 것 — 고침 (2026-09-08)

**정해져 있던 것**: 포장한 앱에서만 파일에 남기고 보낸다. 개발로 돌릴 때는 화면 콘솔로 본다.

**잘못돼 있던 것** (소스 확인)

| 어디 | 상태였던 것 |
|---|---|
| 앱 본체 로그 | **조건 없음** — 개발에서도 파일에 쌓임 |
| 오류 감시 넣기 | **조건 없음** — 개발에서도 걸림 |
| 뻗음 감시 | **조건 없음** — 개발에서도 표시 파일 만듦 |
| 텔레그램 전송 | **조건 없음** — 개발에서도 나감. 있던 줄은 **열쇠 파일 위치만 고르는 것**이지 전송을 막는 게 아니었다 |
| 화면 쪽 | 원래대로 포장했을 때만 파일에 남음 (문제 없음) |

| 설치한 앱 | 걸림 | 생김 | 생김 |

## ★★"지난번에 비정상으로 끝났다" 가 매번 거짓으로 뜨던 것 — 고침 (2026-09-08)

**무엇을 근거로 남기나**: 앱을 켤 때 "돌고 있음" 표시 파일을 하나 만들고, 끝낼 때 지운다.
다음에 켰을 때 그게 남아 있으면 지난번에 못 지우고 죽은 것으로 본다.

**그런데 지금 것은 전부 거짓이었다** (실제 로그·파일로 확인)

| 확인한 것 | 결과 |
|---|---|
| 9월 8일 로그의 **앱 시작** 줄 | **17번** |
| 같은 로그의 **앱 정상 종료** 줄 | **0번** |
| 지금 그 표시 파일 | **남아 있음** |

**원인**: 이 앱은 서버 목록 화면의 닫기·종료에서 **끝내는 신호를 미리 알리지 않고 바로 끝내는 방식**을 쓴다(소스 확인).
그래서 표시를 지우는 자리가 **한 번도 안 불렸다.** 정상으로 껐는데도 다음 실행마다 "비정상"이라고 남고 전송됐다.

**고친 방법**: 앱 본체의 **끝내는 함수 자체를 감쌌다.** 창에서 부르는 것도 결국 그 함수를 지난다(창 쪽 것과 앱 본체 것이 같은 것임을 소스로 확인).
끝내기 직전에 표시를 지우고 종료를 로그에 남긴 뒤 원래 동작을 그대로 부른다. 프로세스가 끝나는 순간에도 한 번 더 지운다.

**실제로 돌려 확인한 결과** (앱 없이 그 부분만 따로 돌림)

| 상황 | 나온 결과 |
|---|---|
| ① 처음 켜기 | 표시 파일 생김 |
| ② 앱이 스스로 끝내기(이 앱이 실제로 쓰는 방식) | **앱 정상 종료** 로그 + 표시 파일 지워짐 |
| ③ 다시 켜기 | **아무 말 없음** (전에는 여기서 거짓 경보가 났다) |
| ④ 표시를 남긴 채 다시 켜기(진짜 뻗은 상황) | **비정상으로 끝났다** + 전송 |

## ★1차 빌드에서 드러난 것 — 고침 (2026-09-08)

> 장군님이 1차 빌드 로그를 주셔서 **실제 줄을 보고** 확인했다.
> **가장 중요한 「어느 조작 때문에 난 오류인지 잇는 것」이 작동하지 않고 있었다.**
> 만들어 놓고 연결을 안 한 것이 원인이다. 아래 다섯 가지를 고쳤다.

| 로그에 보이던 증상 | 원인 | 고친 방법 |
|---|---|---|
| 모든 줄이 **창미상** | 창 이름을 알려 주는 자리를 **아무도 부르지 않음** | 화면마다 부르게 하지 않고 **스스로 알아내게** 바꿈(맨 위 창 제목, 틀 안 화면이면 "(창제목) 안") |
| 첫 화면이 **화면미상** | 화면 이름은 **옮길 때만** 알려 줌 | 비어 있으면 그 자리에서 문서 제목·주소로 **스스로 채움** |
| **★추적 번호가 전부 ----** | 번호를 새로 뽑는 자리를 **아무도 부르지 않음** | **버튼을 누를 때마다 새 번호를 뽑음.** 그 뒤 서버 요청·화면 이동·오류가 자동으로 같은 번호를 물게 됨 |
| **같은 조작이 두 줄** | 앱 본체 감시를 넣을 때 화면쪽 로그 함수가 **아직 안 올라와** 둘 다 설치됨 | 설치할 때가 아니라 **남기는 그 순간에** 판단해 건너뜀 |
| 같은 요청 6개의 **응답이 뒤섞여 짝을 못 지음** | 요청을 구분할 것이 없음 | 요청마다 **번호(#1, #2 …)** 를 붙임. 보낸 줄과 받은 줄의 짝이 맞음 |

**오류가 났을 때 보내는 파일에도** 창 이름과 추적 번호를 실었다. 그 번호로 로그에서 그 조작을 바로 찾을 수 있다.

**실제로 돌려 확인한 결과** (앱 없이 로그 함수만 따로 돌림)

```
[알림] [설계 화면] [WS20] [9ZXL] 눌렀음 | 구문 검사 (Ctrl+F2)
[알림] [설계 화면] [WS20] [9ZXL] 보냈음 | chk_ws_syntx #1 | 0.0초
[알림] [설계 화면] [WS20] [9ZXL] 끝남 | chk_ws_syntx #1 | 성공 | 0.6초
[오류] [설계 화면] [WS20] [9ZXL] 터짐 | 없는 값을 꺼내 씀: 화면정보
        난 자리: (터진 자리 전체)
        그때 화면: 로딩표시 꺼짐 / 떠 있는 창 0개 / 초점 (없음)
[알림] [설계 화면] [WS20] [MYKT] 눌렀음 | Back
```

같은 번호로 **누른 버튼 → 나간 요청 → 터진 자리** 가 한 줄기로 이어진다. 다음 버튼을 누르면 번호가 바뀐다.

## 지금 테스트할 것 — 1차 구현분 (2026-09-08)

> **앱을 다시 빌드해서 설치한 뒤** 아래를 확인해 주십시오.
> 로그 파일 위치 = `%APPDATA%\(앱 폴더)\logs\U4A_WS_연_월_일.log`
> ※ 로그 파일은 **패키징한 앱에서만** 생깁니다. 개발 실행에서는 화면 콘솔로 봅니다.

| 코드 | 동작 | 조작·확인 포인트 | O/X(☐) |
|---|---|---|---|
| WL1 | 앱 시작 정보가 로그 앞머리에 남는다 | ① 앱을 켠다 ② 로그 폴더의 오늘 날짜 파일을 연다 ③ 맨 위에 **앱 시작 / 앱 버전 / 윈도우 / 메모리 / 로그 파일 경로** 다섯 줄이 있는지 본다 | ☐ |
| WL2 | 앱을 정상으로 끄면 종료 줄이 남는다 | ① 앱을 정상으로 닫는다 ② 로그 파일 맨 끝에 **앱 정상 종료** 줄이 있는지 본다 | ☐ |
| WL3 | 창을 강제로 죽이면 로그에 남는다 | ① 앱을 켠다 ② 작업 관리자에서 **자식 프로세스 하나만** 강제 종료한다 ③ 로그 파일에 **창이 죽음** 줄과 사유가 남았는지 본다 | ☐ |
| WL4 | 로그 파일이 1MB 넘어도 안 밀려난다 | ① 앱을 오래 쓰거나 오류를 여러 번 낸다 ② 로그 폴더에 **`.old` 가 붙은 파일이 새로 생기지 않는지** 본다 ③ 오늘 날짜 파일 하나만 계속 커지면 정상 | ☐ |
| WL5 | 오류가 두 번 나도 둘 다 로그에 남는다 | ① 오류를 한 번 낸다(오류창이 뜬다) ② 오류창을 닫지 말고 다시 오류를 낸다 ③ 로그 파일에 **오류 줄이 두 건** 남았는지 본다 ④ 오류창은 **한 번만** 떠야 정상 | ☐ |
| WL6 | 토큰이 없어도 앱이 정상 동작한다 | ① 설정 파일의 봇 토큰을 비워 둔 채 앱을 켠다 ② 오류를 한 번 낸다 ③ 앱이 평소대로 동작하고 **아무것도 안 보내지는지** 본다 | ☐ |
| WL10 | 서버와 주고받은 것이 로그에 남는다 | ① 앱을 켜고 로그인한다 ② 화면을 열거나 저장한다 ③ 로그 파일에 **보냈음 / 받았음 / 끝남** 세 줄이 짝으로 남고 **걸린 시간**이 붙는지 본다 | ☐ |

## ★ 이 작업의 합격 기준 (장군님 지시 2026-09-08)

> **AI 에이전트가 도착한 기록만 보고 "그 자리를 열어 직접 고칠 수 있는" 수준이어야 한다.**
> "무슨 오류가 났는지 알겠다"는 합격이 아니다. **어느 파일 몇 번째 줄을 어떻게 고치면 되는지까지
> 나와야** 합격이다. 아래 다섯 개가 한 건 안에 다 있으면 합격, 하나라도 없으면 불합격이다.

| 코드 | 있어야 할 것 | 없으면 AI가 멈추는 지점 |
|---|---|---|
| **AC1** | **고칠 자리** — 파일 경로 + 줄 번호 + 함수 이름 | "어디인지 모르겠다"에서 끝 |
| **AC2** | **무엇이 없어서 터졌는지** — 없다고 한 이름 그대로 | "값이 이상하다"까지만 말함 |
| **AC3** ★ | **사용 흐름** — 화면에 들어와서 오류까지 무엇을 어떤 순서로 했는지(4장) | **여기가 핵심.** 흐름이 없으면 원인을 못 좁히고, 고쳐도 맞는지 확인할 방법이 없음 |
| **AC4** | **그때 다루던 것의 모양** — 어떤 항목이 비어 있었는지 | 왜 그 값이 없었는지를 못 짚음 |
| **AC5** | **앱 버전** | 이미 고친 것을 또 고치려 듦 |

### ★다섯 중 가장 중요한 것 = AC3 「사용 흐름」 (장군님 지시 2026-09-08)

> **"이 로그를 보고 AI가 원인을 잘 파악할 수 있는가"가 전부다.**
> 그리고 AI가 원인을 짚는 힘은 **오류 줄 하나가 아니라 그 앞의 흐름**에서 나온다.
> 오류 줄만 있으면 "여기서 값이 없었다"까지고, 흐름이 있으면 **"왜 없었는지"**가 나온다.

| 코드 | 흐름이 갖춰야 할 조건 | 안 지키면 |
|---|---|---|
| **AC3-1** | **끊기지 않아야 한다.** 화면에 들어온 순간부터 오류까지가 이어져야 한다 | 중간이 비면 AI가 그 구간을 상상하게 된다 |
| **AC3-2** | **순서와 간격이 있어야 한다.** 무엇 다음에 무엇을, 몇 초 뒤에 | 연타·기다림·꼬임을 못 본다 |
| **AC3-3** | **무엇에 대고 한 조작인지** 대상 이름이 있어야 한다(4-1-b) | "버튼을 눌렀다"만으로는 그림이 안 그려진다 |
| **AC3-4** | **성공했는지 실패했는지**가 조작마다 붙어야 한다 | 앞에서 실패한 게 뒤 오류의 원인인지 못 잇는다 |
| **AC3-5** | **사람이 한 일과 코드가 스스로 한 일이 구분**돼야 한다 | 아무도 안 만졌는데 난 오류를 오해한다 |

**판단 기준 한 줄**: 그 기록을 사람이 읽고 **오류를 그대로 재현할 수 있으면 합격**이다.
재현이 안 되면 AI도 못 고친다.

### ★합격 예시 — AI가 이 문장을 말할 수 있어야 한다 (장군님 지시 2026-09-08)

> **목표 문장**
> *"사용자가 이러이러하게 접속했고, 어느 화면에 들어가서 무슨 버튼을 눌렀는데,
> 화면을 넘기다가 오류가 났군."*
>
> 여기까지 나와야 AI가 **그 자리의 소스를 열고 앞뒤 관계를 따져볼 수 있다.**
> 이 문장이 안 나오면 기록이 부족한 것이다.

### 이 문장이 나오려면 기록이 이런 모양이어야 한다

```
[정보] 앱 시작 | 앱 3.6.4 | 윈도우 11 64비트 | 화면 1920x1080 배율 100% | 메모리 16GB
[정보] 접속 | 서버: 개발서버 / 접속방식: 사내망 / 결과: 성공 | 0.8초 걸림
[정보] 화면 열림 | 화면목록 | 0.3초 걸림
[행위] 화면목록 | 골랐음 | 목록 줄: 주문화면 | 상세 표시됨 | 앞 조작 2초 뒤
[행위] 화면목록 | 눌렀음 | 편집 | 화면 이동 시작 | 앞 조작 1초 뒤
[정보] 화면 이동 | 화면목록 → 화면 편집 | 시작
[오류] 화면 편집 | [코드] 없는 값을 꺼내 씀: 화면정보
        난 자리: <파일 경로>:412  함수: 화면 그리기 준비
        직전 조작: 편집 버튼 누름 (1초 전)
        그때 골라져 있던 것: 목록 줄 주문화면
        다루던 자료: 항목 3개 중 화면정보 비어 있음
```

### 각 줄이 목표 문장의 어느 부분을 만드는가

| 목표 문장의 조각 | 그것을 만드는 줄 |
|---|---|
| "이러이러하게 접속했고" | **접속** 줄 — 서버·접속 방식·성공 여부 |
| "어느 화면에 들어가서" | **화면 열림** 줄 |
| "무슨 버튼을 눌렀는데" | **행위** 줄 — 버튼 이름 + 무엇에 대고 |
| "화면을 넘기다가" | **화면 이동 시작** 줄 |
| "오류가 났군" | **오류** 줄 — 난 자리(파일·줄)·없어진 값 이름 |
| AI가 소스를 열 수 있게 | 오류 줄의 **파일 경로와 줄 번호** |
| AI가 앞뒤 관계를 따질 수 있게 | 각 줄의 **순서와 간격**, 조작마다 붙은 **성공·실패** |

**그래서 이 다섯 줄은 반드시 있어야 한다**: 접속 / 화면 열림 / 버튼 누름 / 화면 이동 / 오류.
하나라도 빠지면 목표 문장이 그만큼 흐려진다.

### 합격 기준을 위협하는 것 — 지금 상태

| 코드 | 위협 | 현재 확인 결과 |

## ★ 로딩 표시가 안 꺼질 때 · 운영에서의 용량 (장군님 지시 2026-09-08)

### 1) 로딩 표시가 계속 도는 것은 **자동으로 오류로 치지 않는다**

| 왜 | 내용 |
|---|---|
| 판단이 안 선다 | **진짜 오래 걸리는 것인지, 컴퓨터가 느린 것인지, 오류가 난 것인지 구분이 안 된다.** 자동으로 오류라고 찍으면 헛것이 쏟아진다 |
| 대신 이렇게 | 그때까지의 **과정은 이미 기록에 남아 있다.** 테스터가 이상하다고 느끼면 **화면을 찍어 증상을 보고**하고, 그때 장군님이 **그 컴퓨터의 기록 파일을 따로 받아** 본다 |
| 그래서 | **자동 전송 대상이 아니다.** 다만 **오래 걸린 일은 기록에 남긴다** — 무엇이 언제 시작해 몇 초째인지 |
| 이것이 | **사용자 동작 기록을 남기는 진짜 이유다.** 멈춘 화면만 봐서는 모르고, 그 앞에 무엇을 했는지가 있어야 판단이 선다 |

**남길 것**: 오래 걸리는 일은 **시작 줄**과 **끝 줄**을 짝으로 남긴다. 끝 줄이 없으면 그 자리에서 멈춘 것이다.

### 2) ★운영에서는 동작 기록이 용량 문제가 될 수 있다

> 장군님 지적: 운영으로 가면 동작 기록을 남기는 것도 잘 따져야 한다. **잘못하면 용량이 커져 문제가 된다.**

**대략 계산** (실측 아님, 가정 위의 산수)

| 가정 | 값 |
|---|---|
| 한 줄 길이 | 200바이트 안팎 |
| 하루 조작 수(사람이 버튼 누르는 속도) | 1,000 ~ 3,000줄 |
| **하루 파일 크기** | **약 0.2 ~ 0.6MB** |
| 3개월 쌓이면 | 약 20 ~ 55MB |

- **사람 손 속도로 누르는 것만 남기면 이 정도다.** 부담이 아니다.
- **진짜 위험은 사람 손이 아니라 코드가 스스로 반복하는 자리다.** 초당 수십 줄이 남으면
  하루에 수백 MB가 된다. 여기서 터진다.

**그래서 지킬 것**

| 코드 | 지킬 것 |

| **Z3** | **한 줄 길이에 상한**을 둔다. 길면 뒤를 자른다 |
| **Z4** | **하루 줄 수 상한**을 둔다. 넘으면 **잔 동작부터 자동으로 줄이고**, 그 사실을 한 줄 남긴다 |
| **Z5** | **운영에서는 동작 기록 수준을 낮춘다** → 아래 D27 |

### 4-0. 왜 자동으로 남겨야 하나 (장군님 지시 2026-09-08)

- 테스터는 한참 쓰다가 오류를 만난다. **그때 뭘 하다 났는지 기억 못 하는 게 정상이다.**
  "저장 눌렀나? 그 전에 뭘 열었더라?" — 물어봐도 정확한 답이 안 나온다.
- 그래서 **묻지 않는다. 앱이 대신 기억한다.** 테스터는 아무것도 안 해도 된다.
- 동작 로그는 **오류 나기 훨씬 전부터 계속 쌓고 있어야** 한다. 오류가 난 뒤에 모으려 하면 이미 늦다.
- 담는 양은 **기억이 흐려지는 구간을 덮을 만큼** — 최근 몇 십 건 + 오류 직전 몇 분 → D15.
- **모으는 방식은 4-3에서 확정**: 각 버튼의 클릭 처리 안에 **버튼 이름을 넣은 기록 한 줄**.

### 4-1. 한 줄에 남길 것

| 항목 | 예시 |
|---|---|
| 어느 창에서 | `화면 편집` |
| 무엇을 했는지 | `눌렀음` / `열었음` / `닫았음` / `옮겼음` / `입력했음` / `골랐음` |
| 무엇을 | **화면에 적힌 글자 그대로** — `저장`, `실행`, `속성 바인딩` |
| 무엇에 대고 | **고른 대상의 이름** — `트리 항목: 버튼1`, `목록 줄: 화면목록`, `파일: 샘플` (4-1-b) |
| 그 결과 | `팝업 열림` / `서버에 요청 보냄` / `실패` |
| 앞 조작과의 간격 | `2초 뒤` (연타인지 한참 뒤인지 구분) |

- 한 줄 예: `화면 편집 / 눌렀음 / 저장 / 서버에 요청 보냄 / 앞 조작 2초 뒤`
- **입력한 값 자체는 안 남긴다**(칸 이름만) → D16.

### 4-1-b. ★"무엇을 대상으로 했는지"까지 남긴다 (장군님 지시 2026-09-08)

> 버튼을 눌렀다는 사실만으로는 부족하다. **무엇에 대고 눌렀는지**가 있어야 행위가 그려진다.
> 앞서 "입력칸에 친 값은 안 남긴다"고 정했는데, 그것과 **아래는 다른 이야기다.** 헷갈리면 안 된다.

| 구분 | 보기 | 남기나 |
|---|---|---|
| **사용자가 타자로 친 값** | 이름 칸에 친 글자, 설명 칸에 쓴 문장 | **안 남긴다**(칸 이름만) |
| **사용자가 고른 대상의 이름** | 트리에서 고른 항목 이름, 목록에서 고른 줄 이름, 고른 파일 이름, 고른 서버 이름, 드롭다운에서 고른 항목 | **남긴다** |
| **대상이 무엇인지 알려주는 값** | 화면 이름, 창 이름, 탭 이름, 어느 영역인지 | **남긴다** |

### 행위를 그릴 수 있게 하는 것 — 한 줄에 이 다섯

| 코드 | 넣을 것 | 보기 |
|---|---|---|
| **A-1** | **어디서** | `화면 편집` |
| **A-2** | **무엇을 했는지** | `눌렀음` / `골랐음` / `열었음` / `닫았음` / `옮겼음` / `입력했음` |
| **A-3** | **무엇에 대고** — 대상 이름 | `저장` 버튼 / `트리 항목: 버튼1` / `파일: 화면목록` |
| **A-4** | **그래서 어떻게 됐는지** | `팝업 열림` / `서버에 요청 보냄` / `실패` |
| **A-5** | **앞 조작과의 간격** | `2초 뒤` |

- 예: `화면 편집 / 골랐음 / 트리 항목: 버튼1 / 속성 목록 바뀜 / 앞 조작 1초 뒤`
- 이 정도면 **그 사람이 무엇을 하려던 참이었는지 그려진다.** 값은 없어도 된다.

### 4-3. 어떻게 모을 것인가 — **방식 확정**(장군님 지시 2026-09-08)

> **각 버튼의 클릭 처리 코드 안에서, 버튼 이름을 넣은 기록을 한 줄 남긴다.**
> 화면 글자를 훔쳐보거나 식별자를 따로 붙일 필요가 없다. 그 버튼이 무슨 버튼인지는
> **그 코드를 쓴 사람이 가장 잘 안다.** 이름을 코드에 직접 적어 넣는다.

| 코드 | 방법 | 비고 |
|---|---|---|
| M1 | **버튼 클릭 처리 안에 기록 한 줄** — 버튼 이름을 그 자리에서 적어 넣음 | **확정 방식.** 그림 버튼이든 글자 버튼이든 이름이 정확히 남음 |
| M2 | 이름은 **화면에 보이는 글자 그대로** 적는다 | 내부 이름·영문 약자로 적으면 나중에 못 알아봄 |
| M3 | 화면 옮김·창 열고 닫기는 **이미 있는 공통 자리**에 한 줄 추가 | 적은 손으로 확실히 잡힘 |
| M4 | 서버에 보내고 받는 자리도 **공통 자리 한 곳**에 한 줄 추가 | 요청과 결과가 짝으로 남음 |
| M5 | 기록이 **화면을 느리게 하면 안 된다** — 메모리에 쌓아 두고 오류 때만 꺼냄 | 평소엔 파일에 안 씀 |
| M6 | 오래된 것은 버리고 **최근 것만** 들고 있는다 | 메모리를 계속 먹지 않음 → D15 |

**이 방식의 약점 하나**: 버튼이 많아서 **기록 줄을 안 넣은 버튼은 아무것도 안 남는다.**
그 버튼을 누르고 오류가 나면 동작 로그에 구멍이 생긴다. 그래서 아래를 정해 주셔야 한다 → D18.

### 4-4. 이 동작 로그로 무엇을 알 수 있나

- `눌렀음 저장` → `서버에 요청 보냄` → `실패` → 오류 : **저장 중 실패**로 바로 좁혀짐.
- `팝업 닫았음` → 0.3초 뒤 오류 : **닫은 뒤에도 그 안의 것을 쓰고 있다**는 뜻.
- 같은 버튼 `0.2초 간격 3회` → 오류 : **연타로 겹쳐 실행**된 것.
- 사람 조작이 하나도 없이 오류 : **코드가 스스로 한 일**(U12)에서 난 것.

### 4-7-1. 서버가 꼭 있어야 하나 — **아니다** (장군님 질문 2026-09-08)

| 방식 | 서버 필요 | 어떻게 되나 | 실시간 알림 |
|---|---|---|---|
| **㉮ 서버로 올림** | **필요** | 죽는 순간 우리 서버로 올라가고, 서버가 텔레그램으로 알림 | **된다**(죽자마자 올리는지는 **미확인**) |
| **㉯ 안 올리고 크래시 리포트만 남김** | **없어도 됨** | 크래시 리포트가 **앱 폴더 안에 파일로** 쌓인다. **다음 실행 때** 우리가 그 파일을 보고 "지난번에 죽었다"를 알고, 우리 전송 자리로 텔레그램에 보낸다 | 안 된다(다음 실행 때) |

- **㉯ 로도 목적은 달성된다.** 우리가 원하는 건 "죽었다 + 그 시각 + 마지막 상태"인데,
  그건 크래시 리포트 파일과 딸려 있는 값들에 그대로 들어 있다.
- **㉮ 의 이점**: 죽는 순간 바로 알 수 있고, 봇 열쇠를 앱에 안 심어도 된다.
- **㉯ 의 이점**: 서버를 안 만들어도 되고, 회사망에서 우리 서버가 막혀도 상관없다.
- **권함**: 지금은 **㉯ 로 시작**한다. 어차피 뻗은 뒤 다음 실행 때 보내는 통로(W10)를 만들어야 하고,
  그 통로에 흔적 정보를 얹기만 하면 된다. **서버는 나중에 필요하면 붙인다.**

### 4-5. "메모리에 계속 쌓이면 그것도 용량 아닌가?" (장군님 질문 2026-09-08)

> ※ 아래는 **메모리 보관소를 두는 경우**의 계산이다. 4-6 결론대로 **파일 쪽으로 가면 이 걱정 자체가 없어진다.**

**계속 쌓지 않는다. 정해진 개수만 들고 있고, 넘치면 가장 오래된 것부터 버린다.**
줄이 하나 들어오면 가장 오래된 줄 하나가 빠진다. 그래서 **몇 시간을 써도 크기가 늘지 않는다.**

### 대략 얼마나 되나 (계산 — 실측 아님, 가정 위의 산수)

| 가정 | 값 |
|---|---|
| 한 줄 길이 | 200자 안팎 |
| 한 자당 차지하는 자리 | 2바이트 안팎 |
| 한 줄 | 약 400바이트 |

| 들고 있는 줄 수 | 한 창당 차지하는 자리 |
|---|---|
| **30줄 (확정)** | **약 12KB** |
| 100줄 | 약 40KB |
| 300줄 | 약 120KB |

- 창이 여러 개면 **창 수만큼 곱해진다.** 창 10개 × 30줄이면 다 합쳐 **120KB 남짓**이다.
- 이 앱은 화면 하나에도 그보다 훨씬 큰 자료를 이미 들고 돌아간다. **부담이 되는 크기가 아니다.**

### 그래도 지킬 것

| 코드 | 지킬 것 | 왜 |
|---|---|---|
| K1 | **개수 상한을 반드시 둔다**(D15) | 상한이 없으면 그때는 정말 계속 늘어난다 |
| K2 | **한 줄 길이에도 상한을 둔다** — 길면 뒤를 자른다 | 자료 값이 통째로 들어오면 한 줄이 몇 십 킬로가 될 수 있다 |
| K3 | **큰 덩어리는 넣지 않는다** — 화면 그림, 파일 내용, 서버가 준 자료 통째 | 이것만 안 지키면 위 계산이 무너진다 |
| K4 | 창을 닫으면 그 창 몫은 **같이 사라진다** | 닫힌 창 몫이 남아 쌓이지 않게 |

### 4-6. 파일에서 뽑을까, 메모리에서 뽑을까 — **파일 쪽을 권함** (장군님 질문 2026-09-08)

**결론: 파일이 본체다. 메모리 보관소는 만들지 않는다.**

| 견줌 | 파일에서 뽑기 | 메모리에서 뽑기 |
|---|---|---|
| **여러 창을 한 줄기로 볼 수 있나** | **된다.** 모든 창 기록이 한 파일에 시간순으로 섞여 남는다 | **안 된다.** 창마다 따로라 그 창 것만 있다 |
| **앱·창이 죽어도 남나** | **남는다** | **사라진다** |
| 지금 당장 되나 | **이미 굴러가고 있다**(1장) | 보관소와 모으는 배선을 새로 만들어야 한다 |
| 오류 순간 꺼내는 속도 | 끝부분만 집어 오면 거의 즉시(6-0 F2) | 더 빠르긴 하나 차이가 의미 없다 |
| 만드는 손 | 적다 | 많다 |

**결정적인 것은 첫 줄이다.** 이 앱은 창이 여럿이고, **오류는 A 창에서 나도 원인은 다른 창에서
시작된 경우가 많다.** 메모리 보관소는 창마다 따로 있어서 그 줄기를 못 본다. 파일은 다 섞여 있다.

### 대신 이 두 가지를 반드시 처리해야 한다

| 코드 | 짚은 것 | 근거 | 처리 |
|---|---|---|---|
| **P1** | 지금은 **한 줄 쓸 때마다 디스크에 곧바로 쓴다**(기다렸다 씀) | 라이브러리 기본값이 그렇게 켜져 있음(코드 확인) | **★뒤집음(2026-09-08): 그대로 둔다.** 앱이 뻗는 케이스가 실제로 있으므로, 즉시 쓰기여야 **뻗기 직전 줄까지 파일에 남는다.** 대신 자주 일어나는 동작은 안 남긴다(P4) |
| **P2** | ~~기다리지 않고 쓰면 마지막 몇 줄이 날아간다~~ | 위 설정의 맞바꿈 | **P1 을 그대로 두기로 해서 이 위험이 사라졌다** |
| **P4** | 즉시 쓰기를 유지하는 대신, **자주 일어나는 동작은 기록하지 않는다** — 마우스 움직임, 스크롤, 창 크기 조절/막대 끌기 **도중** | 사람이 버튼 누르는 속도로는 즉시 쓰기가 부담이 안 되지만, 끌기처럼 초당 수십 번 일어나는 것은 부담이 된다 | 끌기는 **끝났을 때 결과 한 줄만** 남긴다 |
| **P3** | 여러 창이 같은 파일에 각자 쓸 때 **줄이 섞이거나 빠지는지 미확인**(H7) | 착수 때 확인 | 이게 깨지면 파일 방식의 첫 번째 근거가 흔들린다. **가장 먼저 확인할 것** |

### 4-7. 앱이 뻗는 케이스 대비 (장군님 지시 2026-09-08 — 실제로 발견됨)

테스트 중 **앱이 그냥 뻗는 경우가 실제로 나왔다.** 이 부류는 지금 **기록이 한 줄도 안 남는다**(H2).
뻗으면 그 자리에서 보낼 수도 없다. 그래서 대비를 나눠 둔다.

| 코드 | 순서 | 무엇을 하나 | 왜 이 순서인가 |
|---|---|---|---|

- **그때 열려 있던 화면 이름**

## 5. 한 건에 담을 내용 — AI가 이것만 읽고 원인을 짚을 수 있어야 함

| 묶음 | 담을 것 | 없으면 생기는 일 |
|---|---|---|
| 무엇이 | 오류 코드, 오류 문구, **난 자리(파일 이름 + 줄 번호)** | 자리를 모르면 분석이 시작조차 안 됨 |
| 어느 화면 | 창 이름, 그 안에서 열려 있던 것 | 같은 오류라도 화면마다 원인이 다름 |
| 직전에 | **사용자 동작 로그**(4장) 최근 N건 | 무슨 조작 뒤에 났는지 모르면 원인 유추 불가 |
| 어떤 자료로 | 다루던 자료의 **모양**(어떤 항목이 비었는지) → D13 | 값이 이상해서 나는 오류를 못 짚음 |
| 어느 판 | 앱 버전 | 이미 고친 오류인지 구분 못 함 |
| 어디에 붙어 | **접속한 서버** | 서버마다 다른 오류를 구분 못 함 |
| 어떤 컴퓨터 | **윈도우 종류·버전, 메모리, 화면 크기·배율** | 특정 환경에서만 나는 오류를 못 짚음 |
| 몇 번 | 같은 오류가 몇 번 났는지 | 어쩌다 한 번인지 계속 나는지 구분 못 함 |

- 시각은 **파일 안에는 남기되 알림에는 안 붙인다**(같은 오류 여러 건을 순서대로 볼 때만 씀).

### 5-0-a. ★AI 입장에서 실제로 막히는 지점 (내가 겪는 기준, 2026-09-08)

> 장군님 요구대로 **내가 이 기록으로 고쳐야 한다면 무엇이 없어서 막히는가**를 적는다.
> 앞의 다섯 가지(합격 기준)는 기본이고, **이 앱 구조 때문에 추가로 필요한 것**이 아래다.

| 코드 | 없으면 내가 막히는 것 | 왜 이 앱에서 특히 그런가 | 남길 것 |
|---|---|---|---|
| **R1** | **어느 창에서 난 것인지** | 창이 여럿이고 **같은 파일이 여러 창에서 동시에 돈다.** 창을 모르면 같은 줄 번호가 어느 창 것인지 못 가린다 | 창을 구분하는 이름·번호를 **모든 줄에** |
| **R2** | **창끼리 주고받은 신호** | 이 앱은 창끼리 신호를 주고받아 움직인다. **A 창이 보낸 신호 때문에 B 창이 터지는 경우**가 실제로 많다. 지금 계획엔 이게 빠져 있었다 | 보낸 창 / 받은 창 / 무슨 신호 / 결과 |
| **R3** | **끊긴 작업을 잇는 꼬리표** | 잠깐 미뤘다 하는 일, 서버 다녀와서 하는 일은 **오류가 난 자리와 시작한 자리가 다르다.** 그러면 난 자리만 봐선 범인을 못 찾는다 | 한 작업에 **꼬리표 하나**를 붙여 시작·중간·끝·오류에 같이 남긴다 |
| **R4** | **그 순간 화면이 어떤 상태였나** | 로딩 표시가 켜져 있었는지, 위에 덮는 창이 떠 있었는지, 편집 중이었는지. 이 앱은 **이 상태 꼬임이 반복되는 문제**다 | 로딩 표시 켜짐 여부 / 떠 있던 창 / 저장 안 된 편집 있음 여부 |
| **R5** | **정확히 어느 빌드인가** | 지금 소스를 계속 고치는 중이라 **같은 버전 번호로 빌드가 여러 번 나온다.** 버전만으론 그 시점 소스를 못 연다 | 앱 버전 + **빌드 시각(또는 소스 판 번호)** 을 앞머리에 |

## 6. 텔레그램 — **파일 첨부 방식으로 확정**(장군님 지시 2026-09-08)

- **보내는 시점 = 오류를 잡은 바로 그 자리**(장군님 지시 2026-09-08). 모아 두거나 미루지 않는다.
- **글로 길게 적어 보내지 않는다. 파일을 붙여서 보낸다.** 받는 쪽에서 파일을 그대로 내려받아
  AI에게 통째로 던질 수 있어야 한다.
- 붙이는 파일 = 기록 파일(글자 파일). 파일 이름에 **오류 코드**를 넣어 무슨 오류인지 바로 보이게 한다.
- 파일과 함께 가는 **짧은 설명 한 줄**만 붙인다: `화면 이름 / 오류 코드`. 보낸 사람·시각은 안 붙인다.
- 못 보내면 **전송 대기열에 쌓았다가** 다음에 보낸다.
- 열쇠·방 번호는 **한 파일에만** 적어 둔다. 값이 없으면 안 보내고 쌓기만 한다.

### 6-0. "자르느라 느려지지 않나?" — 반대다 (장군님 질문 2026-09-08)

**자르는 쪽이 더 빠르다.** 이유는 셋이다.

| 코드 | 사실 | 무슨 뜻인가 |
|---|---|---|
| F1 | **보내는 시간이 압도적으로 길다.** 파일을 인터넷으로 올리는 데 걸리는 시간은 크기에 비례해 늘어난다 | 큰 파일을 통째로 보내면 **보내는 동안 훨씬 오래 걸린다.** 자르는 시간은 그에 비하면 없는 거나 같다 |
| F2 | **파일 끝부분만 읽는 것은 전체를 훑지 않는다.** 읽을 위치를 정해 그 자리부터 읽으면 된다 | 하루치가 아무리 커도 **끝 몇 백 킬로만 집어 오는 일**이라 거의 즉시 끝난다 |
| F3 | **가장 빠른 길은 파일을 아예 안 뒤지는 것** — 사용자 동작 로그를 메모리에 들고 있다가(D19) 오류 순간 **그걸 그대로 파일로 저장해 보낸다** | 디스크를 읽는 일 자체가 없다. **만들자마자 바로 보낸다** |

**결론: F2 를 기본으로 한다**(4-6 에서 파일 쪽으로 정리). 오류가 나면 **그날 기록 파일의 끝부분만
집어 와서 보낸다.** F3(메모리에 들고 있다 저장하기)은 더 빠르지만, 창이 여럿인 이 앱에서는
**여러 창의 줄기를 한 번에 못 봐서** 원인 추적에 오히려 손해다.

**진짜 느려지는 원인은 자르기가 아니라 이쪽이다** — 아래 6-1 에서 다룬다.
