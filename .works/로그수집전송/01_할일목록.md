## W1. 앱 본체에 받는 자리 걸기 ★1순위

- **대상**: `electron/main.js`
- **지금 상태**: 터진 오류·처리 안 된 약속 실패·창 죽음·창 먹통·자식 죽음 받는 자리 **전부 0건**(전수 확인).
- **할 일**
  1. 앱 본체에서 터진 오류와 처리 안 된 약속 실패를 받아 기록.
  2. 창이 죽는 것, 창이 먹통 되는 것, 자식이 죽는 것을 받아 **어느 창인지 + 왜인지** 기록.
  3. 기록은 화면 쪽과 **같은 파일**에 남도록 앱 본체에서도 기록 라이브러리를 켠다.
- **완료 기준**: 창을 강제로 죽이거나 먹통으로 만들면 그 사실이 파일에 남는다.
- **주의**: 앱 본체에서 오류를 받았다고 앱을 그냥 끄면 안 된다. **기록 → (전송) → 종료** 순서.

## W2. 기록 남기는 그 순간에 전송도 같이 시작 ★2순위 (장군님 지시 정정 2026-09-08)

> **정정**: 앞서 "전송이 끝날 때까지 기다렸다 종료"라고 적었으나 **취소한다.**
> **종료를 붙잡지 않는다.** 사용자가 재빨리 확인을 눌러 앱이 꺼지는 것은 어쩔 수 없는 일로 본다.

- **대상**: `www/ws30/ws10_20/js/ws_trycatch.js` (오류를 잡는 자리)
- **지금 흐름**: 오류 잡음 → 기록 남김(파일로 저장됨) → 오류창 띄움 → 확인 누르면 로그 폴더 열고 앱 종료.
- **바꿀 것**: **기록을 남기는 바로 그 자리에서 전송도 같이 시작**한다.
  즉 흐름이 이렇게 된다 — 오류 잡음 → **기록 남김 + 전송 시작(뒤에서)** → 오류창 띄움 → (사용자가 확인) → 종료.
- **바꾸지 않을 것**
  - 오류창을 띄우는 것, 로그 폴더를 여는 것, 앱을 끝내는 것 — **원래 동작 그대로.**
  - **종료를 미루지 않는다.** 전송이 끝나길 기다리지 않는다.
- **못 보내고 앱이 꺼진 경우**: 보낼 것을 **전송 대기열에 적어 두고**, 다음 실행 때 보낸다(W10 통로 재사용).
- **완료 기준**: 일부러 오류를 내면 ① 파일에 기록이 남고 ② 방에 파일이 도착한다.
  ③ 확인을 아주 빨리 눌러 앱을 꺼도, **다음에 켜면 그때 못 보낸 것이 도착한다.**

### 왜 이걸로 충분한가

| 사실 | 뜻 |
|---|---|
| 오류창은 **사용자가 확인을 누를 때까지 떠 있다** | 그 사이에 전송이 끝날 여지가 크다. 대개는 첫 번째 기회에 나간다 |
| 확인을 즉시 눌러 꺼지면 전송이 잘린다 | **어쩔 수 없다.** 대신 전송 대기열에 남아 다음 실행 때 나간다 |
| 종료를 미루면 사용자가 답답해한다 | 원래 동작을 바꾸지 않는 쪽이 낫다 |

  파일 이름에 오류 코드를 넣는다. 한글이 안 깨지게 저장한다.
- **완료 기준**: 만들어진 파일만 열어 봐도 합격 기준 다섯 가지가 다 들어 있다.

## W9. 텔레그램 전송 ⏸ 대기 — **테스트 기간 한정**(장군님 지시 2026-09-08)

> **테스트가 끝나면 이 부분은 전부 막는다.** 기록을 남기는 일(W1~W8·W14)은 운영에서도 계속된다.


- **막힌 이유**: 봇 열쇠와 방 번호를 아직 못 받음.
- **미리 해 둘 것**: 보내는 자리를 만들어 두고 **열쇠·방 번호는 한 파일에만** 적는다. 값이 비어 있으면 안 보내고 쌓기만 한다.
- **할 일(값 받은 뒤)**: 글이 아니라 **파일을 붙여** 보낸다. 설명은 화면 이름과 오류 코드 한 줄만.
  기다리는 시간에 상한을 두고, 넘으면 포기하고 전송 대기열에 넣는다. 보내는 동안 화면은 안 멈춘다.
- **완료 기준**: 일부러 오류를 내면 방에 파일이 도착하고, 그 뒤에 앱이 끝난다.

## W10. 뻗은 것 판정 + 다음 실행 때 보내기

> **장군님 지시 2026-09-08: 중간에 뻗어도, 그때까지 남긴 기록 + 뻗은 시점을 함께 주면 원인을 유추할 수 있다.**
> 뻗는 순간을 직접 잡지 못해도 **"마지막으로 무엇을 하다 멈췄는가"** 는 남길 수 있다. 이게 핵심이다.

- **할 일**
  1. 정상 종료 때 표시를 지우고, 다음 실행 때 표시가 남아 있으면 **지난번에 뻗은 것**으로 본다.
  2. 전송 파일에 아래를 **반드시** 넣는다.
     - **마지막 기록 줄까지의 내용**(그때까지 남긴 행적 전부)
     - **마지막 줄의 시각** = 사실상 **뻗은 시점**
     - **앱이 다시 켜진 시각** — 둘의 차이로 얼마나 방치됐는지 알 수 있다
     - **마지막으로 한 조작**(4장 동작 로그의 맨 끝 줄) = 가장 유력한 용의자
  3. 앞머리에 **"이 건은 앱이 뻗은 뒤 다음 실행에서 보낸 것"** 이라고 적는다.
     그래야 AI가 "기록이 중간에 끊긴 이유"를 오해하지 않는다.
- **완료 기준**: 앱을 강제로 끝낸 뒤 다시 켜면, 지난번 기록이 **뻗은 시점과 마지막 조작과 함께** 방에 도착한다.

### 뻗은 건에서 AI가 실제로 유추하는 방식 (왜 이게 통하나)

| 기록에 남은 모양 | 유추되는 것 |
|---|---|
| 마지막 줄이 `눌렀음 저장` → 서버에 보냄 → **그 뒤 아무것도 없음** | 저장 보내는 도중에 멈췄다 |
| 마지막 줄 뒤로 **몇 분간 아무 기록 없음** | 조작 없이 놀다가 뻗었다 → 뒤에서 도는 일이 원인일 가능성 |
| 마지막 줄이 큰 자료를 다루는 조작 | 자료가 커서 못 버틴 쪽을 먼저 의심 |
| 같은 조작 뒤에 여러 대에서 같은 끊김 | 그 조작이 원인이라고 거의 확정 |

- 그래서 **시각은 파일 안에 반드시 남긴다**(알림 문구에만 안 붙일 뿐이다).
- 그래서 **사용자 동작 로그를 파일에 계속 써야 한다**(W7). 메모리에만 두면 뻗는 순간 다 날아간다.
- 그래서 **한 줄 쓸 때마다 바로 디스크에 쓰는 지금 방식을 그대로 둔다**(00 문서 P1). 마지막 줄까지 남는다.

## W11. 크래시 리포터 새로 적용 (장군님 지시 2026-09-08 확정)

> 근거: Electron 공식 문서 `app.getPath` / `crashReporter` (2026-09-08 조회).

### 11-0. 확정된 방침 세 가지

| 코드 | 장군님 지시 | 반영 |
|---|---|---|
| **P-1** | 사용자가 쓰다가 오류가 나면 **뒤에서 알아서 텔레그램으로 쏜다** | W2 로 처리(기록 남기는 그 순간 전송 시작, 종료는 안 미룸) |
| **P-2** | 뻗는 순간에 받을 수 있는 신호가 없다면, **앱을 켤 때 그 폴더를 보고 파일이 있으면 쏜다** | 11-3 의 5번 |
| **P-3** | 크래시 리포트 파일도 **지금 기록 파일이 쌓이는 폴더에 같이** 남긴다. 이름은 `crash-report` 로 | 11-2 참조 — **폴더는 가능, 이름은 제약 있음** |

### 11-1. 공식 문서로 확인된 사실

| 코드 | 확인된 것 |
|---|---|
| **C1** | 크래시 리포트는 기본으로 **앱 사용자 데이터 폴더 아래 `Crashpad` 폴더**에 쌓인다 |
| **C2** | **그 폴더를 다른 곳으로 바꿀 수 있다** — 위치를 지정하는 방법이 따로 있다 |
| **C3** | **서버로 안 올리게 끌 수 있다.** 끄면 폴더에 저장만 하고 안 올린다 |
| **C4** | 같이 실을 값의 크기 — 식별자 **39바이트**, 값 **127바이트** |
| **C5** | 실행 중에 값을 채우는 별도 방법은 한도가 훨씬 크다(2만 바이트대) — **착수 때 확인** |
| **C6** | **앱이 켜지는 아주 초반에 시작**해야 한다 |
| **C7** | 그 **뒤에 만들어진 화면만** 감시 대상이 된다 |
| **C8** | 남은 흔적 목록을 물어보는 방법은 **올려 보낸 것만** 준다 → 우리는 **폴더를 직접 읽는다** |

### 11-2. ★파일 위치와 이름 (P-3 처리)

| 항목 | 가능 여부 | 방법 |
|---|---|---|
| **폴더를 지금 기록 폴더 쪽으로** | **가능**(C2) | 크래시 리포트 저장 위치를 기록 폴더 아래로 지정한다 |
| **파일 이름을 `crash-report` 로** | **그대로는 안 된다**(공식 방법 없음 — **판단, 착수 때 재확인**) | 이름은 그 장치가 스스로 정한다. 우리가 바꿀 수 있는 건 **폴더뿐**이다 |

**그래서 이렇게 한다**

1. 크래시 리포트 저장 위치를 **기록 폴더 아래 하위 폴더 하나**로 지정한다.
   (기록 폴더에 **바로** 두지 않는 이유: 그 장치가 자기 하위 폴더와 설정 파일을 여러 개 만든다.
   지금 기록 파일과 섞이면 **3개월 지난 것 지우는 기존 로직이 그 파일들까지 훑게 된다.**)
2. **앱을 켤 때** 그 폴더에 새 크래시 리포트가 있으면,
   **`crash-report_날짜시각` 이라는 이름으로 기록 폴더에 옮겨 담는다.**
   → 장군님이 원하신 "기록 폴더에 `crash-report` 라는 이름으로" 가 이 시점에 이뤄진다.
3. 옮겨 담은 그 파일을 **텔레그램으로 쏜다**(P-2).

- 이렇게 하면 **기록 폴더만 열어 봐도** 날짜별 기록 파일과 크래시 리포트이 나란히 보인다.

### 11-3. 할 일 순서

| 순 | 할 일 |

| 3 | 크래시 리포트 저장 위치를 **기록 폴더 아래 하위 폴더**로 지정한다(C2) |
| 4 | 같이 실을 값을 채운다 — **마지막에 누른 버튼 · 화면 이름 · 앱 버전**. 조작이 바뀔 때마다 갱신. 127바이트 넘으면 뒤를 자른다(C4) |

| 6 | 이미 보낸 크래시 리포트는 **표시해 두고 다시 안 보낸다** |

- **완료 기준**: 앱을 강제로 죽인 뒤 다시 켜면 ① 기록 폴더에 `crash-report` 로 시작하는 파일이 생기고
  ② 방에 그 파일과 "지난번에 죽었다 + 그 시각 + 마지막 조작"이 도착한다. ③ 또 켜도 같은 것을 다시 안 보낸다.
- **한계**: 흔적 덩어리 자체는 **사람도 AI도 못 읽는다.** 어느 줄에서 터졌는지는 여기서 안 나온다.
  → 원인 분석의 본체는 **같이 보내는 글 기록**이다.
- **서버는 필요 없다.**

## W13. 가릴 것 가리기 + **환경 정보 남기기** (장군님 지시 2026-09-08)

  윈도우 로그인 계정 이름.

  3. **앱 환경** — 앱 버전, 바탕 프로그램 버전, 화면 언어, 테마.

## W14. 평상시 기록 심기 — "시스템이 남기는 수준"으로 (장군님 지시 2026-09-08)

> 지금은 **오류가 났을 때만** 남고, 프로그램이 어떻게 흘러갔는지가 거의 안 남는다.
> 그래서 오류 줄 하나만 덩그러니 있고 **그 앞뒤가 안 보인다.**
> 일반적인 시스템처럼 **주요 지점마다 한 줄씩** 남겨야 한다.

### 14-1. 기록 등급 — 네 단계로만

| 등급 | 언제 | 보기 |
|---|---|---|
| **알림** | 정상 흐름의 주요 지점 | 앱 시작, 로그인 성공, 화면 열림, 저장 시작·끝 |
| **주의** | 정상은 아닌데 계속 진행 가능 | 값이 비어 기본값으로 대체, 다시 시도해서 성공 |
| **오류** | 기능이 실패 | 저장 실패, 서버가 오류를 돌려줌, 화면 코드가 터짐 |
| **치명** | 앱을 더 못 씀 | 앱 본체가 터짐, 창이 죽음 |

- 등급은 **줄 앞에 표시**로 남긴다. 나중에 등급으로 골라 뽑기 위해서다.
- 자세한 속내(값 하나하나 찍어 보는 것)는 **평상시엔 안 남긴다.**

### 14-2. ★반드시 남겨야 하는 주요 지점

| 코드 | 주요 지점 | 남길 것 |
|---|---|---|
| **L1** | **앱 시작·종료** | 앱 버전, 윈도우 버전, 시작 시각 / 정상 종료인지 |
| **L2** | **로그인·서버 접속** | 어느 서버에 붙었는지, 성공·실패, 실패 사유 |
| **L3** | **화면 열림·닫힘** | 어느 화면인지, 여는 데 걸린 시간 |
| **L4** | **★서버에 보내고 받는 모든 자리** | 무엇을 요청했는지 / 성공·실패 / 걸린 시간 / 실패면 서버가 준 사유 |
| **L5** | **★스크립트 오류(화면 코드가 터진 것)** | 난 자리 전체, 없어진 값 이름 |
| **L6** | **저장·실행처럼 꼭 성공해야 하는 일** | 시작·끝·결과. 실패면 어느 단계에서 멈췄는지 |
| **L7** | **파일·자료 창고 읽고 쓰기 실패** | 무엇을 하다 실패했는지 |
| **L8** | **오래 걸리는 일** | 시작·끝과 걸린 시간(느려짐 추적용) |
| **L9** | **되돌리기·다시하기, 자료가 크게 바뀌는 일** | 무엇이 어떻게 바뀌었는지 요약 |

- **L4·L5 는 장군님이 특히 지목한 자리다.** 여기부터 손댄다.
- L4 는 **공통으로 지나가는 자리 한 곳**에 넣는다. 화면마다 넣으면 또 빠뜨린다.

### 14-3. 남길 때 지킬 것

| 코드 | 지킬 것 | 왜 |
|---|---|---|
| **L10** | 한 줄에 **언제 · 어느 화면 · 무슨 일 · 결과** 가 다 있게 | 그 줄만 봐도 뜻이 통해야 한다 |
| **L11** | 사람이 읽는 말로. 내부 이름만 던지지 않는다 | AI도 사람도 읽어야 한다 |
| **L12** | **값 통째로 찍지 않는다.** 모양과 개수만 | 파일이 터지고, 업무 자료가 새어 나간다 |

## W16. 보내는 부분을 한 파일에 모으고 끄는 스위치 두기 (장군님 지시 2026-09-08)

> **텔레그램 전송은 테스트 기간에만 한다.** 그래서 처음부터 **떼어내기 쉽게** 만든다.

- **할 일**
  1. **보내는 코드를 한 파일에만** 둔다. 오류 잡는 자리, 앱 켤 때 흔적 보내는 자리 등에서
     **그 파일의 함수 하나만 부른다.** 각자 직접 보내지 않는다.
  2. **켜고 끄는 스위치 하나**를 그 파일에 둔다. 꺼지면 **보내는 일이 전부 멈춘다.**
  3. **봇 열쇠와 방 번호도 그 파일에만** 둔다.
  4. 스위치가 꺼져 있으면 **전송 대기열도 안 쌓는다.**
- **운영으로 넘길 때 할 일**
  - 스위치를 끈다. **그 한 줄이면 끝나야 한다.**
  - 봇 열쇠와 방 번호를 **앱에서 뺀다.**
- **꺼져도 그대로 도는 것 (반드시)**
  - 화면 코드가 터진 오류 → 기록 폴더에 날짜별로 쌓임
  - 서버와 주고받다 난 오류 → 기록 폴더에 날짜별로 쌓임
  - 평상시 주요 지점 로그 → 그대로 쌓임
  - 크래시 리포트 → 기록 폴더에 다른 이름으로 저장
  - 3개월 지난 파일 지우기 → 그대로
- **완료 기준**: 스위치를 끈 채로 일부러 오류를 내면 **방에는 아무것도 안 오고, 기록 파일은 정상으로 쌓인다.**
  스위치를 켜면 다시 방에 온다.
