# SAPGUI 시작 대기 팝업이 안 닫힌 건 — **재발. 안 끝났다** (2026-10-12)

## 0. ★★★ 재발했다 — 「PC 재부팅으로 해결」은 틀린 결론이었다 (2026-10-12 두 번째)

장군님: 「또 같은 문제를 겪고 있는데 이럴때마다 pc를 재부팅 해야되는거냐? 왜?」

**답: 아니다. 재부팅은 고친 게 아니라 증상이 잠깐 사라진 것이다. 원인은 아직 모른다.**
아래 §0-1 의 「재부팅으로 해결」은 **틀린 판정**이므로 그대로 두되 믿지 말 것.

### 왜 또 깜깜한가 — 이미 적어 뒀던 것을 안 고쳤기 때문

이 문서 §4 에 **「1초마다 도는 검사에 로그가 한 줄도 없다」** 고 적어 두고 **지시 대기로 남겨 뒀다.**
그래서 이번에도 **어디서 끊겼는지 증거가 0 이다.** 같은 일을 또 겪지 않으려면 **로그부터 심어야 한다.**

### 지금 모르는 것 (추측 금지 — 전부 미확인)

| 모르는 것 | 왜 모르나 |
|---|---|
| VBS 가 아예 안 돌았는지, 돌았는데 registry 쓰기에서 실패했는지 | VBS 쪽 성공/실패를 남기는 로그가 없다 |
| 1차 VBS(기존 SAP GUI 세션에 붙기)가 조용히 「성공」으로 끝나 2차가 안 돈 것인지 | 1차 결과를 남기는 로그가 없다 |
| 1초 감시가 registry 를 못 읽고 있었는지 | 그 자리에 로그가 0줄 |
| SAP 쪽이 값을 안 지운 것인지 | SAP 접속이 등록돼 있지 않아 ABAP 을 못 본다 |

### 제안 — 지금 고치지 말고 **로그만 심는다** (장군님 지시 대기)

고칠 자리를 모르는 상태에서 코드를 건드리면 지난번처럼 틀린 결론만 쌓인다.
**다음에 터질 때 한 번에 잡히도록 길목 4곳에 로그만 넣는다**(동작은 1도 안 바뀐다):

1. 1차 VBS 가 끝났을 때 — 성공/실패와 그 이유
2. 2차 VBS 를 띄웠는지 여부
3. 1초 감시가 registry 를 읽은 결과 (처음 3번 + 5초마다, 못 읽으면 그 자리에서)
4. 30초를 꽉 채우고 끝났을 때 — 마지막으로 본 값이 무엇이었는지

**당장은 재부팅이 유일한 임시 조치**다. 원인을 모르니 다른 처방을 드릴 수 없다.

**PC 를 재부팅하니 정상으로 돌아왔다. 앱·VBS·SAP 모두 코드 문제가 아니었다.**

| 확인한 것 | 결과 |
|---|---|
| 앱이 registry 에 적은 browserkey | 정상 |

| VBS 가 `TCProxy\ActionParam` 에 적은 값 | **같은 값** |
| git 이력 — 이 기능이 지나는 자리 8곳 | **2026-09-23 이후 건드린 커밋 0건** |
| 조치 | **PC 재부팅 → 정상** |

**고친 코드 없음.** 조사용 로그 3줄만 넣었다(§3).

## 1. ★★★ 다음에 또 겪지 않으려면 — 내 조사 도구의 함정

**Bash · PowerShell 도구로 읽은 registry 값은 실제 값이 아니다.**
이 세션에서 같은 키를 두고 이런 일이 벌어졌다:

| 읽은 방법 | `cSession` / `ActionParam` |
|---|---|
| 내 Bash · PowerShell 도구 (샌드박스를 꺼도 동일) | **옛날 값** |
| 장군님 터미널(`run_in_terminal`) · regedit | **진짜 값** |

이 때문에 **「값이 서로 다르다 → 클라이언트가 두 값을 쓴다」 는 틀린 결론**을 내고
장군님 시간을 크게 버렸다. **registry 는 앞으로 `run_in_terminal` 로만 읽는다.**
(메모리 등록: `registry-reads-by-my-tools-are-stale`)

같이 틀렸던 것들 — 전부 저 가짜 값 때문:
- 「값이 0개다」 · 「WMI 와 Win32 가 어긋난다」 · 「유령 값이 남아 있다」 · 「key 를 지우면 된다」

## 2. 실제로 맞았던 판단

- **git 이력 전수**(함수 범위로 떠서 확인) — 이 기능은 9/23 이후 누구도 안 건드렸다. 이번 세션 수정분도 무관.
- **로그를 넣어 세 자리의 browserkey 를 찍은 것** — 클라이언트가 결백함을 한 번에 증명했다.
- **첫 번째로 드린 처방이 재부팅이었다** — 중간에 가짜 값에 끌려 다른 길로 샜다.

## 3. 조사용 로그 3줄 — **전부 뺐다** (장군님 지시 2026-10-12)

조사 중 `js/ws_common.js` 1줄 · `js/ws_fn_04.js` 2줄에 browserkey 를 찍는 로그를 넣었고,
원인이 PC 쪽으로 확정된 뒤 **장군님 지시로 전부 제거**했다.

- `js/ws_fn_04.js` — **커밋 상태로 완전 복귀**(변경 0).
- `js/ws_common.js` — 이번 조사 전부터 있던 **세션 종료 자리 1줄만** 남아 있다(별창 작업분, 이 건과 무관).

문법 검사(`node --check`) 두 파일 통과.

## 4. 고치지 않고 남겨 둔 것 (보고만)

- **1초마다 도는 검사에 로그가 한 줄도 없다.** 그래서 이번에 아무것도 몰랐다.
  registry 읽기가 실패해도 **조용히 넘어가 30초를 꽉 채운다** — 그 사실이 어디에도 안 남는다.
- **개발 모드에서 registry 라이브러리의 바깥 스크립트 폴더가 실제로 없다**
  (`node_modules\electron\dist\resources\regedit\vbs`). 라이브러리가 폴더 없으면 자기 것을 쓰게 돼 있어
  **동작에는 지장 없다**(라이브러리 소스로 확인). 다만 **포장본과 개발 모드가 서로 다른 스크립트로 돈다.**
