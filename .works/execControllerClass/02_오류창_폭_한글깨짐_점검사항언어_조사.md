## 2. 창 폭이 너무 긴 이유

| 자리 | 폭 설정 |
|---|---|
| 원본 `U4A_WS3.0.0/www/ws30/ws10_20/js/ws_fn_04.js` 407줄 | `contentWidth: "500px"` — **고정 폭** |
| 고치기 전 현행 `www/ws30/ws10_20/js/ws_fn_04.js` 457줄 | `min-width: min(31.25rem, 90vw); max-width: 90vw;` — **최소 폭만** 있고 폭은 안 정함 → **✅ 2026-09-17 `width: min(31.25rem, 90vw)` 로 고침** |

- 폭을 정하지 않은 `<dialog>` 는 내용 길이만큼 넓어진다. 오류 문장(경로 + 깨진 글자)은 한 줄로 길어서 **최대 폭(화면의 90%) 까지 늘어났다** — 첫 번째 캡처.
- 두 번째 캡처는 오른쪽 아래 모서리로 줄인 크기로 보이며, 원본의 500px 과 거의 같다.
- 원본과 어긋난 것은 **제 변환 실수**였다. `width: min(31.25rem, 90vw)` 한 곳만 바꿨다(31.25rem = 500px, 좁은 창 대비는 반응형 규칙).

## 3. 한글이 깨지는 이유 · 원본에 고치는 코드가 있나

**결론: 원본에는 고치는 코드가 없다.** 원본으로 돌려도 똑같이 깨진다.

| 확인한 것 | 결과 |
|---|---|
| 원본 `ws_fn_04.js` 138·202줄 | `parent.SPAWN('cscript.exe', aParam)` — 인코딩 옵션 없음 |
| `parent.SPAWN` 정의 (원본 `ws30/resources/index.js` 1390줄) | `require("child_process").spawn` 그대로 |
| 원본 `ws_fn_04.js` 148·214줄 (stderr 받는 곳) | `data.toString()` — Node 기본값 **UTF-8** 로 읽음 |
| 원본 `www` 앱 코드 전체 검색 `iconv` · `euc-kr` · `cp949` · `ms949` · `chcp` · `TextDecoder` · `setEncoding` (`_` 폴더·에디터 라이브러리 제외) | stderr·VBS 쪽에서 **0건** (`TextDecoder('utf-8')` 1건은 `ws_usp.js:5181` 로 다른 기능) |
| 원본 `package.json` 직접 의존성 | `iconv-lite` **없음** (`node_modules` 에는 다른 패키지가 끌고 온 것만 있음) |
| 원본 저장소 안 `.vbs` 파일 | 없음 (VBS 는 userData `ext_api\vbs` 에 있음) — VBS 쪽에서 `//U`(유니코드 출력) 같은 처리도 앱 코드에서 안 넘김 |

**깨지는 이유 (추정 — 앱 실행 확인은 안 함):**
- `cscript.exe` 는 오류 문장을 **윈도우 한글 코드페이지(CP949)** 로 쓴다. 앱은 그것을 **UTF-8** 로 읽는다 → 한글만 `���` 로 깨진다.
- 근거: 같은 줄에서 **영어·숫자(`sapgui_ws.vbs(508, 3) WshShell.Exec:` · `Exec`)는 멀쩡하고 한글 자리만** 깨졌다. 두 인코딩에서 영어·숫자 바이트는 같고 한글만 다르다.
- 원문은 윈도우 언어에 따라 다르다 — 한글 윈도우라 한글 오류 문장이 나왔다.

**고치는 방법 = §5** (처음 적은 「euc-kr 고정」 안은 한글 윈도우가 아닌 PC 에서 안 맞아 §5 로 대체).

## 4. 「점검사항」 이 영어로 뜨는 이유

**결론: 원본도 똑같이 영어로 뜬다.** 현행 함수는 원본과 창 투명도 2줄 말고 같다(diff 확인).

| 자리 | 쓰는 언어 |
|---|---|
| 도움말 파일 경로 — `ws_fn_04.js` 271줄 `PATH.join(APPPATH, "help", "controllerClass", WS_LANGU, "index.html")` | `WS_LANGU` |
| `WS_LANGU` 정의 — `ws_fn_04.js` 22줄 (원본 21줄) | `SETTINGS.globalLanguage` = **`ws_settings.json` 의 전체 설정 언어** |
| 이 PC 의 값 (`%APPDATA%\com.u4a_ws3.app.dev\conf\ws_settings.json`, 2026-09-17 조회) | **`"globalLanguage":"EN"`** |
| 같은 창의 제목 「VBS 실행 오류」 · 「점검사항」 버튼 글자 — `WSUTIL.getWsMsgClsTxt` (`ws_util.js` 992줄) | 넘긴 `WS_LANGU` 보다 **`process.USERINFO.LANGU`(로그인 Workspace 언어)를 먼저 쓴다** → 한글로 나옴 |

- 그래서 **창 글자는 로그인 언어(한글), 도움말은 전체 설정 언어(영어)** 로 갈린다.
- 도움말 폴더는 `www/help/controllerClass/KO` · `EN` 둘 다 있다 — 한글 문서가 없어서 영어로 뜬 것이 아니다.
- `globalLanguage` 를 쓰는 곳: 서버 목록 화면 언어 선택(현행 `ServerList_v2/ServerList.js` 3310줄 · 원본 4585줄) · 첫 실행 기본값(현행 `intro.js` 1146줄 · 원본 1071줄, 없으면 `EN`).
- **✅ 2026-09-17 고침:** 도움말 언어를 `parent.process.USERINFO.LANGU` 우선, 없으면 `WS_LANGU`. 그 언어 폴더가 없으면 원본처럼 `EN`. 멈추는 두 자리(언어 폴더 없음 · `EN` 도 없음)에 영어 경고 로그 추가.

## 5. 2번(한글 깨짐)을 어떻게 고치나 (2026-09-17 장군님 물음 「2번은 어떻게 고친다는거야?」)

### 5-1. 오류 글자는 어디서 오나 (소스 확인)

| 자리 | 내용 |
|---|---|
| `ws_fn_04.js` — 1차 스크립트(`newSESSTION.vbs`) · 2차 스크립트(`sapgui_ws.vbs`) 실행 | `parent.SPAWN('cscript.exe', aParam)` — `aParam` 맨 앞 = 스크립트 경로 |
| 두 스크립트 안 (`%APPDATA%\com.u4a_ws3.app.dev\ext_api\vbs`) | stderr 에 직접 쓰는 줄은 **없다**. 오류는 `Err.Raise 999, "Error Occurred", ...`(`sapgui_ws.vbs` 478줄 · `newSESSTION.vbs` 285줄)와 실행 중 오류(캡처의 508줄 `WshShell.Exec`)뿐이다 |
| 그래서 stderr 로 오는 것 | **cscript 가 직접 찍는 오류 한 줄** = `스크립트경로(줄, 칸) 오류출처: 오류설명`. 캡처의 `오류설명` 은 **윈도우가 만든 한글 문장**이다 |
| 앱이 읽는 곳 | 1차 = `data.toString()` 뒤 `:` 로 잘라 세로막대(`\|`)가 있는지 봄 · 2차 = `data.toString()` 그대로 오류 창에 넣음 |

**스크립트(.vbs)를 안 고쳐도 되나? (2026-09-18 장군님 물음)** — **된다.** 깨지는 글자는 스크립트가 쓴 게 아니라 **cscript 가 찍은 것**이고(위 표), 깨지는 곳은 **앱이 그 바이트를 UTF-8 로 읽는 자리**다. 그래서 앱 쪽(실행 옵션·읽는 방식)만 바꾸면 된다.
- 스크립트를 고쳐도(`On Error` 로 잡아서 `WScript.StdErr` 로 직접 쓰기) 결국 **같은 cscript 출력 통로**로 나가서 코드페이지 문제는 그대로다 — 스크립트 수정으로 얻는 게 없다.
- 단 방법 가는 `//U` 가 cscript 자신이 찍는 오류 줄에 먹는지 **미확인**(§5-3 시험). 방법 나는 옵션을 안 바꾸므로 이 걱정이 없다.

### 5-2. 방법 두 가지

| | **방법 가 — cscript 에 `//U` 옵션 추가 (제 생각)** | 방법 나 — 옵션 그대로, PC 코드페이지로 읽기 |
|---|---|---|
| 하는 일 | 실행 인자 맨 앞에 `//U` 를 넣어 cscript 가 **유니코드(UTF-16LE)** 로 쓰게 하고, 앱은 `TextDecoder("utf-16le")` 로 읽는다 | 레지스트리 `HKLM\SYSTEM\CurrentControlSet\Control\Nls\CodePage` 의 `OEMCP`(한글 윈도우 = `949`)를 읽어 `949 → euc-kr` 같은 표로 `TextDecoder` 를 고른다 |
| 윈도우 언어 | **상관없다** — 영어·일본어·중국어 윈도우도 맞다 | 코드페이지→이름 표를 **제가 만들어야** 한다. 표에 없는 언어는 다시 깨진다 |
| 고치는 곳 | `ws_fn_04.js` 실행 2줄(`//U` 추가) + stderr 읽는 2곳 | `ws_fn_04.js` stderr 읽는 2곳 + 코드페이지 읽는 코드 새로. 레지스트리 라이브러리(`regedit`)가 **cscript 를 한 번 더** 띄워서 느린 PC 에선 오류 창이 늦게 뜬다 |
| `.vbs` 스크립트 | 안 고친다 | 안 고친다 |
| **확인 안 된 것** | `//U` 가 **cscript 자신이 찍는 오류 줄에도 먹는지** 미확인. 안 먹으면 **영어까지 전부 깨진다** → 반드시 먼저 시험(§5-3) | cscript 가 실제로 쓰는 코드페이지가 `OEMCP` 인지 미확인 (한글 윈도우는 OEM·ANSI 둘 다 949 라 한글 PC 에선 차이 없음) |

두 방법 공통:
- 오류 글자가 여러 조각으로 와도 한 글자가 반으로 잘려 깨지지 않게, 실행마다 `TextDecoder` 하나를 두고 `stream: true` 로 이어 읽는다.
- 1차 스크립트의 세로막대 판정은 **글자로 바꾼 뒤** 하므로 판정 동작은 그대로다.
- 로그(영어): 어떤 방식으로 읽었는지, 읽기 실패 시 바이트 길이. 오류 원문을 콘솔에 찍는 원본 동작은 그대로 둔다.
- 참고: 이 앱이 쓰는 레지스트리 라이브러리(`node_modules/regedit/vbs/util.vbs` 156~176줄)는 cscript 로 값을 내보낼 때 **ASCII 밖 글자를 `\uXXXX` 로 바꿔** 내보낸다. 우리 오류 줄은 cscript 가 직접 찍어서 이 방식은 못 쓴다.

**고친 것** — `www/ws30/ws10_20/js/ws_fn_04.js` (백업 `_ws_fn_04.js.stderrcpbak`)
- 새 함수: 레지스트리 `OEMCP` 를 창 하나에서 **처음 오류 날 때 한 번만** 읽어 `TextDecoder` 이름으로 바꾼다(표: 949·932·936·950·866·874·1250~1258·65001). 표에 없거나 못 읽으면 **원본과 같은 utf-8** + 영어 경고 로그, 다음 오류 때 다시 읽는다.

- 조각이 여러 번 와도 순서대로, 글자가 반으로 잘려도 이어서 푼다(실행마다 `TextDecoder` 하나, `stream: true`).
- 이 자리에서 예상 못 한 오류가 나면 `[WFN4-003]` 으로 콘솔·화면에 알린다(원본은 전역 오류로 올라갔다).
- 앱이 켜질 때는 아무것도 안 한다 — 오류가 났을 때만 레지스트리를 읽는다(느린 PC 부담 없음).
- 스크립트(.vbs)는 안 고쳤다. `node --check` 통과.
