# 03_response — BR27 검수 결과 반영·해명

## 요약

코덱스·안티 **둘 다 동일한 P1** 지적: BR27이 가상 선택 강조를 영속화하면서, 팝업이 재사용(재오픈/새로고침)될 때 이전 세션의 선택 키가 가상 스크롤러(`_vs.selKey`)에 남아, 새 데이터에 같은 `CHILD` 키가 있으면 엉뚱한 줄에 강조가 되살아나는(유령 선택) 회귀. **유효한 지적 — 내 변경이 만든 회귀. 전부 반영.**

## 지적·반영 표

## 반론

- **P1-b의 "활성(`enable===true`)일 때만 선택·스크롤" 게이팅은 미채택(반론).** 처음엔 반영했다가 **되돌렸다.**
  - 이유: 이전 바인딩 줄로 **스크롤(원본 `setFirstVisibleRow`, callBindPopup.js:596 / BR28 재현)**은 그 줄의 선택 가능 여부와 무관하게 항상 해야 한다. 활성 조건으로 막으면 **N건 집합 바인딩의 경로가 비활성 노드일 때 선택·스크롤이 통째로 안 되는 회귀**가 생긴다(BR28 검수에서 동일 지적).
  - "비활성 노드가 화면만 선택돼 보이는 불일치"는 **BR27 이전부터 있던 원본 동작**(원본 `selectByKey`도 그 줄을 강조)이라 BR27 범위에서 바꾸지 않는다(원본 1:1). 필요 시 별도 이슈.
  - "없는 키 저장으로 인한 유령"은 **P1 세션 초기화 하나로 이미 차단**되므로 활성 게이팅 없이도 안전.
- 그 외 반론 없음. 핵심 P1은 반영.

## 원본 parity 확인

- 원본 `design/js/callBindPopup.js` 닫기 경로는 모델 데이터를 비우고 refresh → 재오픈 시 과거 선택이 남지 않는다. HTML5는 컨트롤·스크롤러를 재사용하므로 **세션 시작 시 선택을 명시 해제**해야 원본과 같은 "백지 후 재선택" 흐름이 된다. 이번 반영이 그 parity를 맞춘다.
- 선택은 "이전 바인딩 줄이 현재 데이터에 실제 존재하고 선택 가능할 때만" — 원본 `lf_setSelectTreeItem`의 의도(바인딩 가능 줄 강조)와 일치.

## BR28와의 경계

- BR28(재오픈 스크롤 위치)의 rAF 스크롤 블록은 그대로 두었다. 실제 조건(바인딩 필드가 현재 데이터에 존재+활성)에선 이전과 동일하게 스크롤이 실행된다. BR27은 **선택 키** 잔존만 다루며 BR28의 **스크롤 위치(scrollTop)** 초기화는 건드리지 않았다(별도 이슈).
