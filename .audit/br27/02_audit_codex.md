# 02_audit_codex — BR27 바인딩 필드 목록 가상 스크롤 검수

## 판정

**수정필요**

## 지적

### 1. [P1] 재사용되는 팝업에서 이전 세션의 선택 키가 남아 잘못된 행이 다시 강조된다

- 위치: `www/ws30/ws10_20/theme/u4a-ui.js:1667-1679`, `www/ws30/ws10_20/js/fnBindPopupOpen.js:548-600`, `967-1016`, `1046-1074`
- BR27은 가상 모드 `selectByKey()`가 `_vs.setSel(sKey)`를 호출하도록 바꿔, 화면 밖으로 나간 선택 행의 강조를 의도적으로 영속한다.
- 그러나 바인딩 팝업은 닫을 때 `dialog.close()`만 하고 `oUI.ctrl`/`oUI.tree`/가상 스크롤러를 재사용한다. 다음 `fnBindPopupOpen()`은 `oS.selNode`와 데이터만 초기화할 뿐 `_vs`의 선택 키를 지우지 않는다.
- 새 데이터 로드 후 `lf_renderTree()`의 `rerender(false)`는 “첫 행 자동 선택 안 함”만 수행하며 기존 가상 선택 키를 초기화하지 않는다. `oTree.render()`가 행을 재생성할 때 이전 `_vs.selKey`와 같은 CHILD 키가 새 데이터에도 있으면 그 행에 `aria-selected="true"`가 다시 붙는다.
- 새 속성이 미바인딩 상태라 `lf_setSelectTree()`의 `L_UIATV`가 비어 있으면 이후 올바른 선택으로 덮어쓰는 단계도 없다. 결과적으로 `oS.selNode === null`인데 화면에는 이전 필드가 선택된 것처럼 보이는 상태가 된다.
- 실패/빈 데이터 후 다른 속성으로 재호출하는 경로에서도 동일하다. `makeColumnTree.rerender()`의 빈-root 분기는 `selNode`만 null로 만들고 가상 선택 키와 기존 rows를 초기화하지 않는다.
- 기존 바인딩 키가 현재 응답에 없거나 해당 노드가 `enable !== true`인 경우도 안전하지 않다. `lf_setSelectTree()`는 노드 유효성·활성 여부를 확정하기 전에 `selectByKey(L_UIATV, true)`를 호출하고, `selectByKey()`는 대상 행을 찾지 못해도 `_vs.setSel(L_UIATV)`를 저장한다. 없는 키는 후속 데이터에서 같은 키가 나타날 때 유령 강조로 되살아나며, 비활성 노드는 즉시 시각 선택만 남고 `oS.selNode`는 null인 불일치를 만들 수 있다.
- 이 문제는 비가상 시절에는 전체 DOM 재렌더가 `aria-selected`를 자연히 제거했기 때문에 BR27의 선택 영속 변경으로 새로 생긴 회귀다.
- 원본 `design/js/callBindPopup.js`의 닫기 경로는 모델 데이터를 `{}`로 비우고 refresh한 뒤 닫는다. 반면 HTML5 경로는 컨트롤과 `_vs`를 유지한 채 dialog만 닫으므로, 과거 선택 잔존은 원본 동작과도 어긋난다.
- 영향: 사용자는 다른 속성의 팝업에서 과거 필드가 현재 선택값인 것으로 오인할 수 있다. 내부 적용 대상(`oS.selNode`)과 시각 선택이 불일치하며, 동일 팝업 재호출·새로고침에서 재현된다.
- 제안: 새 바인딩 세션/데이터 로드를 시작할 때 화면 소유 코드에서 `oUI.tree.selectByKey(null, false)`로 가상 선택 키와 DOM 강조를 명시적으로 초기화한 뒤, 서버 응답 후 기존 바인딩이 있을 때만 다시 선택한다. 공통 `rerender(false)`의 의미를 바꾸면 다른 소비처에 영향을 줄 수 있으므로 BR27 팝업 범위에서 초기화하는 편이 안전하다. 빈-root 처리에서도 가상 rows/선택을 비우는 공통 보완이 필요한지는 별도 검토한다.

## 확인 결과

### 가상 렌더링 자체

- `fnBindPopupOpen.js:969`의 `makeColumnTree({ virtual:true })`는 공통 `createTree`에 `virtual:true`와 `scrollContainer:oHost`를 전달한다.
- 펼친 노드만 평탄화한 뒤 `makeVScroller`가 보이는 구간과 오버스캔만 DOM으로 생성하므로 전 행 DOM 렌더 문제는 해소된다.
- 실제 행높이를 측정해 `--u4a-vsrowh`에 기록하고, 컬럼 트리의 행·빈 영역 격자도 같은 토큰을 사용한다. 3열 고정폭·가로 스크롤 구조와 충돌하지 않는다.
- 원본 `sap.ui.table.TreeTable`의 윈도잉 성질을 복원한 것으로 임의 UX 추가는 아니다.

### 현재 세션 내 선택 동작

- 기존 바인딩 자동 선택은 `selectByKey(L_UIATV, true)`가 `scrollToKey()`로 대상 인덱스를 reveal하고 현재 DOM에 강조를 적용한 뒤 `_vs` 선택 키도 저장한다.
- 사용자 클릭은 `lf_selRow()`의 `selectByKey(n.CHILD, false)`가 현재 행을 강조하고 `_vs` 키를 갱신하므로 화면 밖 왕복 후 강조가 복원된다.
- 선택 불가 행 클릭은 `selectByKey(null, false)`로 현재 DOM 강조와 `_vs` 키를 모두 지운다. `findRow(null)`이 일치 행을 찾지 못하는 것은 의도한 전체 해제 동작이다.
- 다만 위 P1처럼 세션 경계 초기화가 빠져 전체 정확성은 통과할 수 없다.

### 공통 소비처 영향

- 비가상 소비처는 `bVirtual && _vs` 가드로 신규 상태 저장을 타지 않는다.
- 가상 소비처는 프로그램적으로 `selectByKey()`를 호출할 때 동일 키를 `makeVScroller`에 저장하므로 현재 세션의 선택 영속에는 맞는다.
- 공통 변경 자체에서 즉시 충돌하는 이중 `aria-selected`는 발견하지 못했지만, 선택 상태의 생명주기를 화면이 명시적으로 끝내야 한다는 새 계약이 생겼다. BR27 팝업은 그 계약을 충족하지 못한다.

### 독립 서브에이전트 재검수 취합

- 독립 검수에서도 팝업 세션 초기화 누락과 빈-root 조기 반환을 동일한 P1로 재현했다. BR28의 `requestAnimationFrame` 취소·재스크롤 보완은 스크롤 시점만 다루며 `_vs.selKey`를 지우지 않으므로 이 결함을 해소하지 않는다.
- 원본 닫기 로직이 모델을 비우고 refresh한다는 점도 대조해, 이 문제가 의도된 선택 유지 UX가 아니라 원본 parity 위반임을 확인했다.
- 추가로 “현재 데이터에 없는 기존 키”와 “비활성 노드 키”가 검증 전에 저장되는 경로를 확인했다. 이는 주 P1의 별도 재현 경로이며 판정을 강화한다.
- 다른 가상 소비처를 교차 확인한 결과, USP 트리는 모델의 `ISSEL`과 `selectByKey()`를 같은 키 또는 빈 키로 함께 갱신하고, MIME 트리는 자체 `rowHook`/`selKey`로 강조를 소유해 이번 한 줄 변경의 직접 영향을 받지 않는다. 비가상 소비처도 가드로 제외된다.
- 따라서 공통 가상화 기능 전체를 되돌릴 근거는 없고, BR27 팝업의 세션 시작 초기화 및 유효 노드 확인 후 선택 저장 순서를 보완하는 것이 최소·안전 수정 범위다.
