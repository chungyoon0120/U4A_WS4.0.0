# BR51 Codex 검수 결과

## 판정

**수정필요**

정상 검증 경로와 잠금 회수는 정합하지만, 검증 모듈 실패 시 검증되지 않은 값을 영속 변경 데이터에 계속 수집하므로 BR51의 원인인 “허용 범위 밖 값 수용”이 해소되지 않습니다.

## 지적

### 1. [P1] 모듈 실패를 알린 뒤 검증되지 않은 값을 그대로 변경 데이터에 수집함

- 위치: `www/ws30/ws10_20/js/ws_html5_ws20_attr.js:3890`, `www/ws30/ws10_20/js/ws_html5_ws20_attr.js:3904`
- 현재 catch는 `console.error`와 토스트만 실행하고 정상 흐름으로 복귀합니다. 이어지는 `attrChgAttrVal(sAttr, uityp)`가 검증되지 않은 `sAttr.UIATV`를 `prev._T_0015` 변경 데이터에 반영하며, 이후 미리보기 반영·재렌더·변경 플래그 처리도 계속됩니다.
- 원본 `www/ws30/ws10_20/design/js/uiAttributeArea.js:1924`~`1948`은 `require` 또는 `checkPropertyValue`가 실패하면 예외가 전파되어 `attrChgAttrVal`에 도달하지 않습니다. 즉 현재 구현은 원본의 fail-closed 경계를 fail-open으로 바꿉니다.
- 따라서 BR51 변경은 “조용한 실패”만 없앴을 뿐, 요청서 배경에 적힌 핵심 위험인 “허용 범위 밖 값 수용”은 그대로 남습니다. 모듈 누락·초기화 불완전·실행 오류 상황에서 잘못된 속성이 저장 데이터에 포함될 수 있어 데이터 무결성 관점의 P1입니다.
- 바깥 `finally`(`3970`~`3976`)가 busy·shortcut·자식창 busy·재진입 플래그를 모두 회수하므로, 오류를 다시 던지거나 명시적으로 후속 수집을 중단해도 잠금 고착은 발생하지 않습니다.

### 2. [P2] 사용자 메시지가 메시지 키를 거치지 않고 내부 예외 원문을 노출함

- 위치: `www/ws30/ws10_20/js/ws_html5_ws20_attr.js:3897`~`3898`
- `.claude/rules/code.md`는 “원본에 없고 지시 없으면 `ZMSG_WS_COMMON_001` 사용”, “임의 문구 금지”, “메시지 함수로 키만 배선”을 명시합니다. 현재 `"WS20ATTR-CHK01: " + e.message`는 이 규칙과 반대입니다.
- `e.message`에는 로컬 경로, 모듈명, 런타임 내부 정보가 들어갈 수 있어 사용자 안내문으로도 부적절합니다. 상세 오류는 이미 `console.error(..., e)`에 충분히 남습니다.
- 요청서의 “DB에 임의 등록하지 않기 위해 원문 표시” 설명은 DB 직접 수정 금지와 기존 공통 메시지 키 사용을 혼동합니다. DB를 수정하지 않으면서 기존 공통 오류 키를 조회해 표시할 수 있습니다.

## 정상 확인 사항

- `checkPropertyValue` 성공 경로의 `RETCD === "E"` 처리(`valst`, `valtx`, `DEFVL` 복귀)는 원본 `uiAttributeArea.js:1924`~`1944`와 의미상 일치합니다.
- `parent.showMessage(null, 10, ...)`의 `null` 인자는 안전합니다. `www/ws30/resources/index.js:186`~`188`에서 HTML5 메시지 구현이 UI5 인자를 무시하고, KIND 10은 `287`~`291`의 토스트 경로입니다.
- `showMessage` 자체는 내부 try/catch로 격리되어 있고, 함수 전체의 `finally`가 잠금을 회수합니다.
- 정상 설치에서 검증 모듈이 성공하면 BR51 catch 변경으로 인한 정상 경로 변화는 없습니다.
- `node --check www/ws30/ws10_20/js/ws_html5_ws20_attr.js` 통과.
- `git diff --check -- www/ws30/ws10_20/js/ws_html5_ws20_attr.js` 통과.

## 제안

1. 검증 모듈 실패 시 사용자에게 공통 메시지 키 기반 오류를 표시한 뒤 `throw`하거나, 최소한 `attrChgAttrVal` 이하의 후속 수집을 중단하십시오. 바깥 `finally`가 잠금을 안전하게 해제합니다.
2. 상세 `e.message`는 콘솔에만 남기고 사용자에게는 지역화된 공통 오류 메시지와 추적 코드 `WS20ATTR-CHK01`만 표시하십시오.
3. 실패 전에 이미 `sAttr`/`T_ATTR`에 옮겨진 입력값을 유지할지 복원할지는 원본 동작과 UI 재렌더 계약을 기준으로 명시하십시오. 어떤 경우에도 검증 실패 값을 `prev._T_0015`에 수집해서는 안 됩니다.

## 독립 재검수 취합 (2026-08-20)

사용자 요청에 따라 두 독립 서브에이전트가 기존 판정을 반박하는 방향으로 다시 검증했습니다. 결론은 **P1·P2 모두 유지**입니다.

### P1 재입증

- 실패 catch 뒤 `attrChgAttrVal`에 도달하는 제어 흐름이 확정됐습니다.
- `attrChgAttrVal`은 기존 행이면 `1981`에서 `_T_0015`의 `UIATV`를 덮고, 신규 행이면 `1993`~`2008`에서 생성·push하며, 일반 프로퍼티 경로도 `2140`~`2141`에서 최종 수집합니다.
- 후속 `chkValidProp`(`2097`~`2106`)은 `checkPropertyValue`의 UW09 사용자 정의 범위 검증을 대신하지 못합니다. 타입상 올바르지만 허용 범위를 벗어난 값은 이 후속 검사만으로 차단되지 않습니다.
- 저장 구성은 `www/ws30/ws10_20/js/ws_html5_ws20_prev.js:443`에서 `getAttrChangedData()`를 호출하고, 반환된 변경분을 `YU4A0015`에 넣습니다. 따라서 검증 실패 값은 단순 화면 상태가 아니라 실제 저장 payload 후보입니다.
- 요청서의 좁은 기대 문구는 “오류 표면화”만 요구하지만, 같은 요청서의 버그 배경과 원본 fail-closed 계약은 “검증 없이 값이 수용되는 문제”를 명시합니다. 좁은 문구만으로 데이터 무결성 회귀를 통과 처리할 수 없습니다.

### P2 재입증

- `.claude/rules/code.md`의 기존 키 사용·임의 문구 금지 규칙과 현재 사용자 토스트 문자열이 직접 충돌합니다.
- DB를 직접 수정하지 않고도 동 파일의 `_wsMsg` 또는 공통 `getWsMsgClsTxt`/`fnGetMsgClsText`를 통해 기존 키를 사용할 수 있으므로, “DB 미등록을 위해 예외 원문 표시”는 필요한 선택이 아닙니다.
- 다만 적합한 메시지 번호는 요청서와 원본에 지정되지 않았으므로 검수자가 임의로 정하면 안 됩니다. 담당자가 번호를 지정해야 합니다.
- KIND 10과 `null` 인자 자체에는 문제가 없으며, 문제는 전달 문자열이 내부 `e.message` 원문이라는 점입니다.
