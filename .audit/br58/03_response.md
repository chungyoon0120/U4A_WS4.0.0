## 1. [반영] 창 여는 실패 갈래에서 잠금 영구 잔류 — 코덱스 P1-1 · 안티 P1-1

### 검증
- `package.json` devDependencies `electron: ^14.2.9`, 설치본 `14.2.9`. **Electron 14 의 `loadURL()` 은 Promise 를 돌려준다** → 로드 실패는 거부(rejection)로 오므로 동기 `try/catch` 로 못 잡는다. **지적 정확.**
- 수정 전에는 해제가 `did-finish-load` 안과 동기 `catch` 안에만 있었다. `did-fail-load`·`render-process-gone`·로드 완료 전 `closed` 에 해제가 없었다. **지적 정확.**
- `did-finish-load` 내부에서 `show()`/`setBrowserOpacity`/`setParentCenterBounds` 중 하나가 throw 하면 그 뒤 해제에 도달하지 못한다. **지적 정확.**

원본에도 같은 취약점이 있으나, BR58 이 "창 생성 실패 방어"를 명시적 변경점으로 선언했으므로 그 선언을 지키지 못한 것이 맞다.

### 반영 내용 — `ws_html5_call_tooltips_popup.js`
멱등 정리기 `lf_finish(사유, 오류, 실패여부)` 를 두고 **한 번만** 동작하게 했다(`bDone` 가드).
연결한 끝맺음 5가지:

| 끝맺음 | 실패로 보나 | 처리 |
|---|---|---|
| `did-finish-load` (성공) | 아니오 | 표시 처리는 `try/catch` 로 감싸 실패해도 해제까지 도달 |
| `loadURL().catch()` | 예 (단 `ERR_ABORTED` 는 취소로 처리) | 오류 표면화 + 창 파기 + 해제 |
| `did-fail-load` | 예 (`isMainFrame===false` 는 무시, 코드 `-3` 은 취소) | 상동 |
| `render-process-gone` | 예 | 상동 |
| `closed` (완료 전 닫힘) | 아니오 | 해제만 |

- 표시 처리(`show`/서서히 나타내기/가운데 배치)를 `try/catch` 로 감싸 **어떤 경우에도 해제에 도달**하게 했다.
- `ready-to-show` 의 가운데 배치도 개별 `try/catch`(`WS20HELP-04`) — 여기서 throw 해도 흐름이 끊기지 않는다.
- `did-fail-load` 는 본문(주 화면) 실패만 본다. 도움말 문서 3종에 하위 화면(`<iframe>`)이 0건임은 확인했으나, 문서가 나중에 바뀔 수 있으므로 방어로 둔다.

## 2. [반영] 통합 도움말 opener 의 약속 거부 미처리 — 코덱스 P1-2 · 안티 P1-2

### 검증
`fnDialogPopupOpener.js:2061` 의 `fnU4AHelpDocuPopupOpener` 는 `async` 함수다. 내부에서
`parent.require(...)` 실패나 `await oHelpDoc.Excute(...)` 거부가 나면 **이미 켠 `fnSetBusyLock("X")` 를 못 끄고** 거부된 약속을 돌려준다. 호출부 3곳은 `await`/`.catch()` 없이 즉시 `return` 하므로 동기 `try/catch` 로는 못 잡는다. **지적 정확.**

원본(uiAttributeArea 614 / uiDesignArea 978 / uiPreviewArea 127)도 `await` 하지 않는다 —
즉 **원본과 동일한 구조의 위험**이다. 그러나 프로젝트 코딩규칙(`code.md`)의
"busy on 은 모든 종료 분기에서 off 짝 필수" 가 상위이고, `.catch()` 추가는 **성공 경로 동작을
전혀 바꾸지 않고 실패 때만 회수**하므로 원본에 없는 UX 창작이 아니다. → 반영.

### 반영 내용
세 곳(트리 `WS20HELP-11` / 속성 `WS20HELP-21` / 미리보기 `WS20HELP-31`) 모두:
돌려받은 값이 약속이면 `.catch()` 를 걸어 오류를 콘솔에 드러내고 `parent.setBusy("")` 로 해제.
동기 throw 도 그대로 같은 코드로 처리.

## 4. [반영] 신규 파일 전송 실패가 WS20 전체 로드를 중단 — 코덱스 P1-5

### 검증
`library-preload.js` 의 `loadLibrary` 는 `success` 안에서만 다음 index 로 재귀한다.
`error` 콜백(수정 전 274~276행)은 **로그만 찍고 재귀도 최종 콜백도 하지 않는다.**
따라서 목록 앞쪽 파일이 404/읽기 실패하면 **그 뒤 전부가 안 실린다.** 내 파일을
`ws_html5_ws20.js` 앞에 둔 상태였으므로, 선택적 도움말 폴백 하나가 WS20 전체 기동 실패로
번질 수 있었다. **지적 정확이며, BR58 이 새로 만든 위험이다.**

요청서에 쓴 "미로드 시 `WS20HELP-12/22/32` 로 표면화된다"는 설명도 **부정확**했다(그 코드가
실행되려면 tree/attr/prev 가 실려 있어야 하는데, 앞에서 끊기면 그것들부터 안 실린다). 정정한다.

### 반영 내용
공통 로더는 건드리지 않고(파급이 크다), **신규 파일 등록을 목록 맨 뒤로 옮겼다.**
근거: 이 파일은 `oAPP.fn.callTooltipsPopup` **정의만** 하고 실제 호출은 도움말 버튼을 누를 때다.
로드 시점 참조가 없음을 확인했다(tree 433 / attr 5379+ / prev 1235+ 모두 클릭 처리 안).
따라서 맨 뒤여도 기능은 동일하고, 이 파일이 빠져도 **WS20 필수 파일은 전부 정상 로드**된다.
그 상황에서 도움말 버튼만 `WS20HELP-12/22/32` 로 드러난다(요청서 설명이 이제 실제와 일치).

**별건 — 폐기(장군님 판단 2026-08-31).** `loadLibrary` 의 `error` 갈래가 재귀·최종 콜백을
하지 않는 것은 사실이나, **실전에서 발생하지 않는다** — 목록의 38개 파일이 모두 앱 파일
안으로 같이 말려 들어가므로 배포본에서 한 개만 빠지는 상황이 없고, 빠졌다면 빌드 자체가
잘못된 것이라 배포 전에 걸린다. 발생하지 않는 상황을 위해 부팅 순서를 건드리는 것은
위험만 크다 → **조치하지 않고 닫는다.** (코덴스가 근거로 든 '신규 파일이 깃에 안 올라감'도
커밋하면 사라지는 걱정이다.)
다만 신규 파일을 목록 맨 뒤로 옮긴 것은 그대로 둔다 — 순서와 무관한 파일이라 기능은 동일하고,
개발 중 그 파일을 잠긐 지우거나 이름을 바꿔볼 때 화면이 통째로 죽지 않는 이득은 남는다.

## 5. [반영] 성공 처리 `on` → `once` — 코덱스 P2-7

원본은 `on("did-finish-load")` 이지만, busy/단축키 잠금은 참조 세기가 없는 전역 토글이라
도움말 창이 나중에 다시 로드되면 **그때 진행 중인 다른 작업의 잠금을 풀 수** 있다. **지적 정확.**
`once` 로 바꾸고 멱등 정리기로 묶어, 어떤 경로로도 해제는 **평생 한 번만** 일어난다.
사용자가 보는 동작은 원본과 동일하다.

## 6. [현행 유지 확정] 화면에 추적 코드 `WS20HELP-02` 표시 — 코덱스 P2-4 · 안티 P2-2

### 판단 근거
- 규칙(`code.md`): "메시지는 원본 키 참조, 원본에 없고 지시 없으면 `ZMSG_WS_COMMON_001`.
  **임의 문구·키 생성 금지, 필요 키 보고**." — 지적의 취지는 맞다.
- 그러나 원본 `callTooltipsPopup` 에는 **창 생성/로드 실패용 안내가 아예 없다**(파일 없음
  안내 `377` 뿐). 쓸 원본 키가 존재하지 않는다.
- 안내를 없애면 사용자는 **아무 반응 없이 도움말이 안 뜨는** 상태가 되어 더 나쁘다.
- 같은 상황에서 **BR51 이 이미 동일한 형태로 운영 중**이다
  (`ws_html5_ws20_attr.js:4161` `parent.showMessage(null, 10, "E", "WS20ATTR-CHK01")`,
  주석에 "정식 안내 문구 키는 장군님 번호 지정 대기"). 장군님 테스트 통과·수정완료 처리된 선례다.

### 장군님 결정 (2026-08-31) — **그대로 둔다. 메시지 번호를 만들지 않는다.**

근거: 빌드 설정상 도움말 문서가 **앱 파일 안으로 같이 말려 들어간다**(`asar: true`,
포함 목록에 `www/**/*`, 바깥 리소스에는 없음). 따라서 배포본에서 파일이 없거나
못 읽는 일이 사실상 없으므로 **이 안내가 화면에 뜼 일 자체가 없다.**
도달할 일 없는 자리에 메시지 번호를 소모하지 않고, 만에 하나 터졌을 때는
추적 코드가 그대로 보이는 편이 원인 찾기에 난다.

소스 주석(`ws_html5_call_tooltips_popup.js` 리리스 처리부)에도 이 결정과 근거를 적어 두었다.
BR51 의 `WS20ATTR-CHK01` 은 별건이므로 **그대로 둔다**(이번 결정 범위 밖).
