## 1. 무엇을 고쳤나

원본은 도움말 버튼을 누르면 두 갈래로 간다 — 서버에 통합 도움말이 등록돼 있으면 그쪽 창을 열고,
등록이 없는 구버전 서버면 앱 안에 들어 있는 도움말 문서 창을 연다.
HTML5 는 앞갈래만 살아 있고 **뒷갈래가 세 영역 모두 죽어 있었다.**

| 영역 | 고치기 전 | 고친 뒤 |
|---|---|---|
| UI 트리 | 부를 때 첫 인자가 `null` 이라 원본의 `if(!oUi) return` 에 걸려 무반응 | 눌린 버튼 전달 |
| 속성 | 폴백 호출 자체가 없고 "아직 작업중입니다" 안내만 | 원본대로 호출 |
| 미리보기 | 함수가 실린 적이 없어 콘솔 경고 후 종료 | 이식본 로드 + 원본대로 호출 |

이식본 = `www/ws30/ws10_20/js/ws_html5_call_tooltips_popup.js` (원본 `design/js/callTooltipsPopup.js` 140행 → 245행).

**이슈 본문의 원인 설명은 사실과 달랐다.** "원본이 `sap.m` 팝업이라 변환 불가"라고 적혀 있었으나,
원본은 UI5 컨트롤을 하나도 쓰지 않고 별도 창에 정적 HTML 을 띄운다. 두 검수 모두 이 판단이 맞다고 확인했다.

## 3. 장군님 결정 2건 (2026-08-31)

### (가) 도움말 창 열기 실패 안내 — **메시지 번호를 만들지 않고 그대로 둔다**

빌드 설정상 도움말 문서가 앱 파일 안에 같이 말려 들어가므로(`asar: true`, 포함 목록에 `www/**/*`,
바깥 리소스 아님) 배포본에서 파일이 없거나 못 읽는 일이 사실상 없다.
**도달할 일 없는 자리**에 메시지 번호를 소모하지 않고, 만에 하나 터지면 추적 코드가 보이는 편이
원인 찾기에 낫다는 판단. 소스 주석에도 결정과 근거를 남겼다.
BR51 의 같은 형태는 별건이므로 손대지 않았다.

### (나) 파일 목록 읽기 공통 처리 별건 — **폐기**

목록의 38개 파일이 모두 앱 파일 안에 말려 들어가므로 배포본에서 한 개만 빠지는 상황이 없다.
빠졌다면 빌드 자체가 잘못된 것이고 배포 전에 걸린다. 발생하지 않는 상황을 위해 부팅 순서를
건드리는 것은 위험만 크다 → **조치하지 않고 닫는다.**
다만 신규 파일을 목록 맨 뒤로 옮긴 것은 그대로 둔다(순서와 무관한 파일이라 기능 동일, 개발 중 이득만 있음).
