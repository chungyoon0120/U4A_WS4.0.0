## 2. P2-1 반영 — 이동 구간 화면잠금 유지 (원본 1:1)

### 원본 확인

원본은 목록을 받은 **뒤에도 잠금을 계속 쥐고 있다가, 목록을 펼치기 바로 직전에 푼다.**

- 콤보 클릭 경로 `uiAttributeArea.js` 1128~1148행
  `setAttrFocus(UIATK,"E")` → `setShortcutLock(false)` → `sap.ui.getCore().unlock()` → … → `_oUi.open()`
- F4 키 경로 1335~1344행
  `setAttrFocus(UIATK,"E")` → `setShortcutLock(false)` → `parent.setBusy("")` → `_oUi.open()`

즉 **"이동 → (잠금 해제) → 펼치기"** 가 원본 순서다. 이동하는 동안엔 화면이 잠겨 있다.

### HTML5 가 어긋나 있던 지점

`getServerEventList` 는 **성공 콜백에 들어가기 전에** 화면잠금을 먼저 푼다
(`ws_html5_ws20_attr.js` 647행 `if (bSkipUnLock !== true) { parent.setBusy(""); }`).
그래서 이동·대기 구간에는 화면이 열려 있었다 — 두 검수가 지적한 그 틈이다.
(BR53 이전에는 조회 직후 같은 처리 안에서 곧바로 펼쳤기 때문에 틈이 없었고, BR53 이 대기를 넣으며 틈이 생겼다.
 **내가 만든 틈이 맞다.**)

### 반영 내용

미등록 판정 분기에서 이동을 시작하기 직전에 화면잠금을 **다시 걸고**(`parent.setBusy("X")`),
대기가 끝나 **목록을 펼치기 직전에 푼다**(`parent.setBusy("")`). 원본이 잠금을 쥐는 구간과 동일하다.

```js
//이동 구간 화면잠금(원본 1:1)
try { if (parent.setBusy) { parent.setBusy("X"); bLocked = true; } }
catch (e) { console.error("[HTML5][WS20][attr][BR53] 이동 구간 화면잠금 실패(이동은 계속):", e); }
try { oAPP.fn.setAttrFocus(sAttr.UIATK, "E", { bKeepRow: true }); bMoved = true; }
catch (e) { console.error("[HTML5][WS20][attr][BR53] 미등록 서버이벤트 줄 이동 실패:", e); }
```

```js
return oAPP.fn.getServerEventList(fnOk, false)
    .then(function () { if (!bMoved) { return; } return _attrWaitScrollIdle(); })
    .catch(function (e) { console.error("[HTML5][WS20][attr] 서버이벤트 목록 조회 실패:", e && e.message); })
    .then(function () {                     // ← 조회 실패·예외도 반드시 여기로 온다
        if (!bLocked) { return; }
        bLocked = false;
        try { if (parent.setBusy) { parent.setBusy(""); } }
        catch (e) { console.error("[HTML5][WS20][attr][BR53] 이동 구간 화면잠금 해제 실패:", e); }
    });
```

### 이 처리가 지적을 실제로 막는 근거 (소스 확인)

- 화면잠금 본체 `www/ws30/resources/index.js` 873~889행:
  `document.body.style.pointerEvents = "none"` 로 **마우스 조작 자체를 차단**한다.
  WS20 은 그 body 안 프레임에 그려지므로, 프레임 안의 '변경 항목 보기' 버튼·트리 줄 클릭도 함께 막힌다.
  → 코덱스·안티가 든 재현 시나리오(대기 중 다른 줄 선택 / 변경 항목 보기 토글)는 **조작 자체가 안 된다.**
- 잠금은 **소유 표시(`bLocked`)로 한 번만** 푼다(BR60 에서 쓴 방식) — 남의 잠금을 대신 풀지 않는다.
- 껐다 켜는 것이 같은 처리 안에서 일어나 **그 사이 화면을 다시 그리지 않으므로 깜빡임이 없다**
  (조회 함수의 `parent.setBusy("")` → 내 `parent.setBusy("X")` 가 동일 실행 단위).
- 부수 확인: 화면잠금은 켤 때 **현재 커서 위치를 기억해 두었다가 끌 때 되돌려 준다**
  (같은 파일 898~918행). 켤 때 커서는 값칸(드롭다운)에 있고 끌 때도 같은 값칸으로 돌아오므로
  BR53 이 노리는 "그 줄 값칸에 커서" 결과와 어긋나지 않는다(오히려 한 번 더 보장된다).

## 3. P2-2 반영 — 대기 상한을 실제 시간으로도 보장

프레임 관찰(스크롤이 3프레임 연속 안 움직이면 끝)은 그대로 두고, **실제 경과시간 800ms 타이머**를 함께 건다.
먼저 도달한 쪽이 끝내고 나머지는 정리한다(중복 종료 차단).

```js
var _MAXMS = 800;
var bDone = false, iTimer = 0;
function fin() { if (bDone) { return; } bDone = true; if (iTimer) { clearTimeout(iTimer); iTimer = 0; } res(); }
iTimer = setTimeout(fin, _MAXMS);
```

- 이것은 "시간으로 눈속임"이 아니라 **끝남을 보장하는 상한**이다. 정상 경로는 여전히
  **실제 스크롤 위치**로 판정해 보통 3프레임(약 50ms)에 끝난다.
- 프레임 카운터 조건도 `iTick > 40`(=41프레임) → `iTick >= 40`(=40프레임)으로 바로잡았다(코덱스 참고 지적).

## 4. 남은 한 가지 — 공통 드롭다운 보강은 **허가 대기**(미반영)

두 검수 모두 마지막 수단으로 **공통 드롭다운(`www/ws30/ws10_20/theme/u4a-ui.js`)** 에
"값칸이 화면에서 사라졌으면 목록을 열지 마라"(`isConnected` 확인)를 넣으라고 권고했다.

- **미반영 사유**: 공통 자산 직접 수정은 규칙상 금지(`.claude/rules/code.md` — 공통은 고치지 말고 스코프로 덧대기).
  이 건은 스코프 override 로는 불가능하다(펼치기 결정이 공통 함수 안에서 일어나고, 바깥에서 취소할 수단이 없다.
  `_requestOpen` 은 내 약속이 성공이든 실패든 똑같이 `_open()` 을 부른다 — 소스 확인).
- **현재 상태**: 2절의 화면잠금으로 **정상 조작으로는 재현 불가**. 남는 경우는
  "다른 창에서 온 알림이 그 50ms 사이에 속성 줄을 다시 그리는" 경우뿐이며, 이는 정상 조작 경로가 아니다.
- **권고(장군님 판단 요청)**: 공통 드롭다운 `_open()` 맨 앞에
  `if (!oCombo.isConnected) { return; }` 한 줄을 넣으면 화면 전체에서 같은 사고가 원천 차단된다.
  사라진 값칸을 기준으로 목록을 여는 것은 어느 화면에서도 옳지 않으므로 부작용은 없다고 본다.
  **허가해 주시면 넣겠습니다.**

## 7. ★테스트 범위 정정 (장군님 지적 2026-08-21)

**지적**: "사용자가 이미 콤보를 열었는데 무슨 이동? 테스트가 의미가 있는거냐?"

**확인 결과 — 지적이 맞다.**

원본 `setAttrFocus` 가 하는 일은 네 가지다: ①위쪽 요약 영역 접기 ②그 줄 선택 강조
③그 줄로 화면 이동 ④그 줄 값칸에 커서.

그런데 이 호출 지점은 **사용자가 그 값칸을 직접 눌러서 시작하는 경로**다(값칸을 누르려면 그 줄이 보여야 한다).
따라서:

- **③ 화면 이동** — 그 줄은 이미 보이는 자리에 있다. 이동량은 사실상 0
  (`scrollIntoView({block:"nearest"})` 는 이미 다 보이면 움직이지 않는다).
- **④ 커서** — 값칸을 누른 순간 이미 그 값칸에 커서가 있다. 달라지는 것이 없다.

노션 이슈 본문에도 같은 취지가 적혀 있다: "이미 그 드롭다운을 연 상황이라 체감은 작다."

→ **이동·커서 항목(옛 BR53-2 / BR53-4)을 테스트에서 삭제**했다
(`.claude/rules/document.md` — 실제 화면 조작으로 재현되는 것만 적는다).

**남는 실제 효과는 두 가지뿐**이며, 이것이 이 수정의 전부다.
1. 위쪽 `UI Object ID`·`Description` 영역이 접힘
2. 그 이벤트 줄이 파랗게 선택 강조됨

**코드는 그대로 둔다** — 원본이 부르는 함수를 그대로 부르는 것이 원본 1:1 이고,
호출을 쪼개서 "접기·강조만" 부르는 것은 원본에 없는 변형이다(임의 창작 금지).

**곁들여 손본 부분은 여전히 필요하다**: 위쪽 영역 접기가 목록을 실제로 스크롤시키므로
(스크롤 위치를 직접 바꾼다), 그 신호에 펼침목록이 스스로 닫히는 것을 막는 대기·잠금 처리는 그대로 유효하다.
BR53-3 으로 확인한다.

**남은 의문(보고만)**: 이 경로에서 위쪽 영역을 접는 동작이 사용자에게 이득인지는 의문이다
(누르려던 값칸 위치가 화면에서 움직인다). 원본이 그렇게 하므로 원본대로 두었다.
빼기를 원하시면 지시 주시면 반영한다.

## 8. ★테스트 의미 재확인 (장군님 지시 "테스트 의미가 있는지 확인해", 2026-08-21)

원본이 부르는 처리 네 가지가 **이 경로에서 실제로 화면에 보이는지** 하나씩 소스로 확인했다.

| 원본 처리 | 이 경로에서 보이나 | 근거 |
|---|---|---|
| ① 그 줄 선택 강조 | **보인다 — 이 수정의 실질 효과** | 속성 줄에 선택 표시를 붙이는 곳은 `setAttrFocus` 하나뿐(`aria-selected` 전수 grep = 이 함수 + 재렌더 복원 2곳). 값칸을 눌러도 강조가 안 붙던 것이 붙게 된다 |
| ② 위쪽 요약 영역 접기 | **조건부 — 대부분 안 보인다** | 속성 줄 정렬이 **종류 순**(`_sortAttrRows` = UIATY 오름차순 → 프로퍼티(1) → 이벤트(2) → 집합(3)). 이벤트 줄은 프로퍼티 줄 **전부 아래**다. 접힘은 "스크롤을 내려 위쪽 요약 영역을 가리는 것"(`_attrHeaderExpanded(false)`)인데, 이벤트 값칸을 누를 수 있을 만큼 목록을 내린 상태면 **이미 가려져 있어** 변화가 0 이다. 프로퍼티가 아주 적은 UI 에서만 둘이 동시에 보여 접힘이 눈에 띈다 |
| ③ 그 줄로 화면 이동 | **안 보인다** | 값칸을 직접 눌러 시작하는 경로 = 그 줄이 이미 보임. `scrollIntoView({block:"nearest"})` 는 다 보이면 안 움직인다 |
| ④ 그 줄 값칸에 커서 | **안 보인다** | 값칸을 누른 순간 이미 그 값칸에 커서가 있다 |

**결론**: 이 수정으로 사용자가 실제로 보게 되는 변화는 **①줄 선택 강조** 하나이고,
②는 프로퍼티가 적은 UI 에서만 덤으로 보인다. ③④ 는 보이지 않는다.

**테스트 항목 재정리(5건)**: ①을 1번으로 올리고, ②는 **조건부(해당 UI 없으면 건너뜀)** 로 맨 뒤,
내가 곁들여 손본 대기·잠금 처리는 **회귀가 안 났는지**로 확인(BR53-2), 나머지 2건은 정상 경로 회귀 확인.
③④ 항목은 삭제.

**코드는 그대로 둔다** — 원본이 부르는 함수를 그대로 부르는 것이 1:1 이다. 눈에 안 보인다고 호출을
쪼개면 원본에 없는 변형이 된다(임의 창작 금지).

**참고(다른 세션 변경 감지)**: 검수 반영 중 다른 세션이 같은 함수에 `bNoRowSelect`(줄 선택 강조를
건너뛰는 옵션)를 추가했다. BR53 경로는 이 옵션을 넘기지 않으므로 **충돌·영향 없음**(되돌리지 않음).

## 9. ★선택 줄 결함 발견·수정 (장군님 실화면 지적 2026-08-21)

**지적**: "마우스 오버했을 때만 앞에 파란줄이 그어지는 게 맞냐"

**확인 결과 — 맞지 않다. 결함이었다.**

### 원인 (꾸밈 규칙 우선순위)

좌측 선택 줄을 **움푹한 표시(그림자)와 같은 자리**(`box-shadow`)에 그리고 있었다.

| 상태 | 겨루는 규칙 | 이기는 쪽 | 결과 |
|---|---|---|---|
| 마우스 뗌 | `.u4aWs20AttrRow[aria-selected="true"]` (0,2,0, 1044행) vs `.u4aWs20AttrRow.changeValue` (0,2,0, 1103행) | 같은 세기 → **뒤에 있는 changeValue** | 움푹한 그림자만, **파란 줄 사라짐** |
| 마우스 올림 | `[aria-selected="true"]:hover` (0,3,0) vs `.changeValue` (0,2,0) — `.changeValue:hover` 는 `background` 만 지정하고 `box-shadow` 를 안 씀 | **선택+hover 가 한 단계 세서 이김** | **파란 줄 나타남** |

→ 마우스 올림 여부에 따라 줄이 나타났다 사라지는 들쭉날쭉. 원본에도 없는 명백한 결함이다.

### 잘못 짚었던 것 (정정)

BR52 때 이 현상을 **"변경됨 표시가 선택 표시를 덮는 것이고 원본도 그렇다"** 로 결론내고,
테스트를 "값을 지워 변경됨 표시를 없애면 선택 강조가 드러나는지"로 잡았다. **틀렸다.**
또한 값이 바뀐 줄 판정은 **기본값과 다르면 참**(`_isChangedRow` — 이번 세션에 바꿨는지가 아니다)이라,
**서버이벤트 값이 들어 있는 줄은 언제나 변경됨 줄**이다. "값을 바꾼 적이 있으면"이라는 단서 자체가 틀렸다.

### 수정

좌측 선택 줄을 그림자 자리에서 떼어내 **따로 그린다**(`::before`) → 변경됨 표시와 자리를 다투지 않아
**마우스와 무관하게 항상 보인다**. 변경됨 표시(움푹한 배경)는 그대로 유지되어 두 표시가 함께 보인다.

- 파일: `www/ws30/ws10_20/WS10/css/ws20.css` (백업 `_ws20.css.br53selbak`)
- 화면 CSS 이며 공통 자산 아님. 색은 의미 토큰(`--accent`)만 사용, 하드코딩 없음.
- 속성 줄 전체에 해당하므로 **BR52 항목에도 같이 적용**된다 → 두 그룹 테스트 문구 모두 정정.

### 테스트 문구 정정

`.works/ws20attrchange/00_현황판.md` 의 BR53·BR52 그룹을 다시 썼다.
- "변경됨 표시가 덮으니 값을 지워서 확인" 단서 **삭제**.
- 두 그룹 모두 **"마우스를 그 줄 밖으로 완전히 치워도 파란 세로줄이 남는지"** 를 확인 항목으로 명시.

## 10. ★마무리 결정 (장군님 지시 2026-08-21)

**장군님 지적**: "노션 증상 '빨간 테두리는 표시되나 오류 콤보 행으로 화면이 이동하지 않는다' 는
이미 그 행의 값칸을 누른 상태인데 성립이 안 된다."

**맞다.** 이 이슈는 **원본 코드에 호출이 있다는 사실만 보고 증상을 적은 것**이고,
실제 화면에서는 사용자가 그 값칸을 직접 눌러 시작하는 경로라 **이동할 곳도, 옮길 커서도 없다.**

**결정**: "그냥 원본대로 해놓고 마무리 짓자" → **원본 호출 그대로 유지**, 코드 원복 없음.
- 원본이 부르는 처리(`setAttrFocus(UIATK,"E")`)를 그대로 부르는 상태를 유지한다(원본 1:1).
- 그 호출 때문에 필요해진 보호(움직임이 멎은 뒤 펼치기 + 그동안 화면잠금)도 함께 유지한다.
  빼면 프로퍼티가 적은 요소에서 펼친 목록이 바로 닫히는 새 결함이 생긴다.
- 화면에서 실제로 달라지는 것은 **그 줄 선택 표시** 하나뿐.
- 테스트는 **BR53-1 한 건**으로 끝낸다.

**곁들여 고친 진짜 결함(유지)**: 선택 줄(왼쪽 파란 세로줄)이 마우스를 올렸을 때만 보이던 문제 →
줄을 따로 그리도록 바꿔 항상 보이게. 속성 줄 전체 공통이라 BR52 에도 적용된다.

## 6. 공통 드롭다운 보강 — **최종 미반영 확정** (장군님 결정 2026-08-30)

4절의 "값칸이 화면에서 사라졌으면 목록을 열지 마라" 권고는 **넣지 않는다.**

- **원본에 없는 방어이고, 원본은 이 사고가 구조상 나지 않는다.** 원본(UI5)은 속성 목록을 다시 그려도
  값칸 컨트롤 인스턴스가 유지된 채 재렌더만 되므로 `open()` 이 항상 제자리에 뜬다.
  HTML5 는 `fnRenderWs20AttrRows` 가 `ROWS.innerHTML=""` 로 줄을 통째로 새로 만들어 옛 값칸이 고아가 되는
  구조 차이에서 생긴 문제다.
- **사용자 체감상으로도 옳지 않다** — 눌렀는데 아무 반응이 없는 동작이 된다(장군님 지적).
- **현 상태로 충분** — 2절의 이동 구간 화면잠금으로 그 사이 재렌더가 발생할 경로가 없다(정상 조작 재현 불가).
- 참고: 굳이 원본 동작에 맞추려면 "안 열기"가 아니라 "새로 그려진 같은 줄의 값칸을 찾아 거기에 열기" 여야 하나,
  이 역시 원본에 없는 창작이라 채택하지 않는다.
